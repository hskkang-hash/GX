## 1. 회수증 — **덤프 + 복구 시험**, 둘이 한 장이다 [실측 2026-09-07]

「백업 있음」은 절이 아니고 **「복구 성공」이 절이다**(D-354 ①). 그래서 두 칸을 함께 낸다.

### ① 덤프 — 무엇이 · 얼마나 · 언제

| 자리 | 파일 | 크기 | 시각(UTC) | sha256 | 뜬 클라이언트 |
|---|---|---|---|---|---|
| **볼륨** `gx_backup_vault_e:/backup/` (저장소 밖 · DB 볼륨과 다름) | `database_guardianx_20260907T191153.dump` | **40,242,094 B** | **2026-09-07T10:11:56Z** | `9e35e04b9c21a998…` | `postgres` 이미지의 **18.1** |
| 판정용 사본(저장소 밖 임시 자리) | `db_database_guardianx_20260907T101116Z.dump` | **40,242,096 B** | **2026-09-07T10:11:16Z** | `8b6391e80c3f134b…` | `docker exec postgres` 의 **18.1** |

대조표(행 수 포함)는 `backup_manifest_20260907_TK.json` 에 그대로 있다.
⚠ **덤프 파일 자체를 저장소에 넣지 않았다** — 40MB 이고, 「같은 디스크는 백업이 아니다」다.
정본은 볼륨의 것이고, 저장소에는 **대조표와 판정문만** 둔다.

### ② 복구 시험 — **행 수 대조** (`ops_restore.py` · 격리 DB)

```

    --manifest <저장소 밖>/manifest.json \
    --evidence docs/agent/evidence/OPS-12/restore_run_20260907_TK.md
→ exit 0
```

복구 대상: **`restore_check_test_gx_e_20260907101131`** — 차선 이름(`DB_TEST_NAME`)을 이름에
넣되 안전 앞머리 `restore_check_` 는 그대로 둔다(§5). 끝나고 지웠다.

| 증인 표 | 백업 | 복구 |
|---|---:|---:|
| `stream_monitors_streammonitor` | 40 | **40** |
| `stream_monitors_detectionevent` | 22 | **22** |
| `stream_monitors_eventclip` | 22 | **22** |
| `user_coreuser` | 113 | **113** |
| `auth_group` | 0 | **0** |

**전부 같다 → 복구 성공.** 원본 `database_guardianx` 에는 **읽기 질의만** 던졌다.

### ③ 복구 시험 — **볼륨에서 · 시계를 들고** (`ops_restore_drill.py`)

```
python scripts/ops_restore_drill.py \
    --evidence docs/agent/evidence/OPS-19/restore_drill_20260907_TK.md \
    --json     docs/agent/evidence/OPS-19/restore_drill_20260907_TK.json

```

| | |
|---|---|
| 살린 덤프 | 볼륨의 `database_guardianx_20260907T191153.dump` · 40,242,094 B |
| 표 수 | 원본 **223개** · 복구 **223개** — 같다 |
| **RTO 실측** | **0.14분(8.5초)** — 임시 DB 만들기부터 지우기까지 벽시계 (SLA 초안 목표 30분) |
| 임시 DB | 지웠다 |

★ ②와 ③은 **다른 것을 잰다**: ②는 **행 수**(자료가 그대로인가), ③은 **표 수 + 시간**
(볼륨의 그 파일에서 되살아나는가 · 몇 분인가). 둘 다 있어야 한 장이다.

## 2. 왜 이렇게 떴나 — **막는 것 ㉰(`pg_dump` 판)을 우회가 아니라 정공법으로 넘었다**

```
$ docker exec -e PGPASSWORD=**** gx-shell pg_dump -h postgres -p 5432 -U postgres \
      -d database_guardianx -Fc -f /tmp/probe.dump
pg_dump: error: aborting because of server version mismatch
pg_dump: detail: server version: 18.1 (Debian 18.1-1.pgdg13+2); pg_dump version: 17.7
exit=1
```

```
$ docker exec postgres pg_dump --version
pg_dump (PostgreSQL) 18.1 (Debian 18.1-1.pgdg13+2)      # 서버와 같다
```

그래서 **`--via docker:postgres`** 다 —
`ops_backup.py` 가 이미 가지고 있던 인자이고, **컨테이너 재생성이 아니다.**
이것이 「이미지 태그를 바꿔야 한다」와 다른 점이다: 재생성 없이 오늘 잴 수 있는 길이 있었고,
어제 문서는 그것을 ㉰(사람 승인)로만 적어 두었다. **㉰ 는 주기에 대해서만 남아 있는 벽이다.**

## 3. 주기가 회수증을 못 남기는 이유 — **넷이다** (어제는 셋)

| | 막는 것 | 실측 근거 | 이번 턴에 한 일 |
|---|---|---|---|
| ㉮ | `/backup` 볼륨이 안 붙어 있다 | `docker exec gx-celery-e ls -ld /backup` → `No such file or directory` (셋 다: `gx-shell`·`gx-celery-e`·`gx-beat-e`) | **선언만.** `docker-compose.yml` 의 세 서비스에 이미 `gx_backup_vault_e:/backup` 이 있다. 붙는 것은 **재생성 때** — 대표 승인 |
| ㉯ | `OPS_BACKUP_DIR` 이 선언되지 않았다 | `docker exec <c> printenv OPS_BACKUP_DIR` → **빈 값** (셋 다) | **고쳤다(선언).** `docker-compose.yml` 세 서비스 + `.env.example`. `docker compose --profile tools config` 가 `OPS_BACKUP_DIR: /backup` 을 **3개** 낸다 |
| ㉰ | 앱 이미지의 `pg_dump` 17.7 < 서버 18.1 | §2 | **주기에는 남아 있다.** 사람이 부르는 길은 `--via docker:postgres` 로 오늘 넘었다 |
| **㉱** | **`OPS_BACKUP_SCHEDULE_ENABLED` 가 꺼져 있다 — 주기가 아예 건너뛴다** | `gx-celery-e` 로그: `verdict='SKIPPED', reason='백업 주기가 꺼져 있다 (OPS_BACKUP_SCHEDULE_ENABLED)'` | **이번 턴에 새로 봤다.** `.env.example` 에 **이름만** 넣었다(값은 `false` 그대로) |

★ **㉱ 가 이 절의 새 사실이다.** 어제 문서는 워커의 판정문을
`SKIPPED_UNDECLARED`(=㉯)로 읽었는데, **오늘 로그가 낸 사유는 `SKIPPED`(=㉱)** 다.
`settings.py:916` 의 기본값이 `False` 이고 아무도 선언하지 않았다. 그런데
`config/retention_seed.py:60` 은 이 값을 **`True` 로 선언**한다 — **선언과 형상이 어긋나 있다.**
㉯ 하나만 고치고 재생성했다면 **여전히 아무 회수점도 안 생겼을 것이다.**

⚠ **여기서 켜지 않았다.** 켜기 전에 `/backup` 이 실제로 붙어 있어야 한다
(`ops_tasks.backup_dir_is_separate_volume()` 이 `st_dev` 로 잰다). 순서는
`.env.example` 이 스스로 적어 두는 그 순서다: ① 이름 → ② `.env` 값 → ③ 마운트가 붙는
재기동 창 → ④ 그때 `true`. 뒤집으면 **켜 놓고 아무 데도 안 뜨는 상태**가 된다.

### 갚힌 것 하나 — 선행 차단이 사라졌다

어제 §4 의 **`backend/common/ops_tasks.py:133` SyntaxError 는 고쳐져 있다**
(`py_compile` 조용 · `gx-shell` 에서 `import common.tasks` OK). 다른 차선이 갚았다.

## 4. RPO 상한 — **여전히 못 쟀다** (그리고 그것을 적는다)

| 물음 | 답 | 표본 |
|---|---|---|
| 주기가 **쏜** 간격 | 24시간 [실측 · `PeriodicTask.total_run_count=2` · `last_run_at 2026-09-06T20:00:00Z`] | 2 |
| **회수점이 뜬** 간격 | **못 쟀다** | **0** (오늘 것은 사람이 불렀다) |
| 가장 새 회수점의 나이 | 이 문서 시각 기준 **0분** (방금 떴다) — 이 수는 RPO 가 아니다 | |

**「쏜 것」과 「뜬 것」은 다른 사실이다.** 쏜 간격을 RPO 로 적는 것이 D-284 의 조용한 성공이고,
이번에도 적지 않는다. RPO 상한은 ㉮㉯㉰㉱ 가 모두 풀린 뒤 **03:00 이 두 번** 지나야 잰다.

## 5. 고친 코드 — `ops_restore.py` 의 격리 DB 이름에 차선 이름을 넣었다

```python
def scratch_name(now, lane=""):   # lane = os.environ["DB_TEST_NAME"]
    slug = re.sub(r"[^A-Za-z0-9_]", "_", lane or "").strip("_")
    return SCRATCH_PREFIX + (slug + "_" if slug else "") + now
```

- 까닭: `DB_TEST_NAME` 이 이 저장소에서 「차선마다 갈라 쓰는 격리 DB」의 정본 이름이다
  (P-18 · D-416). 차선 넷이 같은 초에 복구 시험을 돌리면 시각만으로는 부딪친다.
- ⚠ **`DB_TEST_NAME` 을 그대로 대상으로 삼지 않았다.** `test_gx_e` 는 다른 시험이 쓰는
  **실물**이고, 거기에 복구를 부으면 예행이 아니라 사고다. 앞머리 `restore_check_` 도
  그대로 뒀다 — `guard()` 가 원본 덮어쓰기를 막는 열 줄이다.
- 자기시험 **13건**(종전 8 + 새 5, 음성 포함) 전부 통과.
