## 1. 착수 전 실측 — **셋 다 0건이다** (조율자 실측 + 차선 E 재측)

```
docker inspect gx-celery-e --format '{{range .Mounts}}{{.Destination}} {{end}}'
  → /app /repo/scripts /repo/backend /docs/agent/evidence/D-373        ← /backup 없음
docker inspect gx-beat-e   → /app                                      ← /backup 없음
docker inspect gx-shell    → /docs /app /repo/scripts /repo/backend /repo/frontend  ← /backup 없음
```

판(version) [실측 2026-09-06]:

| 자리 | `pg_dump` | 비고 |
|---|---|---|
| `gx-celery-e` · `gx-beat-e` · `gx-shell` (`guardianx-backend:latest`) | **17.7** (`postgresql-client-17`, Debian 13 trixie) | `postgresql-client-common` 이 딸려 온 것 |
| `postgres` 컨테이너 (`postgres:latest`) | **18.1** | 서버도 18.1 |

**규칙은 하나다: `pg_dump` 의 major 가 서버보다 낮으면 못 뜬다.** 17.7 < 18.1 이라 워커가
뜨려 하면 `server version mismatch` 로 죽는다.

★ **compose 선언은 이미 서 있다** — `docker-compose.yml` 의 `celery`·`beat`·`shell`
세 서비스에 `- gx_backup_vault_e:/backup` 이 적혀 있고, 볼륨은 `external: true` 로
**이미 있는 `gx_backup_vault_e` 를 가리킨다.** 선언은 맞고, **적용이 안 된 것**이다
(이 기계의 셋은 compose 밖에서 손으로 만든 컨테이너라 그 줄이 닿지 않는다).

★★ **가장 중요한 정정 — 마운트가 필요한 것은 `beat` 가 아니라 `celery` 다.**
`beat` 는 **시각만 쏘고** 태스크를 실행하지 않는다. `ops_backup_beat` ·
`ops_restore_drill_beat` · `ops_audit_purge_beat` 을 **실제로 돌리는 것은 워커
(`gx-celery-e`)** 다. 그러므로 창에서 하나만 고른다면 그것은 **`gx-celery-e`** 다.
`gx-beat-e` 와 `gx-shell` 에도 붙이는 것은 ㉠ compose 선언과 실물을 일치시키려는 것
㉡ 사람이 `gx-shell` 에서 손으로 복구 훈련을 돌릴 수 있게 하려는 것이다.

## 2. 갈래를 골랐다 — **㉠ 워커 이미지에 `postgresql-client-18` 을 넣는다**

조율자가 준 세 갈래에 대한 판정이다. **개발에서 되는 법과 운영에서 될 법이
같은 갈래를 고른다** — 그것이 이 판정의 기준 전부다.

### 고른 것 — ㉠ 이미지에 클라이언트 18

| | |
|---|---|
| **무엇** | `backend/Dockerfile` 끝(ENTRYPOINT 앞)에 PGDG 저장소 + `postgresql-client-18` 한 층 |
| **개발에서 되는가** | 된다 |
| **운영에서 될 법인가** | **된다 — 이미지가 그대로 나간다.** 형상이 하나다 |
| **권한** | 아무 권한도 늘지 않는다 |
| **되돌리기** | Dockerfile 의 그 층을 지우고 다시 빌드 |

### ★★ **이 갈래는 추측이 아니다 — `--rm` 컨테이너에서 실제로 넣어 봤다** [실측 2026-09-06]

아래 §3 E-1 의 명령을 `guardianx-backend:latest` 에 그대로 태웠다(**이미지도 컨테이너도
남기지 않는다** — `--rm`). exit **0**:

```
RESULT which=/usr/bin/pg_dump
RESULT pg_dump (PostgreSQL) 18.6 (Debian 18.6-1.pgdg13+2)
RESULT pg_restore (PostgreSQL) 18.6 (Debian 18.6-1.pgdg13+2)
```

즉 **PGDG trixie 저장소가 이 기계에서 닿고, 18 클라이언트가 실제로 들어간다.**
17.7 → **18.6** 이고 서버 18.1 보다 높다. **창에서 처음 시도하는 일이 아니다.**

★ **판 규칙: 클라이언트 major ≥ 서버 major.** 18 클라이언트는 15·16·17 서버도 뜬다.
그러므로 이 한 줄은 고객의 DB 가 18보다 낮아도 맞고, **18보다 높아지는 날 다시 올려야
한다.** 그 날을 사람이 알아채도록 `ops_restore_drill_beat` 이 이미 판을 **먼저 재고**
안 맞으면 `UNKNOWN`(회색)을 낸다 — 「못 쟀다」를 「복구 성공」으로 적지 않는다.

⚠ **빌드 층을 왜 맨 끝에 두는가.** 위쪽(`apt` 큰 덩이 · `pip install --mount=type=ssh`)을
건드리면 사내 private 저장소를 SSH 로 다시 받아야 하고, 그 자리는 창 안에서 깨지면
되돌리기가 가장 비싸다. 끝에 얹으면 `requirements.txt` 가 그대로인 한 pip 층은
**캐시에서 온다.**

### 안 고른 것 — ㉡ 워커에 docker CLI + `/var/run/docker.sock`

**거부한다. 사유는 하나로 충분하다: 그것은 워커에게 호스트 도커 전권을 주는 것이다.**
도커 소켓을 쥔 프로세스는 어떤 컨테이너든 특권으로 띄울 수 있고, 그것은 호스트 루트와
같다. **백업 하나를 위해 그 권한을 주는 것은 값이 안 맞는다.** 그리고 이 갈래는
**개발에서만 되는 법**이다 — 고객 환경(관리형 쿠버네티스·매니지드 DB)에는 워커가
쓸 도커 소켓이 아예 없다. 개발에서만 되는 해법으로 OPS-19 를 닫으면
**RPO 약속이 다시 거짓이 된다.**

### 안 고른 것 — ㉢ 백업 전용 사이드카(`postgres` 이미지 + cron)

돌기는 돈다. 그러나 **주기가 두 벌**이 된다(celery beat + cron). 「백업이 안 돌았다」를
물었을 때 볼 자리가 둘이 되고, 그 둘이 어긋나는 날 아무도 못 찾는다. 그리고 OPS-19 의
닫는 조건 ③은 「**사람 손 0 으로** 만들어진 덤프」이지 「우리 주기 밖에서 만들어진
덤프」가 아니다. **보류한다 — 매니지드 DB 라 클라이언트를 못 넣는 고객이 나오면 그때
다시 꺼낸다.**

### 개발과 운영이 갈리는 자리 — **지우지 않고 적는다**

1. **볼륨 갈래이지 호스트 갈래가 아니다.** `gx_backup_vault_e` 는 **같은 기계** 안이다.
   기계가 타면 백업도 저널도 같이 탄다. 운영의 목적지는 **다른 호스트·다른 계정**이어야
   하고, 그것은 이 창에서 정해지지 않는다(OPS-12a 미완 · SLA v0.2 §4 RPO ㉢).
2. **개발은 `retention_seed.py` 가 선언한다. 운영은 고객이 U5 에서 선언한다.**
   `production` 은 그 표를 한 칸도 안 읽는다 — 이 창에서 켜지는 것은 **개발 형상**이다.
3. **저널은 평문 JSON 이고 감사 로그의 사용자명·IP 가 들어 있다.** 운영에서 그 볼륨은
   백업과 같은 취급(접근 통제·암호화)을 받아야 한다(D-204).

## 3. 창에서 붙여 넣을 것 — **차선 E 몫만** (SEC 선언은 차선 S 가 준다)

> ⓪ **먼저 `RUNBOOK_로컬기동.md` STEP 2D ⓪ 의 확인 셋을 그대로 돌린다.**
> 하나라도 아니면 여기서 멈춘다. (조율자 실측 2026-09-06: 셋 다 만족)
> 그리고 STEP 2D ① 대로 **지금 형상을 저장소 밖에 파일로 뜬다** — 손으로 다시 치지 않는다.

### E-1. 이미지에 `pg_dump` 18 을 넣는다 (한 층)

`backend/Dockerfile` 의 `ENTRYPOINT ["/entrypoint.sh"]` **바로 앞**에 아래를 넣는다.

```dockerfile
# ── OPS-19 · pg_dump 판 맞추기 (2026-09-06 · 턴 H · 차선 E) ──────────────────
#  [실측] 이 이미지의 pg_dump 는 17.7(Debian trixie 기본), DB 서버는 18.1 이다.
#  클라이언트 major 가 서버보다 낮으면 뜨지 못한다 — 주기로 도는 백업이 바로
#  그 자리에서 죽었다. 규칙은 **클라이언트 major >= 서버 major** 하나다.
#  ⚠ 이 층은 **맨 끝**에 둔다. 위쪽 pip 층(사내 private · --mount=type=ssh)을
#    건드리면 창 안에서 가장 비싼 되돌리기가 된다.
RUN set -eux; \
    apt-get update; \
    apt-get install -y --no-install-recommends curl ca-certificates gnupg; \
    install -d /usr/share/postgresql-common/pgdg; \
    curl -fsSL -o /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc \
        https://www.postgresql.org/media/keys/ACCC4CF8.asc; \
    . /etc/os-release; \
    echo "deb [signed-by=/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc] \
https://apt.postgresql.org/pub/repos/apt ${VERSION_CODENAME}-pgdg main" \
        > /etc/apt/sources.list.d/pgdg.list; \
    apt-get update; \
    apt-get install -y --no-install-recommends postgresql-client-18; \
    rm -rf /var/lib/apt/lists/*; \
    pg_dump --version
```

빌드 (창 안):

```bash
cd /c/GuardianX/guardianx-source
DOCKER_BUILDKIT=1 docker build --ssh default -t guardianx-backend:latest ./backend
# 판이 올라갔는지 **이미지에게 직접 묻는다** (Dockerfile 을 믿지 않는다)
docker run --rm --entrypoint pg_dump guardianx-backend:latest --version
#   → pg_dump (PostgreSQL) 18.x   ← 18 이 아니면 여기서 멈춘다
```

### E-2. `/backup` 을 붙여 세 컨테이너를 다시 만든다

⚠ 이 셋은 **compose 밖에서 손으로 만든 것**이다. `docker compose up` 으로 다시 만들면
이름(`gx-celery-e`…)과 망(`gx-main-network`)이 달라진다. **지금 형상 + 마운트 한 줄**로
다시 만든다. 환경변수는 STEP 2D ① 이 뜬 `*.env` 를 쓴다(저장소 밖 · D-204).

```bash
VAULT=/c/GuardianX-vault/recreate         # STEP 2D ① 이 뜬 자리
SRC=C:/GuardianX/guardianx-source

# ── 워커 (이 창의 핵심. 태스크를 **실제로 돌리는 것은 이것**이다) ────────────
docker rm -f gx-celery-e
MSYS_NO_PATHCONV=1 docker run -d --name gx-celery-e \
  --network gx-main-network --restart unless-stopped \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=5 \
  --env-file $VAULT/gx-celery-e.env -w /app --entrypoint python \
  -v gx_backup_vault_e:/backup \
  -v $SRC/backend:/app \
  -v $SRC/scripts:/repo/scripts:ro \
  -v $SRC/backend:/repo/backend:ro \
  -v $SRC/docs/agent/evidence/D-373:/docs/agent/evidence/D-373 \
  guardianx-backend:latest \
  -m celery -A config worker -l INFO --concurrency=2 \
  --time-limit=600 --soft-time-limit=300 -n gx-worker-e@%h

# ── beat (시각만 쏜다. 마운트는 compose 선언과 실물을 맞추려는 것) ───────────
docker rm -f gx-beat-e
MSYS_NO_PATHCONV=1 docker run -d --name gx-beat-e \
  --network gx-main-network --restart unless-stopped \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=5 \
  --env-file $VAULT/gx-beat-e.env -w /app --entrypoint python \
  -v gx_backup_vault_e:/backup \
  -v $SRC/backend:/app \
  guardianx-backend:latest \
  -m celery -A config beat -l INFO

# ── gx-shell (사람이 손으로 복구 훈련을 돌리는 자리) ─────────────────────────
#    ⚠ `--entrypoint sleep` 이 이 컨테이너의 존재 이유다 (STEP 2D ② 참조).
docker rm -f gx-shell
MSYS_NO_PATHCONV=1 docker run -d --name gx-shell \
  --network gx-main-network --restart unless-stopped \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=5 \
  --env-file $VAULT/gx-shell.env -w /app --entrypoint sleep \
  -v gx_backup_vault_e:/backup \
  -v $SRC/docs:/docs \
  -v $SRC/backend:/app \
  -v $SRC/scripts:/repo/scripts:ro \
  -v $SRC/backend:/repo/backend:ro \
  -v $SRC/frontend:/repo/frontend:ro \
  guardianx-backend:latest infinity
```

## 4. 창이 닫힌 뒤 — **무엇을 재면 OPS-19 가 닫히는가**

닫는 조건은 셋이고, ①②는 이미 갚았다(백업 파일 실재 · RTO 0.14분 실측).
**남은 것은 ③ 「사람 손 0 으로 만들어진 덤프」다.**

```bash
# ── ㉠ 마운트가 붙었는가 (위 E-3) — 아니면 아래가 전부 무의미하다
# ── ㉡ 주기가 **스스로** 한 번 돌았는가 · 손으로 부르지 않는다
#     beat 표: ops-backup-daily(매일 03:00) · ops-restore-drill-weekly(일 06:00)
MSYS_NO_PATHCONV=1 docker exec -e DJANGO_SETTINGS_MODULE=config.settings gx-shell \
  python -c "
import django; django.setup()
from django_celery_beat.models import PeriodicTask
for n in ('ops-backup-daily','ops-restore-drill-weekly','ops-audit-purge-daily'):
    t = PeriodicTask.objects.filter(name=n).first()
    print(n, '| enabled=', getattr(t,'enabled',None), '| last_run=', getattr(t,'last_run_at',None))"

# ── ㉢ **사람 손 없이 생긴 파일이 있는가.** 볼륨을 다른 컨테이너에서 읽는다
#     (뜬 컨테이너에서 보면 「방금 쓴 파일이 아직 열려 있다」를 보는 것이다)
MSYS_NO_PATHCONV=1 docker run --rm -v gx_backup_vault_e:/backup alpine:latest \
  sh -c 'ls -l --time-style=full-iso /backup /backup/2*/ 2>/dev/null'
#   판정: `ops_backup_beat` 이 만드는 자리는 **날짜 칸**(`/backup/YYYYMMDD/`)이다.
#         스크립트가 손으로 뜬 파일은 `/backup/database_guardianx_*.dump` 로
#         **뿌리에** 있다. **자리가 다르므로 손과 주기를 눈으로 가를 수 있다.**

# ── ㉣ 태스크가 스스로 남긴 판정문
MSYS_NO_PATHCONV=1 docker exec gx-shell sh -c \
  'cat /docs/agent/evidence/D-373/backup_last.json; echo; cat /docs/agent/evidence/D-373/restore_drill_last.json'
#   판정: backup_last.json 의 verdict 가 **OK** 이고 out_dir 이 /backup/<날짜> 여야 한다.
#         UNKNOWN 이면 separate_volume 을 보라 — 마운트가 안 붙은 것이다.
```

### OPS-19 를 닫으려면 위에서 **무엇이 나와야 하는가**

| 조건 | 판정 |
|---|---|
| ① 백업 파일이 실재한다 | **갚음** [실측 2026-09-06 · 9,209,410바이트 · 목차 3,351줄] |
| ② 복구를 해 보고 RTO 를 쟀다 | **갚음** [실측 · 표 223/223 · RTO 0.14분] |
| ③ **사람 손 0 으로 만들어진 덤프 1개** | 위 ㉢ 이 `/backup/<날짜>/` 에 파일을 내고 ㉣ 의 `verdict=="OK"` 일 때 |

### ⚠ **OPS-19 가 닫혀도 RPO 24h 는 아직 약속하지 못한다**

SLA v0.2 §4 가 RPO 재약속 조건을 셋으로 적어 두었다. ③을 갚아도 남는 것:

- ㉠ **2일 연속** — 하루치 하나로는 24시간을 약속할 수 없다
- ㉡ 그 파일로 **빈 DB 를 세워 본다** → 이미 갚았다(`ops_restore_drill.py` · 223표)
- ㉢ **호스트 갈래** — 지금은 같은 기계의 볼륨이다. 기계가 타면 함께 탄다

**「하나 있다」와 「약속한다」 사이에 이 셋이 있고, 그것을 건너뛰는 것이 상용 사고의 모양이다.**
