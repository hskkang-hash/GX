# OPS-19 · **주기가 뜬 덤프가 실제로 생기고, 그 덤프로 복구된다** — 우리 손 안에서 실증

- 날짜: **2026-09-06** (턴 **TI** · 차선 E) · 기계 시각 UTC
- 판정 근거: 세종 P-67 · P-86 · 지시서 §3 E행
- ⚠ **이 실증은 살아 있는 컨테이너를 하나도 건드리지 않았다.** 쓴 것은 `docker run --rm`
  일회용 컨테이너와 **새 태그** 이미지 하나뿐이다. `guardianx-backend:latest` 는
  덮어쓰지 않았고, `gx-celery-e`·`gx-beat-e`·`gx-shell` 은 그대로 떠 있다.

---

## 0. 무엇을 증명했고, 무엇은 증명하지 못했나 — 먼저 가른다

**증명한 것**

> 이 코드로 주기를 한 바퀴 돌리면, **사람 손 0** 으로 `/backup/<날짜>/` 에 덤프가
> 실제로 생기고, **그 덤프로 빈 DB 가 세워진다**(표 223/223).

**증명하지 못한 것 — 그리고 이것이 RPO 24시간과 이 실증 사이의 거리다**

1. **주기가 스스로 돈 것이 아니다.** 태운 것은 beat 표가 가리키는 **바로 그 태스크**
   (`common.ops_backup_beat`)이고 이름은 이 문서가 짓지 않고 **선언에서 읽었다**.
   그러나 시각을 쏜 것은 크론이 아니라 사람이다. **RPO 는 「자동으로 얼마나 자주」이지
   「한 번 떴다」가 아니다.**
2. **연속 2일이 없다.** 이번 표본 둘은 67초 간격이고, 그것은 주기의 간격이 아니다.
3. **같은 기계의 볼륨이다.** 기계가 타면 백업도 같이 탄다.
4. **살아 있는 `gx-celery-e` 에는 여전히 `/backup` 이 안 붙어 있다** — 그것은
   컨테이너 재생성이라 **사람의 승인 대상**이고, 이 턴에 하지 않았다(§5).

→ 그러므로 **OPS-19 는 「주기 배선 실증 O · 자율 1바퀴 대기」**로 갈라 적는다.
   이 초록을 「RPO 24시간을 지킨다」로 옮겨 적는 것이 D-284 의 「조용한 성공」이다.

## 1. 어느 태스크인가 — **이름을 짓지 않고 선언에서 읽었다**

```python
from config.celery import app
entry = app.conf.beat_schedule["ops-backup-daily"]
entry["task"]            # -> 'common.ops_backup_beat'
entry["schedule"]        # -> <crontab: 0 3 * * * (m/h/dM/MY/d)>
app.conf.beat_scheduler  # -> django_celery_beat.schedulers:DatabaseScheduler
```

| | 값 [실측 2026-09-06 · TI] |
|---|---|
| beat 표의 열쇠 | `ops-backup-daily` |
| **태스크 이름** | **`common.ops_backup_beat`** |
| 주기 | `crontab(hour=3, minute=0)` — 매일 03:00 |
| 태스크를 **실제로 돌리는 자리** | 워커(`gx-celery-e`) — beat 는 시각만 쏜다 |

★ 판정기가 이름을 **하드코딩하지 않는다.** 선언이 바뀌면 이 실증도 따라 바뀐다 —
  베껴 적으면 두 벌이 되고, 두 벌은 반드시 어긋난다(D-369).

## 2. 판(version) 문제를 **새 태그로** 풀었다 — 기존 태그를 덮지 않았다

`guardianx-backend:latest` 의 `pg_dump` 는 **17.7**, DB 서버는 **18.1** 이다.
클라이언트 major 가 서버보다 낮으면 뜨지 못한다.

새 이미지는 `FROM guardianx-backend:latest` 로 **이미 빌드된 이미지 위에** PGDG 저장소와
`postgresql-client-18` 한 층만 얹었다. 그래서 위층(`pip install --mount=type=ssh` ·
사내 private 저장소)은 **한 번도 다시 타지 않는다** — 준비물 §2 가 「창 안에서 가장 비싼
되돌리기」라고 적은 그 자리를 아예 지나가지 않는다.

```
FROM guardianx-backend:latest
RUN set -eux; apt-get update; \
    apt-get install -y --no-install-recommends curl ca-certificates gnupg; \
    install -d /usr/share/postgresql-common/pgdg; \
    curl -fsSL -o /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc \
        https://www.postgresql.org/media/keys/ACCC4CF8.asc; \
    . /etc/os-release; \
    echo "deb [signed-by=/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc] \
https://apt.postgresql.org/pub/repos/apt ${VERSION_CODENAME}-pgdg main" \
        > /etc/apt/sources.list.d/pgdg.list; \
    apt-get update; apt-get install -y --no-install-recommends postgresql-client-18; \
    rm -rf /var/lib/apt/lists/*; pg_dump --version
```

```
DOCKER_BUILDKIT=1 docker build -t guardianx-backend:ops19-pg18-ti .     # exit 0 · 약 25초
```

| | 값 |
|---|---|
| 새 태그 | `guardianx-backend:ops19-pg18-ti` |
| 넣은 것 | `postgresql-client-18` → **`pg_dump (PostgreSQL) 18.6 (Debian 18.6-1.pgdg13+2)`** |
| 기존 태그 | `guardianx-backend:latest` — **손대지 않았다** |

⚠ 준비물 문서(§3 E-1)는 이 층을 `backend/Dockerfile` **끝에** 넣으라고 적었다. 이번 턴에
  그 파일은 고치지 않았다 — 차선 E 의 소유 밖이고, 이미지에 넣는 것과 **같은 결과**를
  일회용으로 얻을 수 있었기 때문이다. `backend/Dockerfile` 반영은 §5 와 함께 사람 승인 대상.

## 3. 태운 것 — 일회용 컨테이너, `/backup` 볼륨을 붙여서

```
SP=<저장소 밖 임시 자리>;  SRC=C:/GuardianX/guardianx-source

# 살아 있는 워커의 환경을 그대로 떠서 쓴다 (저장소 밖 파일 · D-204)
docker inspect gx-celery-e --format "{{range .Config.Env}}{{println .}}{{end}}" > $SP/celery-e.env

MSYS_NO_PATHCONV=1 docker run --rm --network gx-main-network \
  --env-file $SP/celery-e.env -e PYTHONPATH=/app \
  -v gx_backup_vault_e:/backup \
  -v $SRC/backend:/app:ro -v $SRC/scripts:/repo/scripts:ro \
  -v $SP/run_beat_task.py:/tmp/run_beat_task.py:ro \
  -w /app --entrypoint python \
  guardianx-backend:ops19-pg18-ti /tmp/run_beat_task.py
```

`run_beat_task.py` 가 하는 일은 셋뿐이다: ㉠ 선언에서 태스크 이름을 읽고
㉡ `app.tasks[<그 이름>].apply()` 로 **프로세스 안에서** 돌리고 ㉢ 전후의 `/backup` 을 찍는다.

★ `.apply()` 를 쓴 이유: `.delay()` 로 넣으면 **공용 redis 큐**에 들어가고 살아 있는
  `gx-celery-e` 가 집어간다. 그 워커에는 `/backup` 이 없으므로 결과는 `UNKNOWN` 이 되고,
  그 `UNKNOWN` 이 **운영 증거 파일 `D-373/backup_last.json` 을 덮는다.** 남의 증거를
  내 실험으로 덮지 않는다.
★ 같은 이유로 `/docs` 를 **안 붙였다** — 태스크가 남기는 증거 파일은 일회용 컨테이너의
  쓰기층에만 생기고 `--rm` 과 함께 사라진다. 살아 있는 `D-373` 은 그대로다.

### 컨테이너가 본 형상

```
백업_주기        = 켬                  (retention_seed 선언 · GUARDIANX_ENVIRONMENT=development)
백업_보관처       = /backup
separate_volume  = True               <- st_dev 가 루트와 다르다. 진짜로 붙었다
pg_dump          = 18.6               <- 서버 18.1 보다 높다
```

자리가 다르므로 「이 파일을 누가 만들었나」를 **묻지 않고 볼 수 있다.**

### ㉢ 볼륨에 정말 남는가 — **또 다른 `--rm` 컨테이너에서 읽었다**

```
docker run --rm -v gx_backup_vault_e:/backup alpine:latest \
  sh -c "ls -l --full-time /backup/20260906/; sha256sum /backup/20260906/*.dump"
```

| | 값 |
|---|---|
| 읽은 자리 | `alpine:latest` — django 도 저장소도 없는 **완전히 다른 컨테이너** |
| 파일 | `db_database_guardianx_20260906T132227Z.dump` · 22,166,024바이트 · `2026-09-06 13:22:29 +0000` |
| 지문 | 태스크가 대조표에 적은 값과 alpine 이 계산한 값이 **한 글자도 다르지 않다** (sha256 앞 12자 `1bcb2e4e7bd4…`) |
| 재확인 시각 | `2026-09-06T13:22:52Z` |

→ **뜬 컨테이너가 「방금 쓴 파일이 아직 열려 있는 것」을 본 것이 아니다.** 볼륨에 남았다.

### ㉣ **그 회수점으로 빈 DB 를 세웠다** — 이번 턴에 새로 갚은 칸

```
python scripts/ops_restore_drill.py --evidence docs/agent/evidence/OPS-19/restore_drill_20260906_TI.md
```

| | 값 |
|---|---|
| 되살린 덤프 | **`/backup/20260906/db_database_guardianx_20260906T132334Z.dump`** — 주기가 뜬 그 파일 |
| 크기 · 지문 | 22,166,024바이트 · sha256 앞 12자 `ca7b143725d5…` (2회차 대조표와 같다) |
| 표 대조 | 원본 **223** 개 = 복구 **223** 개 |
| **RTO** | **0.13분** (8.0초) |
| 임시 DB | `restore_check_<시각>` — 만들고 지웠다(rc=0) |

⚠ **이 칸은 어제까지 거짓으로 초록이었다.** `scripts/ops_restore_drill.py` 는
`ls -1t /backup/*.dump` 로 **뿌리만** 보고 있었다 — 즉 **주기가 뜬 덤프는 복구 시험을
한 번도 받은 적이 없었고**, 초록이던 것은 늘 사람이 손으로 뜬 파일이었다.
짝인 `common/ops_tasks.py::_newest_dump` 는 이미 `rglob` 로 재귀였으니 **두 벌이
어긋나 있었다**(D-369). 이번 턴에 `find … -printf` 로 맞췄다.

| 수 | 값 | 뜻 |
|---|---|---|
| 회수점 나이(측정 순간) | **0.4분** (13:22:29Z 생성 → 13:22:52Z 재확인) | 지금 사고가 나면 잃는 시간 |

## 5. ⛔ **살아 있는 `gx-celery-e` 에 이 볼륨을 붙이려면** — 실행하지 않았다 · 사람 승인 대상

> 도커 마운트는 컨테이너를 **만들 때** 굳는다. 그러므로 이것은 재생성이고,
> **되돌릴 수 없는 조치**다. 차선 E 는 이 턴에 치지 않았다.

**무엇을**: `gx-celery-e`(주기 태스크를 실제로 돌리는 워커)를 **지우고 다시 만든다.**
`-v gx_backup_vault_e:/backup` 한 줄과 `pg_dump 18` 이미지를 얹기 위해서다.

**왜**: 이 둘이 없으면 03:00 주기는 매일 돌면서 매일 `UNKNOWN`(마운트 없음) 또는
`server version mismatch` 로 끝난다 — **등록돼 있는데 한 번도 안 뜨는** 착시 ⑨ 그대로다.

**어떤 명령으로** (준비물 §3 E-2 와 같다. 환경은 지금 것을 그대로 떠서 쓴다):

```
SRC=C:/GuardianX/guardianx-source
VAULT=/c/GuardianX-vault/recreate        # 저장소 밖. 없으면 먼저 지금 형상을 뜬다:
# docker inspect gx-celery-e --format "{{range .Config.Env}}{{println .}}{{end}}" > $VAULT/gx-celery-e.env

# (0) 이미지 — 준비물 §3 E-1 대로 backend/Dockerfile 끝에 층을 얹고 다시 빌드하거나,
#     이번 턴에 이미 검증된 새 태그를 그대로 쓴다: guardianx-backend:ops19-pg18-ti

docker rm -f gx-celery-e                 # <- 되돌릴 수 없다
MSYS_NO_PATHCONV=1 docker run -d --name gx-celery-e \
  --network gx-main-network --restart unless-stopped \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=5 \
  --env-file $VAULT/gx-celery-e.env -w /app --entrypoint python \
  -v gx_backup_vault_e:/backup \
  -v $SRC/backend:/app \
  -v $SRC/scripts:/repo/scripts:ro \
  -v $SRC/backend:/repo/backend:ro \
  -v $SRC/docs/agent/evidence/D-373:/docs/agent/evidence/D-373 \
  guardianx-backend:ops19-pg18-ti \
  -m celery -A config worker -l INFO --concurrency=2 \
  --time-limit=600 --soft-time-limit=300 -n gx-worker-e@%h

# 붙었는지 도커에게 묻는다 (compose 파일을 믿지 않는다)
docker inspect gx-celery-e --format "{{range .Mounts}}{{.Destination}} {{end}}"   # -> /backup 이 있어야 한다
MSYS_NO_PATHCONV=1 docker exec gx-celery-e pg_dump --version                      # -> 18.x
```

**그 뒤에 무엇을 재면 OPS-19 가 닫히는가** — 준비물 §4 그대로. 요약하면 **다음 03:00 두 번**:

```
# 주기가 스스로 돌았는가 (사람이 부르지 않는다)
MSYS_NO_PATHCONV=1 docker exec -e DJANGO_SETTINGS_MODULE=config.settings gx-shell python -c "
import django; django.setup()
from django_celery_beat.models import PeriodicTask
t = PeriodicTask.objects.filter(name='ops-backup-daily').first()
print('enabled=', t.enabled, 'last_run=', t.last_run_at)"

# 이틀치 날짜 칸이 생겼는가
docker run --rm -v gx_backup_vault_e:/backup alpine:latest ls -l --full-time /backup/2*/
```

⚠ **`gx-beat-e` 와 `gx-shell` 에도 붙이는 것은 급하지 않다.** beat 는 시각만 쏘므로
  `/backup` 이 필요 없고, `gx-shell` 은 사람이 손으로 복구 훈련을 돌릴 때만 쓴다.
  **창에서 하나만 고른다면 그것은 `gx-celery-e` 다.**

### 그리고 `docker-compose.yml` 쪽 — 고칠 것이 **없다**

`docker-compose.yml` 의 `celery`·`beat`·`shell` 세 서비스에는 `- gx_backup_vault_e:/backup`
이 **이미 적혀 있고** 볼륨은 `external: true` 다. 선언은 맞다. 이 기계의 셋이 compose
밖에서 손으로 만들어진 컨테이너라 **그 줄이 닿지 않았을 뿐**이다.
→ 차선 E 는 이번 턴에 `docker-compose*.yml` 을 한 줄도 고치지 않았고, **고칠 것도 없다.**
