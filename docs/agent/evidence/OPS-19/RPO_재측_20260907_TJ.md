## 3. **beat 는 일했다 — 그런데 회수점이 안 생겼다** [이번 턴 새로 잼]

`RPO_실증_20260906_TI.md` §5 가 「그 뒤에 무엇을 재면 OPS-19 가 닫히는가」로 적어 둔
바로 그 명령을 쳤다(읽기만 한다):

```
docker exec -e DJANGO_SETTINGS_MODULE=config.settings gx-shell python -c "
import django; django.setup()
from django_celery_beat.models import PeriodicTask
t = PeriodicTask.objects.filter(name='ops-backup-daily').first()
print('enabled=', t.enabled, 'last_run=', t.last_run_at, 'runs=', t.total_run_count)"
```

| | 값 [실측 2026-09-07T07:02Z] |
|---|---|
| `enabled` | **True** |
| `last_run_at` | **2026-09-06 20:00:00.002785+00:00** |
| `total_run_count` | **2** |
| 주기 | `crontab(hour=3, minute=0)` · `TIME_ZONE=Asia/Ho_Chi_Minh` → **03:00 +07 = 20:00Z** |
| 그러므로 쏜 시각 둘 | **2026-09-05T20:00Z · 2026-09-06T20:00Z — 간격 정확히 24시간** |

→ **㉠「beat 가 스스로 돌았는가」는 이제 예다.** 이틀 연속 · 사람이 부르지 않았다.
   이것은 어제 문서가 「못 했다」로 남겨 둔 칸이고, 오늘 갚혔다.

**그런데 그 두 번은 회수점을 남기지 않았다.** 워커가 남긴 판정문:

```
docs/agent/evidence/D-373/backup_last.json
{ "verdict": "SKIPPED_UNDECLARED",
  "reason": "백업 목적지가 **선언되지 않았다**(OPS_BACKUP_DIR) — 어디에 뜰지 모르는 백업은 백업이 아니다" }
```

```
docker inspect gx-celery-e --format "{{range .Mounts}}{{.Destination}} {{end}}"
→ /app /repo/scripts /repo/backend /docs/agent/evidence/D-373      # /backup 이 없다
docker inspect gx-celery-e ... | grep OPS_BACKUP_DIR
→ (없음)                                                            # 선언도 없다
```

즉 **막는 것이 하나가 아니라 둘이다** (어제는 하나로 적었다):

| | 막는 것 | 고치는 자리 | 되돌릴 수 있나 |
|---|---|---|---|
| ㉮ | `/backup` 마운트 없음 | 컨테이너 **재생성** | **아니오 — 사람 승인** |
| ㉯ | `OPS_BACKUP_DIR` 선언 없음 | 같은 재생성의 `--env-file`. `config/retention_seed.py` 는 `"OPS_BACKUP_DIR": "/backup"` 을 이미 적어 두었다 — 이 워커의 **떠 있는 환경**에 그 값이 안 들어 있을 뿐이다 | **아니오 — 같은 재생성** |
| ㉰ | 앱 이미지 `pg_dump` 17.7 < 서버 18.1 | 같은 재생성의 이미지 태그 | **아니오 — 같은 재생성** |

★ **어제 문서는 ㉮·㉰ 둘만 적었다. ㉯ 를 이번 턴에 새로 봤다.** 재생성 명령의 `--env-file` 을
  살아 있는 워커에서 **그대로 떠서** 쓰면 **㉯ 는 고쳐지지 않는다** — 지금 그 환경에 값이 없기
  때문이다. 아래 §6 의 명령에 그 한 줄을 **더했다.** 이것을 못 보고 재생성했다면 되돌릴 수
  없는 조치를 치고도 회수점은 여전히 안 생겼을 것이다.

### 그래서 RPO 상한은 — **여전히 못 쟀다**

| 물음 | 답 | 표본 |
|---|---|---|
| 주기가 **쏜** 간격 | **24시간** [실측] | 2 (09-05T20:00Z · 09-06T20:00Z) |
| **회수점이 뜬** 간격 | **못 쟀다** | **0** |

**RPO 24시간은 이번 턴에도 약속하지 못한다.** 「쏘는 것」과 「뜨는 것」은 다른 사실이고,
쏜 간격을 RPO 로 적는 것이 D-284 의 조용한 성공이다.

## 4. ⛔ **새 표본을 태우지 못했다 — HEAD 의 코드가 임포트되지 않는다**

지시서는 `--rm` 컨테이너에서 주기 태스크를 한 번 더 태우라 했다. 쳤고, **죽었다**:

```
docker run --rm --network gx-main-network --env-file <저장소 밖>/celery-e.env \
  -v gx_backup_vault_e:/backup -v .../backend:/app:ro -w /app \
  --entrypoint python guardianx-backend:ops19-pg18-ti /tmp/run_beat_task.py

celery.exceptions.NotRegistered: "common.ops_backup_beat"
  ↳ File "/app/common/tasks.py", line 32, in <module>
    File "/app/common/ops_tasks.py", line 133
    SyntaxError: unterminated string literal (detected at line 133)
```

**이것은 내 일회용 컨테이너의 문제가 아니다. 저장소의 문제다** — HEAD `778dad3` 에 그대로
들어 있다(작업본과 HEAD 가 같다 · 이 파일에 대해 `git status` 깨끗):

```
python -c "import py_compile; py_compile.compile('backend/common/ops_tasks.py', doraise=True)"
→ SyntaxError: unterminated string literal (detected at line 133)
```

```python
# backend/common/ops_tasks.py 133~135행 — 줄바꿈을 `\n` 이 아니라 **진짜 줄바꿈**으로 썼다
out.write_text(json.dumps(stamped, ensure_ascii=False, indent=2, default=str) + "
",
               encoding="utf-8")
```

살아 있는 `gx-shell` 에서도 같다:

```
common.tasks     임포트 실패: SyntaxError (ops_tasks.py, line 133)
common.ops_tasks 임포트 실패: SyntaxError (ops_tasks.py, line 133)
```

### 무엇이 걸리는가

- `common.ops_backup_beat` · `ops_monitor_beat` · `ops_audit_purge_beat` — **주기 태스크가
  하나도 등록되지 않는다.**
- `gx-celery-e` 는 **2026-09-05T11:07Z 에 뜬 옛 코드**를 메모리에 들고 돌고 있어서 아직 산다.
  **다음 재기동에서 죽는다** — 그리고 OPS-19 를 닫는 유일한 길이 바로 그 재기동이다.
- 즉 **이 한 자리가 §6 의 사람 승인 작업을 지금 막고 있다.** 재생성 전에 먼저 고쳐야 한다.
- ★ 이것이 「고친 것과 도는 것은 다른 사실이다」(D-301)의 **거울상**이다: 여기서는
  **도는 것이 멀쩡해서 고친 것이 깨진 줄 몰랐다.** 살아 있는 워커가 초록으로 보이는 것은
  코드가 옳아서가 아니라 **그 코드를 아직 안 읽었기 때문**이다.

⚠ **차선 E 는 고치지 않았다.** `backend/` 는 다른 차선의 소유다(지시서 규칙 6).
  고칠 곳은 한 곳이고 고침은 `"` + 줄바꿈 → `"\n"` **한 군데**다.

## 6. ⛔ 사람 승인 대상 — **명령 재확인** (어제 §5 에서 **한 줄이 늘었다**)

> 도커 마운트와 환경은 컨테이너를 **만들 때** 굳는다. 그러므로 이것은 재생성이고
> **되돌릴 수 없는 조치**다. 차선 E 는 이 턴에도 치지 않았다.

**선행 조건 (이것이 없으면 재생성해도 워커가 안 뜬다)**:
`backend/common/ops_tasks.py:133` 의 SyntaxError 를 먼저 고친다. 고친 뒤
`python -c "import py_compile; py_compile.compile('backend/common/ops_tasks.py', doraise=True)"`
가 조용해야 한다.

```
SRC=C:/GuardianX/guardianx-source
VAULT=/c/GuardianX-vault/recreate        # 저장소 밖
# (0) 지금 형상을 먼저 뜬다 — 되돌릴 수는 없어도 **무엇이었는지**는 남긴다
docker inspect gx-celery-e --format "{{range .Config.Env}}{{println .}}{{end}}" > $VAULT/gx-celery-e.env
# ★ 새로 더한 줄 — 지금 환경에 이 값이 **없다**(§3 ㉯). 그대로 떠서 쓰기만 하면 안 고쳐진다.
echo "OPS_BACKUP_DIR=/backup" >> $VAULT/gx-celery-e.env

docker rm -f gx-celery-e                 # <- 되돌릴 수 없다
MSYS_NO_PATHCONV=1 docker run -d --name gx-celery-e \
  --network gx-main-network --restart unless-stopped \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=5 \
  --env-file $VAULT/gx-celery-e.env -w /app --entrypoint python \
  -v gx_backup_vault_e:/backup \
  -v $SRC/backend:/app \
  -v $SRC/scripts:/repo/scripts:ro \
  -v $SRC/backend:/repo/backend:ro \
  -v $SRC/docs/agent/evidence/D-373:/docs/agent/evidence/D-373 \
  guardianx-backend:ops19-pg18-ti \
  -m celery -A config worker -l INFO --concurrency=2 \
  --time-limit=600 --soft-time-limit=300 -n gx-worker-e@%h

# 도커에게 묻는다 (compose 파일을 믿지 않는다)
docker inspect gx-celery-e --format "{{range .Mounts}}{{.Destination}} {{end}}"        # -> /backup
```
