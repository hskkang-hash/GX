# OPS-19 — **백업이 처음으로 저장됐다. 그리고 살려 봤고 몇 분인지 쟀다** (P-67 · 2026-09-06 · 차선 E)

> 세종 판정 P-67: 「백업 **매일 03:00** · 목적지 **별도 볼륨 `/backup`** ·
> 백업 보존 **14일** · 복구 시험 **주 1회 자동**(`ops_restore` dry-run → RTO 실측 기록).」
>
> OPS-19 가 태어난 자리(ga_readiness): 「beat 표에는 `ops-backup-daily` 가 켜져 있는데
> `OPS_BACKUP_SCHEDULE_ENABLED=False` · `OPS_BACKUP_DIR=''` 라 **아무 일도 안 일어난다.**
> 그러므로 **RPO 24h 를 지금 약속할 수 없다.**」

## 0. 착수 전 실측 — 「등록돼 있는데 한 번도 저장된 적 없다」

[실측 2026-09-06 · 개발 환경 · `django.conf.settings`]

    OPS_BACKUP_SCHEDULE_ENABLED = False
    OPS_BACKUP_DIR              = ''      ← 목적지가 **빈 문자열**

즉 beat 항목은 있고, 태스크는 있고, 스크립트도 있는데 **아무 일도 안 일어났다.**
이것이 착시 ⑨(등록만 하고 안 도는 것)의 운영판이다.

## 1. 선언 — 코드 기본값이 아니라 **개발·스테이징이 선언한다**

`backend/config/retention_seed.py` (신규). 운영(`production`)은 이 표를
**한 칸도 읽지 않는다** — `DECLARED_ENVIRONMENTS = ("development", "staging")`.

| 선언 | 값 | 자리 |
|---|---|---|
| 감사 로그 보존 | 365일 | AdminConfig `System > security.audit_log_retention_days` (심었다 · OPS-07b) |
| 스냅샷·구간 참조 | 30일 | `VIDEO_RETENTION_DAYS` |
| 백업 일정 | 매일 03:00 | beat `ops-backup-daily` |
| 백업 목적지 | 별도 볼륨 `/backup` | `OPS_BACKUP_DIR` + 볼륨 `gx_backup_vault_e` |
| 백업 보존 | 14일 | `OPS_BACKUP_RETENTION_DAYS` |
| 복구 시험 | 주 1회 자동 | beat `ops-restore-drill-weekly` (일 06:00) |

[실측] 선언 뒤 개발 DB 의 테넌트 **10개 전부**가 「선언됨」이 됐다
(`declared_tenants()` → 10건 · 출처 `운영 설정 VIDEO_RETENTION_DAYS (전역 선언)`).
그 다음에야 `apps/dsm/retention.py` 의 코드 기본값 30을 지웠다 —
**순서가 곧 내용이다**(지시서 §4 함정 ①).

## 2. **백업 파일이 실재한다** — 도구: `scripts/ops_backup_volume.py`

```
python scripts/ops_backup_volume.py --evidence docs/agent/evidence/OPS-19/backup_volume_20260906.md
```
exit **0**. 전문은 그 파일에 있다. 요약:

| | |
|---|---|
| 목적지 볼륨 | `gx_backup_vault_e` (DB 데이터 볼륨 `gx_pgdata` 와 **다르다**) |
| 컨테이너 안의 자리 | `/backup` — 세종이 정한 이름. 그 전에는 `/vault` 였다 |
| 파일 | `/backup/database_guardianx_20260906T160107.dump` |
| 크기 | **9,209,410 바이트** |
| sha256 | `ef9b9e6eb2dae9f7d8a20eefce09259398e08cc71256997b36e0550090871031` (sha256 값) |
| 거기서 읽히는가 | **다른 컨테이너**에서 `pg_restore --list` 목차 **3,351줄** |
| 저장소 안인가 | **아니다** — 저장소 작업복사본 밖이다 |

★ 판이 맞아야 한다: 앱 컨테이너의 `pg_dump` 는 17.7, 서버는 18.1 이다[실측].
그래서 DB 컨테이너와 **같은 이미지**를 `--rm` 으로 띄워 그 안의 클라이언트로 뜬다.

## 3. **복구를 해 봤고 RTO 를 쟀다** — 도구: `scripts/ops_restore_drill.py`(신규)

```
python scripts/ops_restore_drill.py \
    --evidence docs/agent/evidence/OPS-19/restore_drill_20260906.md \
    --json     docs/agent/evidence/OPS-19/restore_drill_last.json
```
exit **0**. 요약:

| | |
|---|---|
| 되살린 자리 | 임시 DB `restore_check_20260906070334` (끝나고 **지웠다**) |
| 표 수 | 원본 **223개** · 복구 **223개** — 같다 |
| **RTO 실측** | **0.14분 (8.2초)** — 임시 DB 만들기부터 지우기까지 벽시계 |
| SLA 초안 목표 | 30분 (GX-LAW-05) · 이 수는 **판정이 아니라 대조**다 |

★ 복구만 따로 재지 않았다. 새벽에 사람이 겪는 시간에는 **DB 를 만들고 치우는**
시간이 들어 있고, 그것을 빼면 RTO 가 실제보다 짧게 적힌다.

⚠ **이 수를 그대로 운영에 옮기지 마라.** 개발 DB 는 9MB 다. 운영 DB 가 100배면
RTO 도 그만큼 는다. 이 수가 말하는 것은 「30분 안에 된다」가 아니라
**「재는 자리가 생겼고, 지금 이 크기에서는 8초다」**이다.

## 4. 주기 — **등록했고, 그 표를 읽어 확인했다**

`backend/config/celery.py` 의 beat 표(선언)와 `django_celery_beat` 의 주기 표(실제)를
**둘 다** 맞췄다. 코드만 고치면 beat 를 재기동할 때까지 안 돈다 —
「등록했다」와 「등록된 것이 돈다」는 다른 사실이다(D-284).

| 항목 | 태스크 | 전 | 후 | enabled |
|---|---|---|---|---|
| `ops-backup-daily` | `common.ops_backup_beat` | 03:30 | **03:00** | True |
| `ops-restore-drill-weekly` | `common.ops_restore_drill_beat` | (없음) | **일 06:00** | True (**새로 생겼다**) |
| `ops-audit-purge-daily` | `common.ops_audit_purge_beat` | 03:10 | 02:40 | False (**안 건드렸다**) |
| `law02a-video-retention-sweep` | `common.video_retention_sweep_beat` | 03:20 | 02:50 | False (**안 건드렸다**) |

시각의 뜻은 **순서**다: 정리(02:40) → 영상 파기(02:50) → 백업(03:00) → 복구 시험(일 06:00).
지우기 전의 상태가 백업에 담기면 정리와 백업이 서로를 되돌릴 수 없게 된다.

## 5. ⚠ **아직 못 넘은 것 — 이것이 OPS-19 의 남은 절반이다**

### ㉠ 주기가 도는 컨테이너에는 `/backup` 이 **안 붙어 있다**
[실측 2026-09-06 · `common.ops_backup_beat` 를 gx-shell 에서 한 번 부름]
```
{"verdict": "UNKNOWN", "out_dir": "/backup", "separate_volume": false,
 "reason": "보관처 '/backup' 가 **별도 볼륨으로 안 붙어 있다** — 여기에 뜨면
            컨테이너와 함께 사라지고, 그 전까지 「파일이 생겼다」가 초록으로 보인다"}
```
`common/ops_tasks.py::backup_dir_is_separate_volume()` 가 `st_dev` 로 마운트 경계를
재서 **백업을 돌리지 않고** 막았다. 이 가드가 없었으면 오늘 밤 03:00 에
컨테이너 루트에 덤프가 떨어지고 **「백업이 매일 돈다」가 초록으로 보였을 것**이다.

붙이는 선언은 `docker-compose.yml` 에 섰다(`gx_backup_vault_e:/backup` — celery ·
beat · shell 셋). **적용은 컨테이너 재생성이 필요하고, 그것은 이 차선의 권한 밖이다** —
지금 다른 차선 넷이 이 컨테이너들 위에서 일한다. 조율자가 재기동 창을 열 때 붙는다.
그때까지 **백업의 자동 갈래는 회색이고, 손으로 뜬 것(§2)만 사실이다.**

### ㉡ 주 1회 복구 시험은 이 기계에서 **회색**이다
[실측] 앱 컨테이너 `pg_restore` **17.7** < DB 서버 **18.1**. 낮은 판은 높은 판의
덤프를 못 읽는다. 태스크가 그것을 **먼저 재고** `UNKNOWN` 을 낸다 —
못 잰 것을 「복구 성공」으로 적지 않는다. 고치는 자리는 코드가 아니라
**워커 이미지의 `postgresql-client` 판**이다.
(오늘 실제로 부른 결과는 `{"verdict":"UNKNOWN","reason":"보관처 '/backup' 에 덤프가
하나도 없다"}` — ㉠이 먼저 걸렸기 때문이다.)

### ㉡b **`/backup` 을 붙여도 자동 백업은 아직 실패한다 — 같은 판 문제다**
[실측 2026-09-06 · gx-shell 안에서 실제로 `pg_dump` 를 서버에 던져 봤다]
```
pg_dump: error: aborting because of server version mismatch
pg_dump: detail: server version: 18.1 (Debian 18.1-1.pgdg13+2); pg_dump version: 17.7 (Debian 17.7-0+deb13u1)
```
`common.ops_backup_beat` 는 `scripts/ops_backup.py::dump_db(target)` 를 **`via="local"`**
으로 부른다 — 즉 워커 컨테이너 안의 17.7 로 뜬다. 그러므로 ㉠(마운트)을 갚아도
그 다음에 이 벽이 있다. **두 개를 한 개로 세지 마라.**
고치는 길 둘: ㉮ 워커 이미지의 `postgresql-client` 를 18로 올린다 ㉯ 태스크가
`via="docker:postgres"` 로 부르게 한다(그러면 워커 안에 도커 소켓이 필요하다 —
그건 또 다른 권한 문제다). 어느 쪽도 이 차선의 권한 밖이라 **재고 적기만 했다.**

### ㉢ 「백업 보존 14일」은 **선언만 있고 집행이 없다**
14일 지난 덤프를 지우는 손이 아직 없다. 지금 볼륨에는 4개가 쌓여 있다.
선언만 있고 집행이 없는 수는 이 저장소가 방금 지운 것(코드 기본값)과 같은 모양이므로,
**다음 사람이 갚아야 할 빚으로 여기 적어 둔다.**

### ㉣ **객체저장(영상·캡처)은 이 백업·복구에 안 들어 있다**
DB 만 살아나면 「영상이 있었다고 말하는 DB」가 된다. `ops_backup.py --objects` ·
`ops_restore.py --objects` 가 그 절반이고, 이번 턴에 안 태웠다.

### ㉤ **다른 호스트가 아니다**
볼륨을 갈랐다는 사실은 「저장소와 함께 죽지 않는다」까지 말하고,
「이 기계와 함께 죽지 않는다」는 **말하지 않는다.** RPO 24h 를 약속하려면
그 절반이 더 필요하다.

## 7. ⚠⚠ 다음 사람이 밟을 함정 — **전역 선언 30일이 만든 318행**

[실측 2026-09-06 · 개발 DB · `retention.sweep(dry_run=True)`]

    retention_days = 30 · expired_total = **318** · deleted_total = 0 (미리보기라서)

세종이 선언한 「스냅샷·구간 참조 30일」은 **전역 선언**이므로 개발 DB 의
테넌트 10개가 전부 파기 대상이 됐다. 그 결과 **만료 행이 318건** 있다.

지금은 안전하다 — beat 항목 `law02a-video-retention-sweep` 이 `enabled=false` 이고
(2026-09-05 17:42 에 사람이 껐다) 이번 턴에 **켜지 않았다.**

> ⛔ **그 항목을 켜는 사람에게**: 켜는 순간 318행이 **하드 삭제**된다.
>   되돌릴 수 없다. 켜기 전에 ㉠ 이 318행이 버려도 되는 것인지 보고
>   ㉡ 그 전에 백업을 한 번 뜨고(§2 의 한 줄) ㉢ `dry_run=True` 로 목록을 먼저 본다.
>   「선언했으니 켜도 된다」가 아니다 — 선언은 **누가 정했는가**를 갚았을 뿐이고,
>   **무엇이 사라지는가**는 켜기 전에 눈으로 봐야 하는 다른 질문이다.

★ 그리고 이것이 P-67 의 값어치다: 예전에는 같은 318행이 **아무도 정하지 않은
  코드 기본값 30**으로 사라질 뻔했다. 지금 사라진다면 그것은 **세종이 정한 30**이고,
  임자가 있는 수다.
