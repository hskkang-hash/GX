## 1. ★ 적용 前에 잡은 것 — 저널을 못 쓰는 결함 (D-270 ① 그 자체)

승인 명령을 **그대로 실행했으면 실패했다.** `backfill_owner_apply.py` 의 문자열 4곳이
`"\n"`(역슬래시+n 2글자)로 들어가 있었다.

| 위치 | 실행하면 |
|---|---|
| 155행 `open(..., newline="\n")` | `ValueError: illegal newline value` — **단, 그 전에 저널 파일이 0바이트로 생성된다** |
| 157·164행 `+ "\n"` | 저널이 개행 없이 **한 줄로 이어 붙는다** → 롤백의 `splitlines()` 가 0행을 읽는다 |

실측으로 확인했다 (AST 로 리터럴을 꺼내 코드포인트 `[92, 110]` 확인 → `open()` 이
`ValueError` 를 던지고, **파일은 이미 0바이트로 만들어져 있었다**).

무엇이 문제인가 — 두 번째 손해가 더 크다:

1. 저널 경로에 **0바이트 파일이 남는다.** 스크립트는 "저널이 이미 있으면 덮지 않고 거부"하므로
   재실행이 **영구히 막힌다** (사람이 그 파일을 지워야 하는데, 지우는 습관이 붙으면 D-261 (3) 이 무너진다).
2. 만약 155행만 고치고 157·164행을 놓쳤다면 — 백필은 **성공하고** 저널은 한 줄짜리 쓰레기가 된다.
   즉 **25,296행을 되돌릴 수 없는 상태로 쓰게 된다.** 이것이 이 결함의 진짜 위험이다.

> **이것이 D-270 ①이 말한 사고와 같은 계열이다** — 인자 검증 전에 truncate 하는 `io.open`.
> 오늘은 대상이 24KB 스크립트가 아니라 **롤백의 유일한 근거**였다.

**처분**: 4곳을 **원자 교체**(임시파일 + `os.replace`, D-270 ①)로 수정 → `py_compile` 통과 →
AST 로 "역슬래시+n 리터럴 0건 · `newline` 코드포인트 `[10]`" 재확인 → 컨테이너 복사 후
**sha256 동일**(`a46a7f15…`) 확인. 잘린 채 복사되던 사고(D-270 ②)를 같은 방식으로 막았다.

```
pg_restore → gx_verify_before          # 백필 前 상태 (211 테이블)
COPY (SELECT '<tbl>'||'|'||id||'|'||coalesce(group_id::text,'NULL') …)   # 양쪽 45,499행
diff <(sort before) <(sort after)
```

| 항목 | 값 |
|---|---:|
| diff `<` (변경 前) | **25,296** |
| diff `>` (변경 後) | **25,296** |
| **그 외 변경** | **0** |

- 변경된 행이 **전부 `NULL` → 값** 방향임을 확인 (기존 소유자를 덮은 행 **0건**)
- 값을 **`NULL` 로 지운 행 0건**
- 변경된 필드는 **`group_id` 하나뿐** (저널의 `field` 종류 = `['group_id']`)

**초과 0행.** 즉시 롤백 조건에 해당하지 않는다.

## 8. 이 턴이 남기는 교훈 — D-270 ③ 이 왜 게이트여야 하는가

오늘 두 번 연속으로, **판정문은 있었지만 그것을 지킨 것은 게이트가 아니라 사람의 눈**이었다.

둘 다 "잡혔으니 다행"이 아니라 **"안 잡혔으면 그대로 나갔다"**는 뜻이다.
→ `verify_classification.py`(D-270 ③) 와 함께, **쓰기 스크립트의 저널 왕복 자가검사**
(저널을 쓰고 즉시 읽어 행수를 대조)를 게이트에 넣을 것을 제안한다. 다음 단계에서 착수한다.
