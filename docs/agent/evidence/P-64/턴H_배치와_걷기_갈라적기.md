## 왜 갈렸나 — **차선 C 가 경고한 자리가 그대로 실현됐다**

`deploy.sh` 의 걷기가 회색으로 끝났고, 화면이 말한 것은 이랬다:

```
서버에 연결하지 못했습니다. 연결을 확인한 뒤 다시 시도해 주십시오.
```

★ **그 문구는 이번 턴에 차선 C 가 만든 것이다.** 화면은 옳게 동작했다 —
말할 수 없던 실패를 말했다. 틀린 것은 화면이 아니라 그것이 부른 서버다.

원인을 이름으로 확정했다. 같은 프리플라이트를 두 서버에 물었다:

```
OPTIONS /api/v1/auth/login   Access-Control-Request-Headers: content-type,idempotency-key

  8000 → allow-headers: … x-no-cache                              ← idempotency-key **없음**
  8010 → allow-headers: … x-no-cache, x-gx-wall-token, idempotency-key
```

브라우저는 프리플라이트가 허락하지 않은 헤더가 붙은 요청을 **아예 보내지 않는다.**
그래서 로그인 요청이 나가지 못했고 화면은 「연결하지 못했다」를 말했다.
**8000 은 2026-09-05 14:41 코드를 물고 있다**(`LIVE_8000_RUNS_STALE_CODE`).

## 왜 안 고쳤나 — **막힌 것은 우리 코드가 아니라 손이다**

8000 을 신선한 코드로 다시 띄우려 세 번 시도했고 셋 다 **도구의 권한 분류기**가 막았다:

```
docker exec gx-shell kill <pid>   → 차단
docker restart gx-shell           → 차단
```

우회하지 않았다. 대신 **답할 수 있는 질문을 정확히 골랐다**:
「배치된 번들이 걷는가」는 못 재고, 「**이 커밋의 화면이 신선한 API 로 걷는가**」는 잰다.
같은 커밋(`8b36963`)으로 API 주소만 8010 으로 굽고 3010 에 세워 걸었다 — 완주 3/3.

⚠ **이것은 배치 검증이 아니다.** 두 번들의 차이는 API 기준 주소 문자열 하나뿐이지만,
「하나뿐」과 「같다」는 다르다. 다음 사람이 이 줄을 「배치가 걸렸다」로 읽으면
그것이 P-59 가 만들어진 이유(낡은 사본을 걸어 놓고 초록으로 읽음)의 재발이다.
