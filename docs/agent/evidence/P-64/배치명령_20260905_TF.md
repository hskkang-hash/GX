# P-64 — **배치는 절차가 아니라 명령이다** `scripts/deploy.sh` [실측 2026-09-05 · 턴 F · 차선 Q]

- 명령: `bash scripts/deploy.sh` · 자기시험 `bash scripts/deploy.sh --self-test`
- RUNBOOK 의 배치 절(STEP 2C)은 **이 한 줄로 바뀌었다.** 손 절차를 두 벌로 남기지 않았다.
- 판정기를 새로 짓지 않았다: 번들 신원은 `scripts/verify_bundle_hash.py`(P-59),
  걷기는 `scripts/walk_scenarios.py`. 이 명령이 아는 것은 **순서와 되돌리기**뿐이다.

## 0. 무엇을 막는가

09-04 07:17 자 번들이 **하루 동안 서비스됐다.** 손 절차 네 걸음 중 ③(배치)이 한 번
빠졌고, 빠졌다는 것을 아무도 몰랐다. 그 사이 찍은 화면 증거 24장이 전부 낡은 번들의
증거였고, `capture_screens` 의 빨강 10건이 「UX 회귀」로 등재될 뻔했다.

> **절차는 빠뜨릴 수 있고 명령은 빠뜨릴 수 없다.**

## 3. 걷기가 빨간 이유 — **셋 다 배치의 사실이 아니다**

`walk_scenarios` 는 이제 **완주 3/3** 이다(1번 실행에서는 1/3 이었다 · §4).
남은 빨강은 **3건, 전부 같은 것**:

```
503 GET http://localhost:8000/api/dsm/events/{id}/snapshot
```

사유는 게이트용 `runserver`(8000, 23:55 에 다른 차선이 띄운 것)가 **MinIO 없이 떴다**는
것이다 — 그 프로세스 로그가 그대로 말한다:

```
WARNING Retrying … NameResolutionError("… Failed to resolve 'minio.invalid' …")
```

**코드 결함이 아니라 미연결이다**(RUNBOOK: runserver 에 `MINIO_ENDPOINT`·키를 함께 준다).
→ **조율자 배선**: 8000 을 MinIO 환경으로 다시 띄우면 이 3건이 사라지고 걷기가 초록이 된다.
그 전까지 `deploy.sh` 의 완주는 **빨강이 옳다** — 조용히 넘기지 않는다.

## 4. 이 명령이 **다른 도구의 낡음**을 드러냈다 (P-59 의 반복)

새 번들을 배치하자마자 `walk_scenarios` 가 두 걸음에서 멈췄다. 그 빨강은 화면의 결함이
아니라 **걸음표의 기대가 낡은 것**이었다 — 걸음표는 9-04 번들을 보고 적혔다:

| 걸음 | 낡은 기대 | 지금 화면(정본 상수) |
|---|---|---|
| S1 ② 「미처리」 | `미처리 — 대응 축이 아직 「발생」인 것` | `미처리 — 아직 아무도 손대지 않은 것` (`EventList.tsx:98`) |
| S3 ① `/dsm/queue` | `지금 가장 급한 하나` | `지금 처리할 것 — 가장 급한 하나` (`FocusQueue.tsx:97`) |

**낡은 입력은 거짓 초록만 만드는 것이 아니라 거짓 빨강도 만든다.** 고쳤다(완주 3/3).

## 5. 콘솔 줄에 **URL 이 없어서 분류할 수 없었다**

브라우저가 적는 줄은 「Failed to load resource: … status of 404」 **뿐**이고 어느 자원인지가
없다. 그래서 인수 자산의 글꼴 404 와 우리 화면의 고장이 **같은 줄**로 쌓였다.
`walk_scenarios` 가 이제 브라우저의 `location.url` 을 그 줄에 붙이고, 자리로 가른다.
그렇게 이름이 붙은 것 셋(전부 **남의 자리·환경**):

| 자리 | 무엇인가 |
|---|---|
| `/Inter/Inter-VariableFont_opsz,wght.ttf` (404) | **인수 자산 CSS 가 안 실린 글꼴을 부른다.** 우리 CSS 의 `/fonts/Inter-Variable.ttf` 는 200 이다. 화면은 대체 글꼴로 그려진다 — 프런트 차선이 볼 자리 |
| `/api/user-groups/gen-schema` (422) | dj-core · §0.4 · 상용점검 §3.1-5 에 **이미 등재된** 결함 |
| `/ws/surveillance/profiles/` (404) | `runserver` 는 WSGI 라 이 환경에 웹소켓이 없다(partner·orders 와 같은 사유) |

⚠ **분류는 면제가 아니다.** 자기시험에 갈래를 박아 두었다: **URL 이 없는 404 줄은
분류되지 않는다**(그렇지 않으면 목록이 「모든 404 면제」가 된다).

## 6. 이 명령이 잡은 것 하나 더 — **더러운 작업본**

번들에는 `GX_COMMIT:<HEAD>` 가 박힌다. 작업본이 더러우면 **박힌 신원과 내용이 다르고**,
게이트는 그 둘을 구별하지 못한다 — 그 구별 불가가 P-59 사고의 모양이다.
4번 실행이 실제로 그 상태를 잡았다(다른 차선이 프런트를 고치는 중). `--allow-dirty` 로
넘길 수 있지만 그때는 **왜 넘겼는지가 로그에 남는다.**
⚠ `--skip-build` 일 때는 이 검사를 하지 않는다 — 그때 배치의 입력은 작업본이 아니다.

## 7. 남은 위험

- **`package.json` 이 host 와 빌드 컨테이너에서 다르다** [실측 host `5902f8bb…` ≠ 컨테이너 `ef2e4b32…`].
  이 명령은 `npm install` 을 하지 않는다 — **말해 주기만 한다.** 의존성이 바뀐 턴에는
  사람이 한 번 넣어야 하고, 그 자리가 다음 사고의 후보다.
- **원자적 교체가 이 마운트에서는 진짜 원자적이지 않다.** 지금은 「풀고 → 재고 → 바꾸고 →
  다시 재고 → 깨졌으면 복사로 고친다」이지, 한 순간의 rename 이 아니다.
  스테이징(리눅스)에서는 rename 이 원자적이므로 이 우회가 필요 없다 — 그러나
  **필요 없어졌다는 것을 재기 전에는 지우지 않는다.**
- 걷기는 `gx-shell` 의 `playwright`+`chromium` 을 쓴다. 컨테이너를 다시 만들면 **사라진다**
  (이번 턴에 다시 깔았다: `pip install playwright` · `python -m playwright install chromium` ·
  `install-deps`). 없으면 걷기는 **회색(2)** 이고 회색은 초록이 아니다.
