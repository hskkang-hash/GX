# OPS-13a · **「설명되지 않는 502 7건」에 이름을 붙인다** — 갈라 보니 결함이 아니라 **판정기의 눈**이었다

- 날짜: **2026-09-07** (턴 **TJ** · 차선 E) · 기계 시각 UTC
- 근거: 지시서 턴 J §2 **P-92** · §3 E행 ①
- 읽은 것만 했다. 살아 있는 컨테이너를 지우거나 다시 만들지 않았고, 설정을 한 줄도 고치지 않았다.

---

## 0. 한 줄

> **7건은 「다른 결함」이 아니다.** 나머지 6건과 **같은 원인**이고, 판정기가 못 본 까닭은
> ㉠ **틀린 자국**(`Autorestarting` = 예고)을 보았고 ㉡ **틀린 창**(요청의 **끝** 시각, 그것도 초 단위)을
> 보았기 때문이다. 옳은 자국(`Worker exiting`)과 옳은 창(요청이 **살아 있던 구간**)으로 다시 재면
> **13/13 이 설명된다** — 그리고 음성 대조는 18.8% 에 머문다(차 **81.2%p**).
>
> 다만 갈라 보는 도중 **새 결함 하나**가 나왔다: **앞단의 재시도가 두 번에서 멈춘다.**
> 그것이 이 7건이 아니라 **13건 전부**를 손님에게 새어 나가게 한 마지막 한 걸음이다. → §4

## 3. 7건이 왜 「같은 초」에 안 걸렸나 — 까닭은 둘, 둘 다 판정기 쪽이다

1. **자국이 예고였다.** `Autorestarting worker after current request.` 는 **선언**이다 —
   워커는 그 뒤 「지금 처리 중인 요청을 마치고」 나간다. 손님의 연결을 실제로 끊는 것은
   그 다음의 **`Worker exiting (pid: N)`** 이고, 둘 사이는 [실측] 0.13~0.25초 벌어진다.
   #02·#03 이 정확히 그 틈에 빠졌다: 예고 `27.724`·`27.726`·`27.730` → 종료 `27.856`·`27.857`.
2. **창이 요청의 끝 한 점이었다.** 접근로그의 시각은 요청이 **끝난** 순간이고 초 단위다.
   재활용은 요청이 **도는 동안** 일어난다. `rt = 0.234` 인 요청은 27.77 에 시작해 28.0 에 끝나는데,
   판정기는 28초만 보고 27초의 자국을 놓쳤다. **끝 한 점으로 재면 짧은 요청은 언제나 무죄가 된다.**

→ 그러므로 **7건은 잡음이다.** 사유: **판정기가 예고를 자국으로 삼고 요청의 끝 한 점만 보았다.**
   결함은 「다른 무엇」이 아니라 **이미 이름이 있는 것**(OPS-13 워커 재활용)과 같다.

## 4. 그러나 — 갈라 보다 나온 **새 결함**: 앞단의 재시도가 **두 번**에서 멈춘다

13건 **전부**의 `$upstream_addr` 이 한 글자도 다르지 않다:

```
"172.18.0.6:8000, 172.18.0.6:8000, gx_app"
```

세 번째 칸의 `gx_app` 은 서버 주소가 아니라 **업스트림 무리의 이름**이다 — nginx 가
「고를 서버가 더 없다」를 적을 때 쓰는 자리다. 앞단 오류로그가 같은 순간에 이렇게 적었다:

```
[error] *36944 recv() failed (104: Connection reset by peer) while reading response header
[error] *36944 recv() failed (104: Connection reset by peer) while reading response header
[error] *36944 no live upstreams
```

까닭은 앞단 설정에 있다 (`nginx/gx-front.conf` · 컨테이너 안 `/etc/nginx/gx/gx-front.conf` 105~117행):

```nginx
upstream gx_app {
    server gx-gunicorn-e:8000 max_fails=0;
    server gx-gunicorn-e:8000 max_fails=0;   # 같은 서버를 두 줄 적어 재시도를 만들었다
    keepalive 32;
}
```

- 재시도를 **서버 줄을 두 번 적어** 만들었고, `proxy_next_upstream_tries` 는 선언이 없다.
  그러면 nginx 는 **무리의 서버 수만큼**, 즉 **딱 두 번** 시도한다.
- 죽어 가는 워커가 여럿이면 앞단 연결 풀(`keepalive 32`)에 **끊긴 연결이 여러 개** 들어 있다.
  두 번 뽑아 둘 다 끊긴 연결이면 **세 번째 기회가 없다** — 손님이 502 를 본다.
- 이것이 「재시도 138건 중 125건은 되살아나고 13건은 새어 나갔다」의 정확한 갈림길이다.
  되살아난 125건은 두 번째 뽑기가 성한 연결이었을 뿐이다.

### 절 신설 — **OPS-13b · 앞단의 재시도가 두 번에서 멈춘다** · **회색**

| | |
|---|---|
| 이름 | **OPS-13b — 앞단의 재시도가 두 번에서 멈춘다(`gx_app` 서버 두 줄 · `proxy_next_upstream_tries` 미선언)** |
| 색 | **회색** — 원인은 [실측]으로 짚었으나 **고쳐서 502 가 줄어드는지는 재지 않았다** |
| 왜 회색인가 | 이 저장소는 이 자리에서 두 번 넘어졌다: `keepalive_requests 50`(3→5건 악화) · 지터 확대(3→5건 악화). **생각으로 고른 값은 여기서 두 번 다 틀렸다.** 재기 전에는 초록이 아니다 |
| 재는 법 | `proxy_next_upstream_tries 3;`(또는 서버 줄 하나 더) 를 켠 **전/후**로 같은 부하를 걸어 502·p95 를 나란히 적는다. 값을 바꾸는 것은 앞단 `reload` 이므로 **살아 있는 컨테이너를 만지는 일** — 차선 E 는 이 턴에 하지 않았다 |
| 소유 | `nginx/` 는 차선 E 의 소유가 아니다. **제안만 남긴다** |

⚠ **「그러면 `max_requests` 를 끄면 되지 않나」에 다시 답하지 않는다.** 그 실험은 턴 D 가
  이미 했고(502 0건) **되돌렸다** — 그 0 은 결함을 고친 0 이 아니라 **숨긴 0** 이고,
  대가는 몇 시간 뒤의 OOM 이다. 그 문단은 `backend/gunicorn.conf.py` 에 살아 있다.

## 5. 이 문서가 **재지 않은 것**

- 워커가 나가고 새 워커가 뜨기까지 [실측 151건] 중앙값 **1.32초** · 최대 **7.88초** · 최소 0.03초.
  그러나 지금 워커는 **4개**(`--workers 4`)이므로 이 창에도 받을 워커는 남아 있다 —
  **「받을 워커가 0 이 되는 창」은 이번 표본에서 재지 못했고, 502 의 원인도 그것이 아니다.**
  원인은 **앞단 연결 풀에 남은 끊긴 연결**이다. 둘을 섞어 적지 않는다.
- 앞단 컨테이너의 `--workers 4 --threads 4 --worker-class gthread` 는 **명령줄**에서 오고,
  `backend/gunicorn.conf.py` 의 `workers = min(cpu,2)` · `worker_class = uvicorn…` 을 **덮는다**.
  즉 **선언과 도는 것이 다르다**(D-301). `max_requests=200`·`jitter=50` 은 명령줄에 없으므로
  설정 파일 값이 산다. 이 어긋남은 이번 502 의 원인이 아니지만 **적어 둔다** — 다음 사람이
  `gunicorn.conf.py` 를 고치고 「워커 수를 바꿨다」고 믿을 자리다.
- **운영 기계가 아니다.** 이 13,619줄은 이 개발 기계의 운영형 인스턴스(8500)에서 나왔다.

## 7. 판정기를 고쳤다 — **초록으로 만든 것이 아니라 자를 바꾸고 대조를 같이 바꿨다**

`scripts/verify_front_line_502.py` (차선 E 소유) 를 고쳤다. 고친 것은 **넷**이다:

| | 고친 것 | 왜 |
|---|---|---|
| ㉠ | 뒷단 자국을 **마이크로초까지** 읽는다 (`_DOCKER_TS_US`) | 초로 자르면 같은 초의 자국이 뭉개진다 |
| ㉡ | 자국을 **둘** 읽는다 (`read_marks`) — 예고 `Autorestarting` · **종료 `Worker exiting`** | 손님의 연결을 끊는 것은 종료다 |
| ㉢ | 접근로그에서 **`$request_time` 을 버리지 않는다** (`parse_access` 가 `(끝난 시각, rt)` 짝을 낸다) | 구간을 그리려면 필요하다 |
| ㉣ | 새 순수 함수 `span_coincidence(events, marks)` — 창이 `[끝 - rt, 끝 + 1초)` | 요청은 점이 아니라 구간이다 |

### 이것이 왜 「예외 칸 열기」(D-327)가 아닌가 — 셋으로 답한다

1. **음성 대조를 같은 자로 다시 댔다.** 창을 넓히면 무엇이든 자국 옆에 놓인다 —
   그래서 정상 200 에도 **똑같은 구간 자**를 대서 **18.8%** 를 얻었다. 502 는 100% 다.
   대조 없이 창만 넓혔다면 그것이 예외 칸이다.
2. **종전 수를 지우지 않았다.** 출력 표에 `±0초` 줄이 그대로 있고(6/13 = 46%),
   판정문 ②에도 「종전 자로는 미설명 7건이었다」가 **글자로 남는다.**
   자를 바꾸면서 옛 수를 지우면 「무엇을 바꿔서 설명이 되었는가」가 사라진다.
3. **자기시험에 음성 갈래를 먼저 넣었다.** 「구간으로 100% 인데 정상도 96%」인 합성 표를
   먹이면 판정기는 **회색**을 내야 한다 — 그 시험이 들어 있고, 통과한다.
   구간으로도 설명 안 되는 표(13 중 9)는 여전히 **빨강**이다.
