# W0-16 (e) — 레거시 `superuser` 역할 회수 절차서

**작성** 2026-08-22 (에이전트) · **실행 주체: 대표/운영자** · **에이전트는 운영에 반영하지 않는다**
**결정** D-243(무중단 순차 회수) · D-244(운영 조치는 사람) · 불변제약(운영 서버·운영 DB 직접 변경 금지)

> 이 문서는 **운영 반영 대기 상태**로 제출된다. 로컬/스테이징 검증은 끝났다
> (`http_role_split_test.md`). 아래 절차를 운영에 적용할지는 대표가 정한다.

---

## 0. 회수하면 무엇이 닫히나 (실측된 값)

| | 회수 전 | 회수 후 (파일럿 1계정 실측) |
|---|---:|---:|
| Anyang 운영자가 보는 남의 테넌트 레코드 | **15건** | **1건** |
| 자기 테넌트 레코드 | 7건 | **7건 (변화 없음 — 업무 무중단)** |

남는 1건은 `created_by IS NULL` 경로다. **이 절차로는 닫히지 않는다** — W0-13 의 몫이다.

---

## 1. 순서 (되돌릴 수 있는 것부터)

```
STEP 1  대체역할 부여        ← 되돌리기 쉬움 · 업무 영향 없음 (권한이 늘기만 한다)
STEP 2  전환 플래그 끄기      ← 설정 1줄. 여기서 처음으로 "좁아진다"
STEP 3  검증                 ← 좁아진 것이 의도한 만큼인지 본다
STEP 4  레거시 역할 회수      ← 계정 단위로 쪼개서
STEP 5  뒷정리               ← is_default 내리기 · 회수 이력 남기기
```

**STEP 2 와 STEP 4 를 바꾸지 말 것.** 플래그를 먼저 끄면 문제가 생겨도 한 줄로 되돌아온다.
역할을 먼저 떼면 되돌리려고 다시 DB 를 만져야 한다.

---

## 2. STEP 1 — 대체역할 부여 (무중단)

```bash
# 계획을 먼저 본다. 한 행도 쓰지 않는다 (D-209)
python scripts/role_split_local.py --global-groups 5,7

# 적용
python scripts/role_split_local.py --global-groups 5,7 --apply
```

생기는 것:
- `gaion_global_admin` — GAION 운영 6계정 (group 5·7)
- `tenant_admin_6` — Anyang 7계정
- 두 역할 모두 레거시 `superuser` 의 메뉴/탭 권한 행을 **그대로 복제** (menus 101 · tabs 27)

이 시점에 계정들은 **레거시 역할과 새 역할을 동시에** 갖는다. 권한은 늘기만 하므로 업무가 끊기지 않는다.

**확인**: 각 테넌트에서 1명씩 로그인해 평소 화면이 그대로인지 본다. 이상 있으면 여기서 멈춘다
(새 역할을 떼면 원상복구 — 아직 아무것도 좁아지지 않았다).

### ⚠ 사람이 정해야 하는 것 하나
`--global-groups 5,7` 의 **5(Group Default)** 포함 여부. 근거는 두 계정(`hans`·`ldk`)의 이메일
도메인이 `gaion.kr` 이라는 것뿐이다. 조직도로 확인해 GAION 직원이 아니면 `--global-groups 7` 로 좁힌다.

## 3. STEP 2 — 전환 플래그 끄기

```
TENANT_TRUST_LEGACY_SUPERUSER=False      # backend/.env (설정 1곳 · D-212)
```
이 순간부터 **이 저장소의 판정**은 레거시 `superuser` 역할을 전역으로 인정하지 않는다.

> **주의 — 이 플래그는 dj-core 를 바꾸지 못한다.** `core/base.py:308` 의 ORM 우회와
> `core/role/permission.py:475` 의 권한 우회는 §0.4 라 그대로다. 즉 **플래그만으로는 안 닫힌다.**
> 실제 차단은 STEP 4(역할 회수)와 W0-14(뷰 스코프)가 함께 만든다. 플래그는 **저장소 쪽 판정을
> 미리 맞춰 두는 것**이고, 되돌리기 쉬운 순서를 만들기 위한 단계다.

**되돌리기**: 값을 `True` 로. 재배포 외 작업 없음.

## 4. STEP 3 — 검증

| 확인 | 방법 | 통과 기준 |
|---|---|---|
| 업무 무중단 | 테넌트별 1명 로그인 → 평소 화면 | 200 · 자기 데이터 건수 변화 없음 |
| 격리 | `scripts/probe_tenant_isolation.py` (복제본에서) | 고객 테넌트 `foreign` 이 `created_by NULL` 건만 남음 |
| 전역 유지 | GAION 계정 로그인 | 기존과 동일한 범위가 보임 |

실패하면 STEP 2 를 되돌리고 원인을 본 뒤 다시 온다. **STEP 4 로 넘어가지 않는다.**

## 5. STEP 4 — 레거시 역할 회수 (계정 단위)

```bash
python scripts/role_split_local.py --apply --revoke <user_id>        # 1계정씩
python scripts/role_split_local.py --apply --revoke all              # 고객 테넌트 전원
```

권장 회차:
1. **파일럿 1계정** — 최근 로그인이 없는 계정부터 (`rin_superuser`·`tuan_superuser` 는 로그인 이력 없음)
2. 24시간 이상 두고 문의가 없으면 Anyang 나머지 5계정
3. **GAION 계정(group 5·7)은 회수 대상이 아니다** — `gaion_global_admin` 으로 대체됐을 뿐,
   전역 권한은 유지된다

**되돌리기**: 역할 재부여 (`--apply` 는 대체역할만 다루므로, 레거시 재부여는 수동 1행 INSERT).
되돌림 비용이 여기서부터 올라간다 — 그래서 STEP 3 를 통과한 뒤에만 한다.

## 6. STEP 5 — 뒷정리

1. **`role_role.is_default` 를 내린다** (id=1 `superuser` 가 `true` 다).
   지금은 사용자 생성 경로가 `code='user'` 를 찍어 고르므로 무해하지만,
   `is_default` 로 기본역할을 고르는 코드가 하나 생기면 **신규 계정이 전역 권한을 받는다.**
2. **회수 이력을 남긴다.** `user_coreuser_roles` 에는 `created_on`·`created_by` 가 없다 —
   누가 언제 줬는지도, 뗐는지도 DB 로 답할 수 없다(`superuser_accounts.md` §4-1).
   회수 회차·대상·수행자를 **별도 문서로** 남긴다. 이것이 감사 대응의 유일한 근거가 된다.
3. 로컬 시험 복제본을 지운다: `DROP DATABASE rolesplit_guardianx` (프로브가 재설정한 비밀번호가 남는다).

## 7. 하지 않는 것

| | 이유 |
|---|---|
| 운영 DB 에 직접 SQL 을 치는 것 | 불변제약. 이 스크립트도 **운영 복제본 DB 이름이면 쓰기를 거부**한다 |

| 이 절차만으로 "격리 완료" 선언 | 경로②(`created_by NULL`)가 남는다 — W0-13 · D-249 의 EXIT 기준은 **누출 0건** |
