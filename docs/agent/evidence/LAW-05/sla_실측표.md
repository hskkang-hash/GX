# LAW-05 — SLA 실측표 (**수를 넣을 자리**)

> **본문은 세종(CPO)이 쓴다.** 이 파일은 차선 E 가 만든 **자리**이고, 지금 실측
> 가능한 칸만 채웠다. 못 잰 칸은 「**못 쟀다**」로 남긴다 — 재지 않은 것을
> 약속하면 그 약속이 계약이 되는 순간 우리가 못 지킨다.
>
> 규칙 하나: **이 표의 어떤 칸도 「목표」로 시작하지 않는다.** 먼저 재고, 나온 수
> 위에서 목표를 정한다(D-280). 목표를 먼저 적으면 그 목표에 맞춰 재게 된다.

측정 2026-09-05 · 차선 E(턴 F) · **개발 기계 1대**(WSL2 · CPU 8 · mem 8GB · GPU 없음)

## 2. 각 칸의 근거와 **한계**

### ① 가용성 99.9% — 못 쟀다

99.9%는 **한 달에 43분 21초**의 정지를 허용한다는 뜻이다. 그것을 말하려면
**가동 시간을 재는 자리**가 있어야 하는데, 이 저장소에는 없다:

    · 밖에서 주기적으로 두드리는 것(외형 감시)이 **없다**
    · `ops_monitor.py` 는 **안에서** 잰다 — 시스템이 죽으면 감시도 같이 죽는다
    · 정지 시각을 기록하는 자리가 없다

★ **없는 것을 「99.9%」라고 적지 않는다.** 이 칸은 스테이징에 공개 URL 이 서고
  밖에서 두드리는 자리가 생긴 뒤에 처음 수가 들어온다.
  **세종 판정 필요**: 「밖에서 두드리는 자리」를 우리가 세우는가, 고객이 세우는가.

### ② 5xx ≤ 0.1% — **0.0776%** [실측]

    창    2026-09-02 ~ 2026-09-05 (앞단 nginx 접근로그 46,425줄)
    분포  200 = 43,160 · 401 = 3,226 · 502 = 36 · 404 = 2 · 499 = 1
    5xx   36건 ÷ 46,425건 = **0.0776%**
    근거  docs/agent/evidence/OPS-07/gx-front.access.log.gz (원본 그대로 보관)

⚠ **이 수를 그대로 SLA 로 옮기면 안 되는 이유 셋** — 적어 두지 않으면 다음 사람이 옮긴다:

    ㉠ 이 트래픽은 **개발 트래픽**이다. 사람 이용자가 아니라 차선들이 두드린 것이고,
       실사용 분포(로그인·목록·영상 조회)와 다르다.
    ㉡ 502 36건은 **백엔드가 재기동하던 순간**의 것이다. 운영에서는 무중단 배포가
       그 자리를 메우지만, 이 저장소에는 무중단 배포가 **아직 없다**.
    ㉢ 401 이 3,226건(6.9%)이다 — 5xx 는 아니지만 **정상도 아니다.**
       인증 실패가 이 비율이면 사용성 문제이거나 시험 잡음이다. 어느 쪽인지 못 쟀다.

### ③ RTO 30분 — 부분 실측

| 갈래 | 실측 | 자리 |
|---|---|---|
| 마이그레이션 되돌리기 | **381초** (6분 21초) · 판정 통과 | `docs/agent/evidence/OPS-08/rollback_drill.md` |
| DB 덤프에서 복구 | **성공** (시간은 안 적혔다) | `docs/agent/evidence/D-354/restore_run.md` |
| 객체(영상) 복구 | **못 쟀다** — `minio.invalid` 라 저장소가 없다 | 같은 파일 |
| 전체 복구(기계 재구성 포함) | **못 쟀다** | — |

★ **381초는 RTO 가 아니다.** 그것은 RTO 의 한 갈래(스키마 되돌리기)이고,
  진짜 RTO 는 「사람이 알아채고 → 판단하고 → 되돌리고 → 확인하기」까지다.
  알아채는 시간은 감시가 정하고(`ops_monitor` 주기), 판단하는 시간은 사람이 정한다.
  **셋 중 둘을 아직 안 쟀다.**

★ 그리고 [실측] **DB 만 살아나면 영상은 안 돌아온다.** 복구된 시스템은
  「영상이 있었다고 말하는 DB」가 된다 — 이것을 30분 안에 되돌린다고 적으면
  절반의 약속이다. **세종 판정 필요**: RTO 를 DB 기준으로 적는가, 영상 포함인가.

### ④ RPO 24시간 — **지금은 못 지킨다** [실측]

    [실측 2026-09-05]
      django_celery_beat 표: `ops-backup-daily`(common.ops_backup_beat) = **켜짐**
      settings.OPS_BACKUP_SCHEDULE_ENABLED = **False**
      settings.OPS_BACKUP_DIR             = **''** (빈 문자열)

★ 주기는 켜져 있는데 **태스크가 스스로 건너뛴다.** 즉 **자동 백업이 한 번도 안 돈다.**
  손으로 뜬 덤프는 하나 있다(2026-08-29 · 4,447,529바이트 · sha256 기록됨) —
  그러나 **손으로 뜬 것은 RPO 가 아니다.** RPO 는 「자동으로 얼마나 자주 뜨는가」이고,
  안 도는 백업의 RPO 는 24시간이 아니라 **무한**이다.

  ⚠ 이것은 결함이 아니라 **판정 대기**다: 백업은 「어디에 얼마나 오래 쌓을 것인가」를
    정해야 도는 일이고, 그 답은 고객 환경마다 다르다(D-375). 기본값으로 켜면 우리가
    남의 디스크에 대해 그 답을 정하는 것이 된다.
  **세종 판정 필요**: 보관처와 보관 기간. 그 둘이 정해지면 이 칸이 채워진다.

### ⑤ 응답 예산 — 두 층을 갈라서 잰다

**HTTP(밖에서 본 것)** — `GET /api/v1/health` · 앞단 nginx:8500 경유 · 순차 20회
[실측 2026-09-05]

    최소 28.2ms · p50 30.7ms · p95 45.7ms · 최대 103.2ms

**내부 파이프라인(안에서 본 것)** — `scripts/perf_measure.py` · 표본 30 (워밍업 5 제외)
[실측 2026-09-05]

    이벤트 처리(검출 → 이벤트 행)   p50 19.13ms · p95 38.59ms · 최대 44.83ms
    알림 발송(이벤트 → 수신자)      p50  4.82ms · p95 11.18ms · 최대 15.00ms

⚠ **이 수로 응답 예산을 못 정한다.** 왜 못 정하는지가 이 칸의 값이다:

    ㉠ 잰 엔드포인트가 **하나**다. 화면이 실제로 부르는 것 — 대시보드 목록,
       영상 조회, 검색 — 은 안 쟀다. 무거운 것은 안 재고 가벼운 것만 재면
       예산은 언제나 지켜진다.
    ㉡ **동시 접속 1**이다. 예산은 부하 아래에서 지켜져야 뜻이 있다.
       (이 기계에서 동시 접속을 올리는 것은 다른 차선의 작업을 방해한다 —
        `scripts/perf_load.py` 가 있으나 이번 턴에 **안 돌렸다**)
    ㉢ 데이터가 작다 — DB 95MB · 이벤트 0건 · 카메라 40대. 운영 규모에서 같은
       수가 나온다는 근거가 없다.

  **세종 판정 필요**: 예산을 어느 화면·어느 API 에 걸 것인가. 「전 API p95 500ms」
  같은 문장은 못 지킨다 — 영상 목록과 로그인은 같은 예산을 쓸 수 없다.

## 3. 이 표가 다음에 채워질 순서

    ① 스테이징 공개 URL 이 선다 → **밖에서 두드리는 자리**가 생긴다 → ①(가용성) 시작
    ② 보관처·보관 기간 판정 → 자동 백업이 돈다 → ④(RPO) 가 수를 갖는다
    ③ 예산을 걸 화면 목록 판정 → 그 목록으로 `perf_load.py` → ⑤(응답 예산)
    ④ 전체 복구를 한 번 해 본다(기계 재구성 포함) → ③(RTO)

**넷 중 셋이 판정 대기이고, 판정은 세종의 것이다.** 차선 E 는 그때 잴 준비가 됐다.

### 판정 — **닫을 수 없다**

`ga_readiness` 의 LAW-05 는 「**가용성을 약속하지 않는 SLA 는 완성이 아니다**」라고
스스로 적어 두었고, 그 칸은 **공개 URL(대표 승인)** 과 **외형 감시**가 서야 처음 수를
갖는다. 둘 다 이번 턴에 서지 않았다. 상태는 **미측정** 그대로 둔다 — 수는 안 움직인다.

### 이번 턴에 **움직인 칸 하나** — RPO ㉡ 을 갚았다

턴 G 의 SLA v0.2 §3-A 는 RPO 를 못 약속하는 이유 넷 중 ㉢ 을 이렇게 적었다:
「**목차가 읽힌 것**이지 **빈 DB 를 세워 본 것**이 아니다」.
그것은 이제 사실이 아니다 — `scripts/ops_restore_drill.py` 가 임시 DB
`restore_check_20260906070334` 를 **만들어 복구하고 지웠고**, 표 수가 원본 223 · 복구 223 로
같았다[실측]. **㉢ 은 갚혔고 ㉠㉡㉣ 는 남았다.** 남은 셋을 갚기 전에 RPO 를 약속하면
그것이 SLA v0.2 §3-A 가 이름 붙인 상용 사고의 모양이다.
