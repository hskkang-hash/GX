# P-110 — 백업 주기 스위치의 **반경**, 그리고 왜 회수증이 아직 0장인가

**잰 사람** 차선 E (DevOps/Release) · **잰 때** 2026-09-07 턴 M · **잰 자리** 이 기계, `gx-celery-e` 안

> 지시: 「스위치의 반경을 먼저 재고, **재기동으로 켤 수 있을 때만** 켠다.
> 컨테이너 재생성이 필요하면 멈추고 그렇게 말한다 — 그것이 대표 결정 ③ 이다.」

---

## 0. 한 줄

**스위치는 재기동으로 켜졌다.** 그리고 켜자마자 **다음 관문에서 멈췄다** —
`/backup` 이 볼륨으로 안 붙어 있다. 그 관문은 재생성이 필요하다.
**주기가 만든 회수증은 여전히 0장이고, 이번 턴에도 0장이다.**

---

## 1. 반경 ① — 이 이름은 **어디서 읽히나**

| 자리 | 무엇을 하나 |
|---|---|
| `backend/config/settings.py:916` | `env.bool("OPS_BACKUP_SCHEDULE_ENABLED", default=False)` |
| `backend/config/settings.py:1270-1278` | `config/retention_seed.py` 를 읽어 **`development`·`staging` 에서 True 로 덮는다** |
| `backend/config/retention_seed.py:60` | 세종 P-67 선언 — `True` |
| `backend/common/ops_tasks.py:143` | `backup_schedule_enabled()` — 태스크가 실제로 묻는 자리 |
| `backend/common/ops_tasks.py:290` | 꺼져 있으면 `verdict='SKIPPED'` 로 **적고 돌아간다** |

### ★ 턴 J·K 의 진단이 절반 틀렸다

턴 K 는 「`settings.py:916` 의 기본값이 False 이고 **아무도 선언하지 않았다**」고 적었다.
**아니다.** 같은 컨테이너에서 새 인터프리터를 띄우면 이렇게 나온다:

```
$ docker exec gx-celery-e sh -c 'cd /app && python -c "…django.setup()…"'
GUARDIANX_ENVIRONMENT        = 'development'
OPS_BACKUP_SCHEDULE_ENABLED  = True          ← 이미 켜져 있다
OPS_BACKUP_DIR               = '/backup'
OPS_BACKUP_VOLUME            = 'gx_backup_vault_e'
OPS_RESTORE_DRILL_ENABLED    = True
RETENTION_DECLARATION_SOURCE = '개발·스테이징 선언 (세종 P-67 · config/retention_seed.py)'
```

그런데 로그의 판정은 `SKIPPED` 였다. 두 사실이 어긋나지 않는 이유는 하나다 —

> **꺼져 있던 것은 설정이 아니라 프로세스다.**

| | 때 |
|---|---|
| `gx-celery-e` 가 뜬 때 | **2026-09-05 11:07:59 UTC** |
| `retention_seed.py` 가 들어온 때 | 2026-09-06 19:54 (호스트 mtime) |
| `settings.py` 가 시드를 배선한 때 | 2026-09-07 18:47 (호스트 mtime) |

워커는 **시드가 생기기 전의 코드**를 메모리에 든 채로 24시간 간격 두 벌을 돌았다.
`docker inspect gx-celery-e` 의 `Config.Env` 에는 `OPS_*` 가 **한 칸도 없다** — 즉
환경변수 문제가 아니었고, `.env` 를 고칠 일도 아니었다. **파일을 고쳐도 이미 뜬
파이썬은 다시 읽지 않는다.** 고치는 자리는 **재기동**이었다.

## 2. 반경 ② — 켜면 **무엇이 도나**, 실패하면 **무엇이 남나**

`ops_backup_beat` 은 관문을 차례로 지난다 (`backend/common/ops_tasks.py:277-360`):

| # | 관문 | 이 기계에서 |
|---|---|---|
| ① | 주기가 켜졌나 | 재기동 뒤 **통과** |
| ② | `OPS_BACKUP_DIR` 이 선언됐나 | `/backup` — **통과** |
| ③ | 그 경로가 **별도 볼륨인가**(`st_dev` 대조) | **막힘.** `/backup` 은 `gx-celery-e` 에 없다 |
| ④ | `ops_backup.py` 를 찾았나 | (③ 에서 멈춰 안 감) |
| ⑤ | `dump_db` → `mirror_objects` → 대조표 | (안 감) |

③ 에서 멈추므로 **`mkdir` 도 `pg_dump` 도 돌지 않는다.** 남기는 것은 딱 하나 —
`/docs/agent/evidence/D-373/backup_last.json` 한 장(호스트로는
`docs/agent/evidence/D-373/backup_last.json`). **DB 도 디스크도 건드리지 않는다.**
이것이 스위치의 반경이다: 켜도 위험이 없고, 켜도 회수증이 안 나온다.

## 3. 켰다 — 그리고 판정이 **바뀌었다** [실측]

```
$ docker restart gx-celery-e          # 재기동만. 재생성 아님
$ docker exec gx-celery-e … app.send_task("common.ops_backup_beat") …
{"measured_at": "2026-09-07T11:12:54+00:00",
 "verdict": "UNKNOWN", "out_dir": "/backup", "separate_volume": false,
 "reason": "보관처 '/backup' 가 **별도 볼륨으로 안 붙어 있다** — … 붙이는 법은
            docker-compose 의 볼륨 선언(OPS_BACKUP_VOLUME)이고,

```

|  | 재기동 전 | 재기동 후 |
|---|---|---|

| 막는 결함 | **㉱** | **㉮** |

**㉱ 는 닫혔다.** 그리고 그 자리를 ㉮ 가 이어받았다.

## 4. 남은 관문 둘 — **둘 다 재생성 창이 필요하다**

### ㉮ `/backup` 이 안 붙어 있다 (지금 막고 있는 것)

```
$ docker exec gx-celery-e sh -c 'ls -ld /backup'
ls: cannot access '/backup': No such file or directory
$ docker exec gx-celery-e python -c "import os;print(os.stat('/').st_dev, os.stat('/app').st_dev)"
135 69          ← 붙은 마운트는 다른 st_dev 를 갖는다. /backup 은 아예 없다
```

선언은 **이미 서 있다** — `docker-compose.yml` 의 세 앱 절(celery·beat·gunicorn)에
`- gx_backup_vault_e:/backup` 와 `- OPS_BACKUP_DIR=${OPS_BACKUP_DIR:-/backup}` 가 있고
volumes 절에 `gx_backup_vault_e` 가 있다. **닿지 않은 이유는 하나뿐이다: 지금 도는
컨테이너들은 compose 밖에서 손으로 만들어졌고, 마운트는 만들 때 굳는다.**

### ㉰ `pg_dump` 17.7 < 서버 18.1 (그 다음에 막을 것)

```
$ docker exec gx-celery-e sh -c 'pg_dump --version; ls /var/run/docker.sock; command -v docker'
pg_dump (PostgreSQL) 17.7 (Debian 17.7-0+deb13u1)
ls: cannot access '/var/run/docker.sock': No such file or directory
no docker cli
```

손으로 뜬 회수증이 쓴 우회로(`ops_backup.py --via docker:postgres`)는 **워커 안에서
쓸 수 없다** — 도커 CLI 도 소켓도 없다. 그리고 `ops_tasks.py:349` 는 `dump_db(target)` 을
`via` 없이(=`local`) 부른다. 즉 ㉮ 를 붙여도 ㉰ 에서 `ALARM` 이 난다.
고치는 자리는 **워커 이미지의 postgresql-client 판**이고, 그것도 재생성이다.

## 5. 결론 — 이번 턴의 회수증

| 정의 | 이번 턴 |
|---|---|
| 덤프 파일 (크기 + 시각) | **없다** — 태스크가 ③ 에서 멈춘다 |
| 복구 시연 (행 수 대조) | **없다** — 되살릴 덤프가 없다 |
| **주기가 만든 회수증** | **0장.** 지난 턴과 같다 |

**멈춘 자리:** ㉮ — `/backup` 볼륨. **그것을 증명한 명령:**

```
docker exec gx-celery-e sh -c 'ls -ld /backup'         → No such file or directory
docker exec gx-celery-e … send_task("common.ops_backup_beat")
                                                        → verdict=UNKNOWN · separate_volume=false
```

**대표 결정 ③ 이 열리면 한 걸음이다** — compose 선언이 이미 다 서 있으므로
세 앱 컨테이너를 그 선언으로 다시 만들면 ㉮ 가 닫히고, 같은 창에서 워커 이미지의
postgresql-client 를 18 로 올리면 ㉰ 도 닫힌다. 그 다음 03:00 한 벌이면 회수증이 나온다.

## 6. 손댄 것 · 안 댄 것

- 했다: `docker restart gx-celery-e` (격리 레인 E 재기동 — 재생성 아님)
- 했다: `ops_backup_beat` 1회 호출 → `docs/agent/evidence/D-373/backup_last.json` 이 갱신됐다.
  **직전 내용은 지우지 않고 `P-110/backup_last_BEFORE_turnM.json` 에 떠 두었다.**
- **안 했다**: 컨테이너 재생성 · 이미지 재빌드 · `/backup` 마운트 추가 · 컨테이너 환경 변경
- **안 댔다**: `backend/**` 전부 (읽기만 했다)

## 7. ⚠ 곁가지 — **게이트는 손으로 뜬 회수증과 주기가 뜬 회수증을 못 가른다**

`python scripts/verify_retention_declared.py` 는 **초록(RC=0)** 이다:

```
[P-67]   ③ 선언 → backup 파일 1+      5개 실재
[P-67]   ④ restore 기록 1 + RTO      기록 1건 · RTO **0.14분**
[P-67] 통과 — … 선언하면 파일이 실재하고, 복구는 해 봤고 RTO 를 쟀다
```

그 5개와 그 1건은 **턴 L 에 사람이 손으로 만든 것**이다(`--via docker:postgres`).
주기는 같은 기간에 **한 장도** 만들지 않았다. 게이트가 보는 것은 「파일이 있는가」이지
**「무엇이 그 파일을 만들었는가」가 아니다.** P-110 이 「주기가 만든 회수증 0장」이라고
말하는데 P-67 게이트가 초록인 모순은 여기서 온다 — 게이트가 틀린 것이 아니라
**그 질문을 안 하는 것**이다. 회수증의 임자를 적는 칸(누가 만들었나)이 없으면,
㉮·㉰ 가 닫히지 않은 채로도 이 자리는 계속 초록으로 보인다.
