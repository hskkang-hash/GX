## 3. ★ 확인된 누출 1건 — `flight_log.FlightLog` (D-266 대상)

### 3-1. 어떻게 드러났나

시험이 상세에 **500** 을 받았다. 500 은 `(403, 404)` 가 아니므로 실패로 기록된다 — 맞다.
그러나 500 에는 성격이 다른 둘이 섞인다:

- **(가) 막혔다** — 조회가 안 됐고 그 뒤 처리가 죽었다 → 격리는 서 있다
- **(나) 찾았다** — 남의 레코드를 꺼낸 뒤 다른 데이터가 없어 죽었다 → **격리가 없다**

**둘을 구별하지 않고 "500 이니 안전하다"고 읽는 것**이 이 저장소가 반복해 만난 실패 모양이다.
그래서 읽기 전용 프로브로 갈랐다 (`probe_flightlog_lookup.py`).

### 3-2. 실측

```
flight_log.FlightLog 전체 308행 · 소속 group 6종 (204 / 80 / 15 / 3 / 3 / 3)
핸들러의 조회 = FlightLog._base_manager.get(id=id)
  (flight_log/services/flight_log_service.py :: get_flight_log_detail)

_base_manager.get(id=253) → group_id=7 · 조회 성공
_base_manager.get(id=19)  → group_id=8 · 조회 성공
_base_manager.get(id=258) → group_id=6 · 조회 성공
```

**서로 다른 테넌트 3건을 같은 조회 한 줄로 전부 꺼냈다.**
그 조회에는 **요청자도 테넌트도 인자로 들어오지 않는다.**
→ (나)다. 500 은 "막혔다"가 아니라 **"찾은 뒤 다른 데서 죽었다"** 였다.

### 3-3. 번지는 범위

같은 서비스 함수를 **`download-log/{id}` 도 부른다** — 그쪽은 죽지 않고
비행 로그 전문을 **파일로 내려준다.** 상세보다 이쪽이 더 크다.

### 3-4. 조치 — W0-14c 1차의 문지기 패턴

`assert_scoped(FlightLog, id, request.user)` 를 상세·다운로드·삭제 **3곳**에 부착.

```python
def get_flight_log_detail(self, request, id: int):
    # ★ 문지기는 try 밖이다 (W0-14c 1차의 교훈).
    #   아래 except 가 모든 예외를 삼켜 BaseResponse 로 바꾸므로,
    #   try 안에 두면 Http404 도 삼켜져 아무것도 막지 못한다.
    assert_scoped(FlightLog, id, request.user)
    try:
        ...
```

**결과: 상세 500 → 404 · 삭제 400 → 404.**

## 4. `surveillance.VideoAnalysis` — 누출은 아니었다. 계약이 틀렸다

상세에 **400** 이 나왔다. 로그를 보니 `VideoAnalysis matching query does not exist` —
**매니저가 실제로 걸렀다.** 즉 데이터는 새지 않았고, 상태코드가 틀린 것이다.

그래도 고쳤다. 두 가지 이유다:

1. **400 은 존재 여부에 대해 다른 말을 한다.** 404 규약은 "남의 것은 없는 것과 같아야 한다"이고,
   400("요청이 틀렸다")은 그 규약을 지키지 않는다.
2. **우연한 차단에 기대지 않는다.** 지금 막고 있는 것은 dj-core 매니저의 필터인데,
   그 필터에는 `created_by__isnull=True` OR 절이 있다(§0.4 라 고칠 수 없다) —
   **소유가 빈 행에서는 걸러 주지 못한다.** W0-13 백필이 25,296행의 `group_id` 를 채운 것이
   바로 그 구멍을 좁히는 일이었고, 그래도 남는 행이 있다(`tenant_unassigned` 1,590).

같은 문지기를 상세·다운로드 2곳에 부착 → **400 → 404.**

## 5. 시험 자체의 결함 3건 — 배선만 고쳤다 (단언 무변경)

D-253 의 선례를 따랐다: **판정은 건드리지 않고 부르는 곳만** 고쳤다.

### 5-1. 픽스처가 남의 것을 못 만들고 있었다 (가장 큰 것)

`_create_for` 는 `groups` M2M 이 있을 때만 소유자를 붙였다. dj-core 의
`BaseModelWithGroup` 계열(= P0 15종 전부)은 **`group` FK(단수)** 를 쓰므로
**소유자가 붙지 않은 채** 시험 대상이 됐다.

소유가 틀리면 이 시험은 격리가 아니라 **자기 자신을 재게 된다** —
D-253 2차 정정이 잡은 오염이 정확히 그 모양이었다.

**처분**: `group` FK 를 명시적으로 세우고, **픽스처가 스스로 증명하게 했다** —
`_assert_owned_by` 가 "내가 만든 것이 정말 그 테넌트 소유인가"를 매번 단언한다.

### 5-2. 그 단언이 곧바로 두 번째 결함을 잡았다

붙이자마자 `Dashboard` 가 **`groups = set()`** 으로 나왔다. 붙였는데 없다?
읽는 쪽이 문제였다 — `obj.groups.values_list(...)` 는 `UserGroup` 의 테넌트 필터를 타므로
**사용자 문맥이 없는 자리에서는 붙어 있는데도 빈 집합**을 돌려준다.

**처분**: 연결 테이블을 `_base_manager` 로 직접 읽는다.
D-253 이 삭제 판정을 `_base_manager` 로 옮긴 것과 **같은 이유, 같은 함정**이다.

### 5-3. 앞의 실패가 뒤의 전부를 가리고 있었다

`orders.Order` 상세가 미포착 예외(`DoesNotExist`)로 죽으면서 **그 뒤 대상들이 호출조차
되지 않았다.** 그 상태의 "실패 1건"은 실제로는 **"1건 실패 + N건 미측정"**이다.
FlightLog·VideoAnalysis 를 등재하고도 판정됐는지 알 수 없었다.

**처분 둘**:
- 예외를 **500 응답으로 바꿔 기록**한다. 500 은 `(403,404)` 가 아니므로 단언은 그대로
  실패한다 — 판정이 느슨해지지 않고, 뒤의 대상이 판정된다.
- 시나리오마다 **대상별 표**를 출력하고 새는 것 전부를 한 번에 단언한다.

```
[ISO] detail — 대상 7건
  LEAK Order              500  Order matching query does not exist.
  OK   Terminal           404
  OK   Device             404
  OK   SurveillanceProfile 404
  OK   ReportTemplate     404
  OK   FlightLog          404      ← 이번에 고친 것
  OK   VideoAnalysis      404      ← 이번에 고친 것
```

**미측정을 통과로 읽지 않는 것** — 이 표가 그것을 구조적으로 막는다.

총합만 보면 한 모델의 증가가 다른 모델의 감소 뒤에 숨고, 그때 "줄었다"는 보고가 나온다.

## 10. ★ 새로 드러난 물음 — P0 의 "라우트가 닿는다"가 두 뜻이다

`leak_targets_coverage.md` §7-2 는 P0 를 "**pk 를 지목하는 경로가 닿고** 행 50+"로 정의했다.
그런데 실경로를 대조하니 여러 종에 그런 경로가 없다:

- `surveillance.MissionWaypoint`(8,877행) — `waypoint` 를 포함하는 라우트 **0개**
- `orders.OrderHistory`(5,882) · `orders.OrderItem` — 직접 경로 없음
- `terminals.RouteTerminal`(2,062) — 초안이 지목한 `export-single-plan/{route_id}` 는
  **`Routes` 의 id** 이지 RouteTerminal 의 pk 가 아니다

이것은 모순이 아니라 **정의가 두 뜻으로 쓰인 것**이다 — `map_routes_to_models.py` 의
"닿는다"는 *핸들러가 그 모델을 만진다*(부모 경로를 통해)는 뜻이고,
격리 시험의 5시나리오는 *pk 로 그 레코드를 지목한다*를 전제한다.

**부모를 통해 자식이 새는 것**은 실재하는 위험이고 재야 한다. 다만 `detail/update/delete`
칸으로는 잴 수 없다 — 재려면 "부모 경로를 부르고 **응답 본문에 남의 자식 pk 가 없는지**"를
보는 시나리오가 필요하다(지금 `export` 가 그 모양이다).

이것을 어떻게 셀지가 **P0 13종의 등재 방식을 정한다.** 임의로 정하지 않고 **P-W0-14-5** 로 적재했다.
