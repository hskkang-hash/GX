# OPS-13b · P-101 — **앞단의 재시도가 두 번에서 멈춘다**를 고쳤다 (그리고 다른 결함 하나를 새로 봤다)

> 2026-09-07 · 턴 K · 차선 E(운영·영역 ④) · 격리 차선 `gx_e`(`gx-nginx-e` 8500 / `gx-gunicorn-e`)
> 부하 도구는 **하나뿐이다** — `scripts/verify_perf_budget.py --measure --rounds 30`.
> 새 부하 도구를 만들지 않았다(표가 둘이면 다음 사람이 어느 표를 볼지 모른다 · OPS-13a §0).

## 0. 이번 턴의 한 줄

> **고친 결함은 닫혔다(11건 → 0건). 그런데 502 는 0 이 아니다 — 남은 4건은 다른 모양이다.**
> 종전 502 는 **전수**가 「세 번째 시도가 `gx_app` 로 새고 0.000초에 끝나는」 모양이었다.
> 고친 뒤 그 모양은 11,166 요청에서 **0건**이다. 남은 4건은 **시도를 한 번밖에 안 한** 것이고,
> 그것은 이 절이 고친 결함이 아니라 **아직 이름 없는 다른 결함**이다. 묻지 않고 §4 에 세운다.

## 1. 무엇을 고쳤나 — 한 줄

```diff
 upstream gx_app {
-    server gx-gunicorn-e:8000 max_fails=0;
     server gx-gunicorn-e:8000 max_fails=0;
     keepalive 32;
```

`nginx/gx-front.conf`. 적용은 **reload 뿐**이다(`docker exec gx-nginx-e nginx -s reload -c …`).
컨테이너를 내리지 않았다 — RUNBOOK STEP 2D 가 「`gx-nginx-e` 는 재기동하지 않는다,
필요한 것은 reload 하나」라고 못박은 그대로다.

### ⚠ 지시서가 준 진단 두 줄 중 **한 줄은 사실이 아니었다**

| 진단 | 실측 |
|---|---|
| 같은 서버가 두 줄이다 | **맞다.** 이것이 결함이었다 |
| `proxy_next_upstream_tries` 가 **선언돼 있지 않다** | **아니다.** `nginx/gx-proxy.inc` 에 `proxy_next_upstream_tries 3;` 이 있고, **도는 형상에도 있었다** — `docker exec gx-nginx-e nginx -T \| grep -c proxy_next_upstream_tries` → 2(선언 1 + 주석 1) |

`verify_front_line_502.py` 머리말(P-92 · 턴 J)의 「선언이 없다」는 **틀린 메모**다.
고칠 자리는 하나였고, 그 하나가 `tries 3` 을 **못 쓰게 만들고 있었다.**

## 2. 잰 것 — **A / B / A′ / B′ / B″ 다섯 벌** [실측 2026-09-07 09:39–10:05 UTC]

한 벌 = 면 4종 × 동시 10 × 30라운드 × 3반복 = **3,600 요청**(+워밍업·로그인 122 = 접근로그 3,722줄).
부하는 `max_requests 200` 인 뒷단 위에서 도므로 **워커 재활용 창을 반드시 지난다**
(벌마다 `Worker exiting` 11~24건 관측). 즉 「재기동 창을 지나는 3,600 요청」이 그대로 성립한다.

| 벌 | 형상 | 접근로그 | **502** | 재시도 | 되살림 | 판정기 exit |
|---|---|---|---|---|---|---|
| **A** | peer **2** (종전) | 3,722 | **3** | 37 | 34 | 0 |
| **B** | peer **1** (고침) | 3,722 | **0** | 30 | 30 | 2 (502 가 없어 ②③이 회색) |
| **A′** | peer **2** (되돌림 · 대조) | 3,722 | **8** | 27 | 19 | 1 |
| **B′** | peer **1** (다시 고침) | 3,722 | **2** | 34 | 34 | 0 |
| **B″** | peer **1** (설정 안 건드림 · 세 번째 표본) | 3,722 | **2** | 28 | 28 | 0 |

```
peer 2 합계   11 / 7,444  = 0.148%
peer 1 합계    4 / 11,166 = 0.036%      (4.1배 낮다)
```

★ **A/B/A′ 를 안 쟀으면 이 표를 못 읽는다.** OPS-13a §3 ① 이 못박은 대로 건수는
기계 상태가 좌우한다 — 실제로 같은 peer 2 형상에서 3건과 8건이 나왔다. 그래서 아래
§3 의 **모양**이 이 절의 실제 근거이고, 건수는 그 곁에 둔다.

### 판정기 출력

```
python scripts/verify_front_line_502.py --since-time 09:39:50 --until-time 09:44:13   # A  → exit 0
python scripts/verify_front_line_502.py --since-time 09:44:14 --until-time 09:49:30   # B  → exit 2
python scripts/verify_front_line_502.py --since-time 09:49:31 --until-time 09:53:37   # A′ → exit 1
python scripts/verify_front_line_502.py --since-time 09:53:38 --until-time 09:57:30   # B′ → exit 0
python scripts/verify_front_line_502.py --since-time 10:01:33 --until-time 10:05:05   # B″ → exit 0
```

전문은 `judge_*.md` 다섯 벌. ⚠ **exit 2 는 나빠진 것이 아니다** — 502 가 0건이면
「설명」과 「대조 분리」는 판정할 대상이 없어 회색이 된다(그 갈래가 판정기 자기시험 ⑥에
박혀 있다). **없는 것을 통과로 적지 않는다**는 규약의 결과이지 회귀가 아니다.

## 3. **모양** — 이것이 건수보다 값나간다 [실측]

`$upstream_addr` 의 쉼표 개수를 벌마다 세었다(`raw/*.txt`).

| 형상 | 되살아난 200 의 시도 수 | 502 의 모양 |
|---|---|---|
| peer **2** | **언제나 정확히 2** (A 34건 · A′ 19건 — 3회는 **한 건도 없다**) | 전수가 `addr, addr, gx_app` · 셋째 `0.000` |
| peer **1** | 2 (50건) · **3 (7건)** · **4 (1건)** | `addr` **하나** (4건) |

즉 실측으로 확인된 것:

- **두 줄로 적으면 실효 시도가 2에서 멈춘다.** `proxy_next_upstream_tries 3` 이 선언돼
  있어도 3회째 시도는 **peer 를 못 얻어** `gx_app`(upstream **이름**) · `0.000`초로 샌다.
  종전 502 **11건 전수**가 이 모양이었다.
- **한 줄로 적으면 3회째가 실제로 간다** — 되살아난 200 중 7건이 3회, 1건이 4회 시도였다.
  그리고 `gx_app 0.000` 은 11,166 요청에서 **0건**이다. **이 결함은 닫혔다.**

## 4. ⛔ 남은 502 4건은 **다른 결함**이다 — 이름을 세운다

```
172.18.0.4 [07/Sep/2026:09:53:49] "GET /api/dsm/events?limit=50…" 502 150 0.004 "172.18.0.6:8000" 0.004
172.18.0.4 [07/Sep/2026:09:54:34] "GET /api/dsm/dashboard/link-state…" 502 150 0.001 "172.18.0.6:8000" 0.000
172.18.0.4 [07/Sep/2026:10:01:56] "GET /api/dsm/events/summary…"       502 150 0.000 "172.18.0.6:8000" 0.001
172.18.0.4 [07/Sep/2026:10:04:14] "GET /api/dsm/events?limit=50…"      502 150 0.004 "172.18.0.6:8000" 0.004
```

`$upstream_addr` 이 **하나**다 — 앞단이 재시도를 **한 번도 안 했다.** 앞단 오류로그의 사유는
같은 부하에서 수백 번 나고 **대부분 되살아나는** 바로 그 사유다:

```
recv() failed (104: Connection reset by peer) while reading response header from upstream
```

즉 **같은 사유가 어떤 때는 재시도되고 어떤 때는 안 된다.** 왜 갈리는지 이 턴에는 못 쟀다.

> **회색이다. 고치지 않았다.** 이 자리에서 손댈 만한 손잡이는 `non_idempotent` 인데
> 그것은 OPS-13a §3 ④ 가 **수를 들고** 금지한 것이다(재시도 113건 중 104건이 쓰기였다면
> 중복 전송 · 재난 경보를 두 번 보낸다). 한 벌 재고 손잡이를 당기면 턴 C 의
> 「고치려다 나빠졌다」를 되풀이한다.
>
> 다음 사람이 볼 자리: **왜 어떤 reset 은 `proxy_next_upstream` 을 안 타는가.**
> `error_log … debug` 한 벌이면 갈릴 것이다(지금은 `notice`).

## 5. ★ 판정기에 있던 결함 하나 — **`--since-line` 은 도는 로그 위에서 미끄러진다** (이번 턴에 물렸다)

앞단은 접근로그를 `/dev/stdout` 으로 낸다(OPS-07). 그래서 판정기는 `docker logs` 를 읽고,
그 로그는 `json-file` **회전**(`max-size=10m max-file=5`)을 받는다. 회전이 앞머리를 버리면
**줄 번호가 통째로 앞으로 당겨진다.**

[실측 2026-09-07] 같은 부하 한 벌(B′)을

| 자 | 읽은 줄 | 502 |
|---|---|---|
| `--since-line 25075` (부하 직전의 줄 수) | 3,760 | **0건** |
| `--since-time 09:53:38` | 3,722 | **2건** |

**회전이 502 2건을 창 밖으로 밀어냈다.** 하마터면 이 문서에 「502 0건」을 적을 뻔했고,
그 0 은 고쳐서 난 0 이 아니라 **못 본 0** 이다.

그래서 `--since-time` / `--until-time` 을 넣었다(시각은 회전과 무관하다). `--since-line` 은
옛 증거를 되읽으려고 남기되 **쓰면 경고를 낸다.** 자기시험에 갈래 5개(양성 2 · 음성 3)를 박았다.

⚠ 이 절의 표 §2 는 **전부 시각 창으로 다시 잰 수**다. 줄 번호로 잰 첫 판의 파일들은
지웠다 — 남기면 다음 사람이 그 수를 인용한다.

## 6. 이 절이 **닫혔는가** — 정직하게

| 물음 | 답 |
|---|---|
| 「세 번째 시도가 낭비된다」가 고쳐졌는가 | **예** — 11,166 요청에서 `gx_app 0.000` **0건** |
| 502 가 줄었는가 | **예** — 0.148% → 0.036% (peer2 7,444 · peer1 11,166) |
| **502 = 0건인가** | **아니다.** 세 벌 중 **한 벌(B)만 0** 이고 두 벌은 2건이다 |
| 그 남은 건은 이 결함인가 | **아니다** — 모양이 다르다(§4). 알려진 창에 묻지 않는다 |
| SLA 5xx 예산(0.1%)은 | peer1 세 벌 **0.000% · 0.056% · 0.083% — 모두 예산 안**. peer2 두 벌은 0.111% · 0.194% 로 **빨강**이었다 |

**주 서버(main)는 건드리지 않았다.** 이 저장소에서 `upstream gx_app` 을 가진 형상은
`nginx/gx-front.conf` **하나뿐**이고, 그것을 읽는 컨테이너는 `gx-nginx-e` 하나다
(`nginx/nginx.conf` = 스테이징 형상에는 `upstream` 블록 자체가 없다). 즉 격리 차선의
이 한 줄이 곧 그 형상의 전부이며, 옮겨 붙일 두 번째 자리가 없다.

## 6. 턴 M 재확인 — **수가 그대로 선다** [실측 2026-09-07 11:16:56–11:19:27 UTC]

지시 「이 수가 아직 서는지 다시 재라」에 답한다. **같은 도구 · 같은 부하 · 손대지 않은
peer 1 형상**으로 한 벌 더 쟀다(B‴).

먼저 도는 형상을 확인했다 — 파일이 아니라 **도는 것**을 봤다:

```
$ docker exec gx-nginx-e sh -c 'cat /proc/1/cmdline | tr "\0" " "'
nginx: master process nginx -c /etc/nginx/gx/gx-front.conf -g daemon off;
$ docker exec gx-nginx-e nginx -T -c /etc/nginx/gx/gx-front.conf | grep -E "server gx-gunicorn|proxy_next_upstream"
    server gx-gunicorn-e:8000 max_fails=0;          ← **한 줄** (peer 1)
proxy_next_upstream error timeout http_502;
proxy_next_upstream_tries 3;
proxy_next_upstream_timeout 15s;
```

⚠ `nginx -T` 를 **`-c` 없이** 부르면 이 컨테이너의 재고 `conf.d/default.conf` 를 떠서
`upstream gx_app` 이 **0건**으로 나온다. 「선언이 없다」로 읽힐 자리다 — `-c` 를 붙여라.
그리고 `non_idempotent` 는 **여전히 없다**(OPS-13a §3 ④ 를 지켰다).

| 벌 | 형상 | 요청 | **502** | 재시도 | 되살림 | 샌 `gx_app` |
|---|---|---|---|---|---|---|
| **B‴ (턴 M 재확인)** | peer **1** · 손 안 댐 | 3,722 | **1** | 29 | 29 | 0 |

```
peer 2 (전) 합계   11 / 7,444  = 0.148%
peer 1 (후) 합계    5 / 14,888 = 0.034%      ← B‴ 를 더한 수
gx_app 0.000 결함              0 / 14,888    ← 여전히 0
```

판정기: `python scripts/verify_front_line_502.py --since-time 11:16:56 --until-time 11:19:27`
→ **exit 0** · 전문 `judge_B4_reverify_peer1.md`.

### 그 1건도 **§4 의 모양 그대로다**

```
172.18.0.4 [07/Sep/2026:11:18:01] "GET /api/dsm/events/summary…" 502 150 0.001 "172.18.0.6:8000" 0.001
```

`$upstream_addr` 이 **하나** — 다시, 앞단이 재시도를 **한 번도 안 했다.** 그런데 같은 창의
앞단 오류로그에는 `recv() failed (104: Connection reset by peer)` 가 **30건** 있고
그 중 29건은 되살아났다. **같은 사유가 29번은 재시도되고 1번은 안 된다.**
§4 가 세운 결함이 우연이 아님을 세 번째 표본이 다시 말한다.

## 7. OPS-13b 는 **닫히지 않는다**

| 무엇 | 판정 |
|---|---|
| `gx_app 0.000` 삼킴 (이 절이 표적으로 삼은 결함) | **닫혔다** — 11/11 → **0 / 14,888** |
| 502 율 | 0.148% → **0.034%** (4.4배 낮다) |
| **닫힘 조건 「모든 벌에서 502 = 0」** | **못 채웠다** — 후속 네 벌이 0 · 2 · 2 · **1** |

그래서 이 절은 **열어 둔다.** 남은 502 는 고친 결함의 잔량이 아니라 §4 가 이름을 세운
**다른 결함**(재시도가 아예 안 일어난다)이고, 그것을 「같은 결함이 조금 남았다」로 적으면
다음 사람이 엉뚱한 자리를 판다.
