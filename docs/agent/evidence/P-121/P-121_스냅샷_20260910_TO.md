## 1. 원인 — 한 칸

`services/API.ts` 는 rj-core 의 `createApiClient()` 로 axios 를 만든다.
그 안의 응답 인터셉터를 **빌드가 실제로 쓰는 파일**에서 읽었다
(`gx-fe-build:/app/node_modules/rj-core/dist/rj-core.es.js`):

```js
interceptors.response.use(
  (i) => { … ; return i.data; },      // ← ★ 봉투가 아니라 **본문**을 돌려준다
  async (i) => { …401 재발급… }
)
```

그래서 `API.get(url, {responseType:'blob'})` 이 돌려주는 것은 `AxiosResponse` 가
아니라 **Blob 자체**다. 그런데 `fetchSnapshotUrl()` 은 이렇게 읽고 있었다:

```ts
const status = res?.status ?? 0;      // Blob 에는 status 가 없다 → 0 → 검사 통과
const url = URL.createObjectURL(res.data as Blob);   // Blob 에는 .data 가 없다 → undefined
```

`URL.createObjectURL(undefined)` 은 **TypeError** 를 던진다. 그 던짐은 async 함수
안에서 나므로 **콘솔에 한 줄도 안 남고**(실측: 콘솔에 `createObjectURL`·`TypeError`
문자열 0건), 부르는 쪽 `.catch` 가 삼켜 화면에 「사진을 불러오지 못했습니다」를 띄운다.

> **서버가 200 으로 37KB 를 보낸 화면에 「불러오지 못했습니다」가 떠 있었다.**
> 거짓 사유는 없는 사유보다 나쁘다 — 사람이 저장소를 보러 간다.

`dsmGet()` 이 멀쩡했던 이유는 `unwrap()` 이 `res?.data ?? res` 로 **두 모양을 다 받기**
때문이다. 그 관용이 이 한 함수에만 없었다.

모바일은 아예 부르지도 않았다. 화면에는 이렇게 적혀 있었다:

> 「휴대전화 화면에서 여는 길이 아직 열리지 않았습니다 — 관제 화면에서 확인하십시오.」

두 문장 다 거짓이었다. 길(`GET …/snapshot`)은 P-25 로 이미 열려 있었고,
**관제 화면도 같은 이유로 사진을 못 그리고 있었다.** 고장 하나를 가리키며
다른 고장으로 사람을 보내는 표지판이었다.

## 2. 무엇을 고쳤나

| 파일 | 고친 것 |
|---|---|
| `features/dsm/api.ts` | `pickBlob()` — Blob 이든 봉투든 **모양을 가정하지 않는다**. 0바이트·모양 불명은 조용히 빈 그림을 그리지 않고 던진다. 실패는 **거절 갈래**에서 `err.response.status` 로 읽는다(성공 갈래에 상태가 없으므로). 오류 본문이 Blob 으로 와도 사유 한 줄을 꺼낸다. |
| `features/dsm/components/EventSnapshot.tsx` | 문장을 **셋으로 가른다**: 503 저장소 / 그 밖 4xx·5xx 「사진을 불러오지 못했습니다」 / 상태 0 「연결이 끊겼습니다」. 「다시 시도」는 `<a onClick>` → **`<Button>`**. `compact` 로 손바닥 화면에서 높이를 놓아 준다. |
| `features/mobile/pages/MobileEventDetail.tsx` | 거짓 안내 **삭제**. 그 자리에 관제 화면과 **같은 부품** `EventSnapshot` 을 세웠다. 객체 키는 버리지 않고 「참조 보기」 아래로 접었다. |

| 화면 | | XHR | 바이트 | 그려진 픽셀 | 「불러오지 못했습니다」 | 거짓 안내 |

| 데스크톱 상세 `/dsm/events/4798` | 전 | 200 | 37,472 | **없음** | **떠 있다(거짓)** | — |
| | 후 | 200 | 37,477 | **640×360** | 없다 | — |

| | 후 | 200 | 37,632 | **640×360** | 없다 | — |

바이트가 호출마다 몇 십 바이트씩 다른 것은 정상이다 — 나가는 그림에 **열람 시각**이
소인으로 찍힌다.

### 「다시 시도」가 실제로 요청을 내는가

강제 500 화면에서 단추를 누르고 **요청 수를 세었다**:

```
전 : 누르기 전 1건 → 누른 뒤 2건   (요청 나감)
후 : 누르기 전 1건 → 누른 뒤 2건   (요청 나감 · 이제 <Button> 이라 키보드로도 눌린다)
```

⚠ **청에 적힌 「오늘 이 단추는 요청을 하나도 내지 않는다」는 재현되지 않았다.**
지금 서는 번들에서는 **전에도** 요청이 나갔다(`nonce` 가 effect 의 인자라서다).
고친 것은 「요청을 내게 만든 것」이 아니라 **누를 것의 모양**(앵커 → 단추 ·
키보드 초점)이다. 안 재현된 것을 재현했다고 적지 않는다.

### 정상 화면에서 「다시 시도」가 없는 것이 정답이다

후 측정의 데스크톱 상세·모바일 상세에서 `retry.found = false` 인 것은 결함이 아니라
**사진이 떠서 오류 상자 자체가 없기 때문**이다(같은 줄의 `drawn=True` 가 그것을 말한다).
