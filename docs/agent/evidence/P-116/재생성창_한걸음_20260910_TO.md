## ⓪ 재기동 정책 — **세 아침 연속 멈춰 있었다** 〈가장 먼저〉

### 사실 — 일화가 아니라 자료점 셋

Docker Desktop 이 **09-07 · 09-08 · 오늘 09-10** 세 아침 모두 멈춰 있었다. 그때마다
넷은 스스로 돌아왔고 **여섯은 안 돌아왔다 — 재기동 정책이 없기 때문이다.**
매 아침이 `docker start` × 6 으로 시작한다. 일이 시작되기 전에 사람이 여섯 번 손을 쓴다.

**[실측 2026-09-10 · `docker inspect .HostConfig.RestartPolicy`]**

| 컨테이너 | 지금 정책 | 아침마다 손이 가나 | 무엇이 멈추나 |
|---|---|---|---|
| **`postgres`** | **`no`** | **간다** | **데이터베이스 전부** |
| **`redis`** | **`no`** | **간다** | 큐 · 캐시 · 세션 |
| **`gx-gunicorn-e`** | **`no`** | **간다** | API (앞단의 유일한 peer) |
| **`gx-nginx-e`** | **`no`** | **간다** | 앞단 8500 |
| **`gx-shell`** | **`no`** | **간다** | 게이트가 때리는 서버 · SPA 3002 |
| **`gx-fe-build`** | **`no`** | **간다** | 프런트 빌드 |
| `gx-celery-e` | `unless-stopped` | 안 간다 | — |
| `gx-beat-e` | `unless-stopped` | 안 간다 | — |
| `guardianx-source-minio-1` | `unless-stopped` | 안 간다 | — |
| `guardianx-source-mailpit-1` | `unless-stopped` | 안 간다 | — |

★ **`postgres` 가 재기동 정책 없이 도는 것은 백업 논의보다 큰 사실이다.**
  백업은 「잃었을 때 얼마나 되돌리나」를 말하고, 이 줄은 「아무도 안 볼 때 그냥 안 뜬다」를 말한다.
  뒤의 것이 먼저다 — 세 번 일어났고, 세 번 다 사람이 알아채서 손으로 살렸다.
  **네 번째 아침에 아무도 안 볼 수 있다.**

### ⚠ 이 한 칸만은 **재생성 창을 안 기다려도 된다**

여섯은 전부 `docker run` 으로 만들어졌다 — 컴포즈가 안 쥐고 있다
(**[실측]** `com.docker.compose.service` 라벨이 여섯 다 **비어 있다**).
그런데 재기동 정책은 **컨테이너를 다시 만들지 않고** 바꿀 수 있다:

    docker update --restart=unless-stopped <이름> …          # 여섯

- **멈춤 없다** — 도는 컨테이너를 안 건드린다. 프로세스도 안 죽는다.
- **재생성이 아니다** — 마운트도 환경변수도 이미지도 그대로다.
- 그래서 ㉠~㉲ 와 **묶지 않아도 된다.** 창이 열리기를 기다릴 이유가 이 칸에는 없다.

★ 그러나 차선 E 의 이번 턴 권한 밖이다(「컨테이너 환경을 바꾸지 마라」).
  **승인만 나면 초 단위로 끝난다** — 이 문장이 이 절의 요점이다.

### 뒤이어 — 창이 열릴 때 같이

컴포즈 선언에는 `restart: unless-stopped` 가 **이미 서 있다**(`docker-compose.yml`).
㉠~㉱ 로 컨테이너를 다시 만드는 순간 정책은 선언에서 따라온다.
그러니 `docker update` 는 **창까지의 다리**이지 창의 대체물이 아니다.

## ㉠ `gx-shell` 의 MinIO 자격증명 — **마운트된 파일로는 못 고친다**

**[재실측 2026-09-10 · 값은 안 적는다 · 길이와 sha256 앞 12자로만 대조]**

| 자리 | `MINIO_ENDPOINT` | `MINIO_ACCESS_KEY` | `MINIO_SECRET_KEY` |
|---|---|---|---|
| `gx-gunicorn-e` | 서비스 이름`:9000` | **진짜** (7자) | **진짜** (28자 · 접근키와 **다른 글자**) |
| **`gx-shell`** | **`*.invalid`** | **자리표** (5자) | **자리표** (5자 · 접근키와 **같은 글자**) |

두 자리표는 **서로 같은 글자다**(sha256 앞 12자 일치). 진짜 자격은 절대 그렇지 않다 —
이것이 「값을 안 보고 자리표를 가리는」 모양이다.

### 왜 파일로는 못 덮는가 — **두 겹으로 확인했다**

1. `settings.py:25` 의 `environ.Env.read_env(BASE_DIR/".env")` 는 **`setdefault`** 다.
   프로세스 환경에 이름이 **이미 있으면** 파일은 비켜선다. `gx-shell` 은 **틀린 값이 있는 것**이지
   없는 것이 아니다.
2. **[실측 2026-09-10]** 그 마운트된 `/app/.env` 에는 `MINIO*` 이름이 **한 칸도 없다.**
   있는 것은 `K2_*` 넷과 `EMAIL_*` 넷뿐이다. 즉 **덮을 파일 자체가 그 이름을 모른다.**

두 겹 다 같은 곳을 가리킨다: 값은 **`docker run --env-file` 이 읽는 파일**에서 온다.
그 파일을 고치고 **컨테이너를 다시 만드는 것**이 유일한 길이다.

### 최소 변경 — 이름 셋 (값 없음)

**자리:** 저장소 뿌리 `.env` (저장소 밖 · `.gitignore` 가 잡는다).

| 이름 | 값의 **모양** |
|---|---|
| `MINIO_ENDPOINT` | `<minio 서비스 이름>:9000` — **스킴 없이** `host:port` |
| `MINIO_ACCESS_KEY` | 같은 파일의 `MINIO_ROOT_USER` **와 같은 글자를 그대로** |
| `MINIO_SECRET_KEY` | 같은 파일의 `MINIO_ROOT_PASSWORD` **와 같은 글자를 그대로** |

이미 맞는 것(안 건드린다): `MINIO_BUCKET_NAME` · `MINIO_USE_HTTPS`(모양 `False`).

⚠ **`--env-file` 은 `${...}` 를 펴 주지 않고 따옴표도 안 벗긴다.**
`MINIO_ACCESS_KEY=${MINIO_ROOT_USER}` 라고 적으면 그 **열여덟 글자가 계정 이름**이 된다.
글자를 그대로 두 번 적는다.

## ㉡ `/backup` 마운트 — **주기가 만든 회수증까지 남은 마지막 관문**

**[실측 2026-09-10]** `gx-celery-e` 안에 `/backup` 이 **없다**
(`ls: cannot access '/backup'`). 도는 컨테이너의 마운트는 넷이고 그중 볼륨은 **하나도 없다**.

| 있는 것 | 없는 것 |
|---|---|
| 볼륨 `gx_backup_vault_e` 는 **이미 만들어져 있다** (`docker volume ls`) | 도는 컨테이너에 **안 붙어 있다** |
| `docker-compose.yml` 에 `gx_backup_vault_e:/backup` 선언 **셋 다 서 있다** | 도는 컨테이너는 그 선언 **이전에** 만들어졌다 |
| `OPS_BACKUP_DIR` 선언도 서 있다 | — |

★ **선언은 다 됐다. 붙이는 일만 남았다.** 마운트는 `docker update` 로 못 바꾼다 —
  **컨테이너를 다시 만들어야만** 붙는다. 이 칸이 재생성 창을 진짜로 필요로 하는 자리다.

**집행:** 세 앱 컨테이너(`gx-gunicorn-e` · `gx-celery-e` · `gx-beat-e`)를
`docker-compose.yml` 의 선언으로 다시 만든다. 새 값은 없다.

## ㉢ 워커의 `pg_dump` — **없는 게 아니라 서버보다 한 세대 낮다**

턴 M 이 짚은 자리이고, 오늘 **실패 회수증을 실제로 떴다.**

**[실측 2026-09-10 · `gx-celery-e` 안에서 `pg_dump --schema-only` 를 실제로 걸었다]**

    pg_dump: error: aborting because of server version mismatch
    pg_dump: detail: server version: 18.1; pg_dump version: 17.7
    rc=1

| 자리 | 세대 |
|---|---|
| `gx-celery-e` 의 `pg_dump`·`psql` | **17.7** — 있긴 **있다** |
| `postgres` 서버 | **18.1** |

★ **「`postgresql-client` 가 없다」가 아니다.** 있고, 서버보다 낮아서 `pg_dump` 가
  **스스로 멈춘다.** 「깔면 된다」로 적으면 다음 사람이 `postgresql-client` 를 깔고
  같은 자리에서 다시 막힌다. 필요한 것은 **`postgresql-client-18` 이상**이다.

⚠ 그리고 **한 줄 더**: `postgres` 이미지가 `latest` 다. 클라이언트를 18 로 올려도
  서버가 19 로 흘러가면 **같은 사고가 그대로 돌아온다.** 같은 창에서
  **서버 이미지 태그를 major 로 고정**하는 것이 이 칸의 진짜 마무리다.

⚠ 우회 불가: `gx-celery-e` 에는 **도커 CLI 도 `/var/run/docker.sock` 도 없다**
  (**[실측 2026-09-10]** 둘 다 없음). 예약 백업은 `ops_tasks.py` 에서 `via` 없이
  `dump_db(target)` 을 부른다 = **`local`**. 손으로 뜬 회수증이 쓴 길은 **사람의 길**이다.

**집행:** 워커 이미지(`backend/Dockerfile`)의 `apt-get install` 줄에
`postgresql-client-18` 을 더하고 **이미지를 다시 굽는다** + `postgres` 태그 고정.

## ㉣ `gx-gunicorn-e` 의 **운영 보안 프로파일** — 지금은 개발 프로파일이다

**[재실측 2026-09-10 · 오늘 재기동 뒤 · 컨테이너 안에서 `django.conf.settings` 로 직접 읽었다]**

| 이름 | 지금 | 운영에서 있어야 할 **모양** |
|---|---|---|
| `DJANGO_SETTINGS_MODULE` | `config.settings` | `config.settings_prod` |
| `GUARDIANX_ENVIRONMENT` | `development` | `production` |
| **`DEBUG`** | **`True`** | **`False`** |
| **`ALLOWED_HOSTS`** | **`['*']`** | 실제 호스트 이름만 (와일드카드 없음) |
| `SESSION_COOKIE_SECURE` | `False` | `True` |
| `CSRF_COOKIE_SECURE` | `False` | `True` |
| `SECURE_HSTS_SECONDS` | `0` | 0 이 아닌 값 |
| `SECURE_SSL_REDIRECT` | `False` | `True` |
| **DB 비밀번호** | **5자** | **20자 이상** |
| `DJANGO_SECRET_KEY` | 33자 · 이름에 `local-bringup-only` 라고 **스스로 적혀 있다** | 금고에서 온 값 |

★ **모양이 갈려 있다** — 프로세스는 운영형(gunicorn · 워커 4 · 스레드 4)인데
  보안 프로파일은 개발형이다. **둘 중 하나를 보고 「운영이다」라고 부를 수 없다.**

★ **DB 비밀번호 5자**는 자리표의 모양이다(`gx-shell` 의 MinIO 자리표와 같은 5자).
  `gx-gunicorn-e` 의 MinIO 자격은 **진짜인데** DB 자격은 **아니다** — 한 컨테이너 안에서
  금고에서 온 것과 안 온 것이 **섞여 있다.** 「자격은 금고에서 온다」는 조건은
  **한 칸이라도 자리표가 있으면 거짓**이다.

**집행:** `--env-file` 이 읽는 파일에서 위 이름들의 값을 운영 모양으로 바꾸고
`gx-gunicorn-e` 를 다시 만든다. ㉠·㉡ 과 **같은 창**이다.
