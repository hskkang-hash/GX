# OPS-07b — DB 감사 로그 보존은 **선언이다. 기본값이 아니다** (P-67 · 2026-09-06 · 차선 E)

> 세종 판정 P-67: 「보존 일수·백업 목적지·일정에 **코드 기본값 없음.**
> 미선언 = 파기·백업 **돌지 않음**. 개발·스테이징 감사 로그 보존 **365일**.」

## 0. 무엇이 거짓이었나 — 지우지 않고 적는다

| | 턴 F 까지 적혀 있던 말 | 실측 |
|---|---|---|
| `config/celery.py:85` | 「보존기간의 답이 제품 안에 이미 있다 (**기본 90일**)」 | **거짓** |
| `common/ops_tasks.py:284` | 「`System > security.audit_log_retention_days` (**기본 90**). 고객이 정한 값이다」 | **거짓** |

[실측 2026-09-06 · 개발 DB · `AdminConfig(name="System", is_active=True)`]
그 행의 `settings` 최상위 키는
`ui · otp · cidr · user · domain · subtitle · timezone · validation · time_format · refresh_time`
— **`security` 키가 아예 없었다.** 즉 `security.audit_log_retention_days` 는
선언된 적이 없고, 90은 dj-core `core/logger/tasks.py::purge_old_audit_logs` 의
**코드 기본값**이다. 그리고 그 삭제는 `_base_manager.filter(...).delete()` =
**하드 삭제**다 — 되돌릴 수 없다.

정리하면 그 beat 항목이 켜지는 순간 일어나는 일은
「고객이 정한 보존기간의 집행」이 아니라
**「아무도 정하지 않은 수로 감사 기록을 되돌릴 수 없게 지우는 일」**이었다.

## 1. 고친 자리 — 우리가 쥔 손잡이는 「부르지 않는 것」 하나다

dj-core 는 §0.4 이관 자산이라 그 함수의 기본값 90을 지울 수 없다. 그래서
**부르는 쪽에서 막는다.**

| 자리 | 무엇이 됐나 |
|---|---|
| `backend/common/ops_tasks.py::audit_retention_declared_days()` | 선언이 없으면 `None`. **dj-core 가 읽는 그 자리 하나만** 읽는다 |
| `backend/common/ops_tasks.py::ops_audit_purge_beat()` | `None` 이면 dj-core 태스크를 **부르지 않는다**(호출 0) · 판정 `SKIPPED_UNDECLARED` · 증거에 사유를 남긴다 |
| `backend/config/celery.py` | 거짓 주석을 **지우지 않고** ⛔ 로 표시한 뒤 사실을 적었다 · 03:10 → **02:40**(백업이 03:00 으로 당겨졌으므로 순서를 지킨다) |

★ **왜 우리 쪽 설정(`AUDIT_LOG_RETENTION_DAYS`)을 「선언됐다」의 근거로 안 쓰는가**
그것이 가장 그럴듯한 함정이다. 실제로 지우는 것은 dj-core 이고 그 함수는
`AdminConfig::System > security.audit_log_retention_days` **하나만** 읽는다.
우리 설정을 근거로 삼으면 이렇게 된다:

    우리 층 판정 : 「365일로 선언됐다 — 돌려도 된다」
    실제 삭제    : **90일 기준 하드 삭제**

「선언한 수」와 「지우는 수」가 갈리는 그 상태가 D-369 다. 그래서 값을
**그 자리에 심는다** — 적어 두는 것이 아니라.

## 2. 개발·스테이징 선언을 **심었다** (세종이 정한 수 · 365)

도구: `scripts/seed_retention_declaration.py` (자기시험 통과 · 정상 1 · 음성 3)

```
docker exec -e DJANGO_SETTINGS_MODULE=config.settings gx-shell \
    python /repo/scripts/seed_retention_declaration.py --apply
```

```
[P-67] [입력] 환경 'development' · 심을 값 365 · 그 자리의 지금 값 None
[P-67]   개발·스테이징인가            선언 환경이다
[P-67]   심을 값이 있는가            365일
[P-67]   그 자리가 비었는가           비었다 — 심을 수 있다
[P-67] 심었다 — `security.audit_log_retention_days = 365` · dj-core 가 읽는 값 365
[P-67] 통과 — 이제 감사 로그 파기가 **선언된 365일**로 돈다. 되돌리려면 `--unseed`
```
exit **0**. 같은 명령을 다시 돌리면 **exit 1** 로 거부한다(「이미 값이 있다 —
덮지 않는다. 남의 선언이다」) — 시드가 고객의 선언을 덮으면 그 순간
시드는 기본값이 된다.

★ 쓴 것은 **그 행의 칸 하나**다. 되돌리는 법: 같은 스크립트에 `--unseed`.
★ 운영에서는 이 스크립트가 **거부**한다 — 운영 값은 고객이 U5 에서 선언한다.

## 3. 실측 — 선언 뒤에 실제로 무엇이 도는가

`common.ops_audit_purge_beat` 를 한 번 불렀다 (2026-09-06 · gx-shell):

```
{"verdict": "OK", "retention_days": 365,
 "source": "선언 System > security.audit_log_retention_days (U5 설정 화면 · dj-core 가 읽는 자리)",
 "rows_before": 7371, "rows_after": 7371, "purged": 0}
```

**0건 정리.** 감사 로그의 가장 오래된 행이 2026-08-27T13:28:44Z 이고
365일 기준선은 2025-09-06 이므로 만료 행이 하나도 없다 —
**한 행도 안 지워진 것이 옳은 결과다.** 「돌았는데 아무 일 없었다」와
「돌지 않았다」를 판정 낱말이 가른다(`OK` vs `SKIPPED_UNDECLARED`).

미선언 갈래도 함께 쟀다 — `scripts/verify_retention_declared.py` ②:
목적지·일수를 비우면 **호출 0 · 판정 `SKIPPED_UNDECLARED`**.

## 4. 아직 못 넘은 것 — 덮지 않는다

- **beat 항목 `ops-audit-purge-daily` 는 여전히 꺼져 있다**(`enabled=false`).
  2026-09-05 17:42 에 사람이 껐고, 켜는 것은 이 차선의 판단 밖이다 —
  켜면 그 순간 파기가 실제로 돈다. 지금 켜도 0건이라는 것은 위 §3 이 보였지만,
  **켜는 시각은 사람이 정한다**(같은 표의 `sec-key-rotation-watch` 주석과 같은 규약).
  시각만 코드 선언대로 02:40 으로 옮겨 두었고 `enabled` 는 건드리지 않았다.
- **`purge-audit-logs-daily`**(dj-core 태스크를 직접 부르는 낡은 항목)도 꺼진 채다.
  그 항목은 우리 감싸개를 거치지 않으므로 **켜면 선언 검사를 우회한다** —
  켜지 말고 지우는 것이 옳다. 지우는 것은 조율자의 판단이라 손대지 않았다.
- 감사 로그는 지금 **7,371행**이다. 365일 선언 아래에서는 당분간 한 행도
  안 지워진다 — 상한은 보존 일수가 아니라 **디스크**가 정하고 있다.
