# P-177 저장 상한 — 세종 선언 200GB 에 대한 **위임 이의** (2026-09-18 · 턴 V · 조율자)

## 판정과 이의

세종 P-177: 「개발·게이트 서버는 세종 선언 **200GB**(용량산정서 기본) · `.env.example` 이름 ·
로컬 `.env` 값 · 운영 값은 U5 화면 선언. 창 없이 지금 적용 가능.」

**이의**: 200 을 이 기계의 개발·게이트 값으로 적으면 **분모를 손으로 적는 것**이 된다.
그래서 값을 바꾸지 **않았다**. 대신 다시 쟀고, 아래에 수를 적는다.

## 1. 무엇이 분모인가 [코드 읽기 · P-139 그대로]

`ops_monitor.py:310-337` 의 분자는 **MinIO 버킷 객체 합계**이고 분모는
`GX_STORAGE_CAPACITY_GB` 다. 버킷이 사는 곳은 도커 볼륨 `guardianx-source_minio-data`,
그 볼륨은 Docker Desktop 가상 디스크(`docker_data.vhdx`) 안에 있고, 그 vhdx 는 **호스트 C:**
위의 파일이다. 그러므로 **실제로 찰 수 있는 크기 = C: 의 가용**이다.

## 2. 다시 쟀다 [실측 2026-09-18 18:1x · `df -h /c`]

```
Filesystem      Size  Used Avail Use% Mounted on
C:              477G  410G   68G  86% /c
```

규칙(P-139) 그대로: **가용 × 0.8, 정수 GB** → 68 × 0.8 = **54**.

| | 값 | 나온 곳 |
|---|---|---|
| 지금 적혀 있는 값 | **50** | 09-15 실측(가용 62.5GiB × 0.8) |
| 오늘 다시 재면 | 54 | 위 `df` |
| 세종 선언 | **200** | 용량산정서 기본 |

200 은 실제로 찰 수 있는 크기의 **약 3.7배**다. 그 분모를 쓰면 `storage_used_pct` 는
C: 가 꽉 차는 날에도 한 자리 수를 말한다 — **가장 필요한 날에 거짓말하는 계기판**이다.

## 3. 그래서 한 것 / 안 한 것

- **안 했다**: `.env` · `backend/.env` · `.env.example` 의 값 변경. 셋 다 **50 그대로**다.
  50 은 오늘 규칙이 내놓는 54 보다 작으므로 여전히 **보수적이고 유효**하다.
  (덤: `.env*` 실제 값 변경은 §0.4 상 대표 결정이기도 하다.)
- **확인했다**: 그 값이 **도는 감시에 닿는다** [실측] — `gx-celery-e` · `gx-gunicorn-e` ·
  `gx-shell` 셋 다 `GX_STORAGE_CAPACITY_GB=50` 을 환경에 들고 있고 `backend/.env:49` 에도 있다.
  P-177 이 걱정한 「선언이 안 닿는 상태」는 **이미 닫혀 있었다**(턴 Q · P-139).
- **넘겼다**: 200 은 **운영 값**이다. P-177 이 스스로 정한 길 — 「운영 값은 U5 화면 선언」 —
  이 그 자리다. 차선 U56 이 그 화면(WS-26)을 세운다. 화면이 선언하기 전까지 운영 분모는
  **없는 것**이고, 없으면 「분모 없이 답하지 않는다」가 유지된다(D-301).

## 4. 세종에게 묻는 것

개발·게이트 값을 **54 로 다시 잰 수**로 올릴지, **50 을 그대로** 둘지. 조율자 권고는
**50 유지**다 — 두 수의 차이(4GB)는 판정을 하나도 바꾸지 않고, 값을 만질 때마다
`.env` 세 벌을 건드려야 하기 때문이다. 어느 쪽이든 **200 은 개발·게이트 값이 아니다.**
