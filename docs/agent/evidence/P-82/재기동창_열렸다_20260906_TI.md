## 1. 턴 H 를 막던 것이 사라졌다 — `LIVE_8000_RUNS_STALE_CODE` 해소

턴 H 는 「재기동 권한 1회」를 대표께 올리고 끝났다. 이번 턴 첫 확인에서
**`gx-shell` 이 이미 재기동돼 있었다**(`Up 5 minutes` · 컨테이너 안 프로세스 **0개**).
즉 8000 을 물고 있던 2026-09-05 14:41 짜리 프로세스는 **없어졌다.**

조율자가 8000·8010 을 HEAD(`abbdf36`)로 다시 세우고, 턴 H 가 낡음을 못 박을 때
썼던 **바로 그 프리플라이트**를 다시 물었다:

```
OPTIONS /api/v1/auth/login   Access-Control-Request-Headers: content-type,idempotency-key

  턴 H  8000 → allow-headers: … x-no-cache                              ← idempotency-key 없음
  턴 I  8000 → allow-headers: … x-no-cache, x-gx-wall-token, idempotency-key   ✔
  턴 I  8010 → allow-headers: … x-no-cache, x-gx-wall-token, idempotency-key   ✔
```

**같은 질문에 다른 답이 왔다.** 그래서 이 문장은 추론이 아니라 실측이다:
8000 은 더 이상 낡지 않았다. `.env.gates` 의 `GX_API` 를 8010 → **8000** 으로
되돌리고, 그 파일에 「이 줄을 믿지 말고 재라」와 재는 명령을 같이 적었다.

★ P-82 의 「8000/3002 는 때리지 않는다」는 **조건이 사라져 해제**된다.
  판정 대상은 다시 8000 이고, 그 신선함은 아래 게이트가 매번 말한다.

## 2. 첫 빨강은 **우리가 만든 회귀**였다 — 턴 G 의 교훈이 그대로 재발했다

서버를 세운 직후 게이트 13종을 전수로 돌렸다. `route-alive` 가 **빨강**이었다:

```
503 GET /api/media-data?page_size=25&current_page=1
```

턴 G 가 이미 적어 둔 문장이 있다 — 「차선 셋이 **환경**이라 부른 빨강은 **우리가
만든 회귀**였다」. 이번에도 그랬다. 원인은 **조율자가 서버를 MinIO 자격증명 없이
띄운 것**이다. 컨테이너에 구워진 값은 `minio.invalid` 라 객체저장소 이름 풀이부터
실패하고, 미디어 라우트가 503 을 낸다.

이 실패 모양은 이 저장소에 **이미 이름이 있었다** —
`docs/agent/evidence/TD-COORD/README.md` 가 같은 사고를 적어 두었다:

> 게이트가 두 턴 동안 초록이었던 것은 **그 프로세스가 죽지 않았기 때문**이다.
> 죽는 날 아무도 다시 못 세운다 — 그리고 그날은 「어제까지 초록이던 게이트가
> 갑자기 빨갛다」로 보인다.

**오늘이 그 「죽는 날」이었다.** 기동 절차가 문서에 있었기 때문에 5분 만에 되세웠다.
없었으면 이 빨강은 「제품 결함」으로 보고됐을 것이다.

되세운 뒤 `/api/media-data` 는 두 포트 모두 **401**(관문이 선 정상 응답)이다.

| | 잘못 세운 서버 | 바로 세운 서버 |
|---|---|---|
| `/api/media-data` (인증 없이) | 503 | **401** |
| MinIO 이름 | `minio.invalid` (구운 값) | `minio:9000` |

★ **영실 오판 +1.** 우회하지 않고 원인을 이름으로 확정했고, 그 이름은 새것이 아니라
  저장소가 이미 아는 것이었다. 새 교훈은 하나다 — **기동 절차를 문서가 아니라
  명령으로 만들어야 한다.** 다음 턴 후보: `scripts/serve_gate_api.sh`.

## 3. 그래서 만든 것 — `verify_live_freshness.py` (P-82 · 새 게이트)

낡음의 **넷째 얼굴**(낡은 판정)만 도구가 못 잡고 있었다. 이제 잡는다.

```
python scripts/verify_live_freshness.py            # GX_API 를 잰다
./docs/agent/verify_gates.sh --gate live-freshness
```

첫 줄은 **언제나 같은 세 가지**다 — 대상 서버 · 기동 시각 · 커밋.

| 판정 | 사유 이름 | 뜻 |
|---|---|---|
| 빨강(1) | `LIVE_COMMIT_MISMATCH` | 서버가 문 커밋 ≠ HEAD. 사실이지 환경이 아니다 |
| 회색(2) | `LIVE_OLDER_THAN_SOURCE` | 기동이 소스보다 오래됐다 — **증명할 수 없다** |
| 회색(2) | `LIVE_NO_PROCESS` | 그 포트를 문 프로세스가 없다 |
| 회색(2) | `LIVE_NO_CONTAINER` | 볼 자리가 없다 (`GX_ROUTE_CONTAINER`) |
| 초록(0) | `FRESH` | 기동이 소스보다 뒤 · 커밋이 같거나 모름 |

**소스 시각은 HEAD 커밋 시각이 아니다.** HEAD 가 `docs/**` 만 고쳤으면 서버는
낡지 않았다. 그래서 재는 것은 서버가 실제로 실행하는 나무(`backend/`)의
㉠ 마지막 커밋 시각과 ㉡ **작업본 mtime** 중 큰 쪽이다. ㉡ 을 빼면 커밋 안 된
수정이 도는 서버를 초록으로 읽는다.

`ALL_GATES` 의 **첫째**에 둔다. 이 게이트가 회색이면 **뒤의 게이트 색은 어제의 색**이다.

### ★ 만든 지 4분 만에 제 일을 했다

```
[FRESH] 대상 서버 http://localhost:8000 · 기동 2026-09-06 22:20:29 · 커밋 abbdf36
[FRESH] [입력] 저장소 HEAD abbdf36 · 소스 최신 2026-09-06 22:24:18
                (작업본 backend/common/management/commands/relink_control_role_menus.py)
[FRESH] **판정 불가(회색)** — `LIVE_OLDER_THAN_SOURCE`: 기동이 소스보다 4분 오래됐다
```

차선 하나가 22:24 에 백엔드 소스를 고쳤고, 22:20 에 뜬 서버는 그것을 **안 물고 있다.**
사람은 이 4분을 절대 못 본다. 병합 직전 서버를 다시 세우고 초록을 확인한다.
