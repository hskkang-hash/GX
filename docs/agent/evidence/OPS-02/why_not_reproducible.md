# OPS-02 — 빈 환경에서 매뉴얼대로 세우는 것이 **이 기계에서 왜 불가한가**

**실행 2026-09-04 · 차선 E3** · 결론: **손 밖 후보로 올린다. 그러나 아직 옮기지 않았다**(D-389)

---

## 0. 착시 ⑤를 먼저 피한다

> **우리 환경에서 한 번 더 도는 것은 재현이 아니다.** (지시서 §3-2 착시 ⑤)

그래서 아래는 「돌려 봤더니 됐다」가 아니라 **「어디까지 되고, 어디서 막히는가」**다.
막히는 자리를 짚지 못하면 그 절은 회색이고, 회색은 초록이 아니다.

---

## 1. 오늘 실제로 **재현된 절반** — 빈 DB 에서 매뉴얼 §2-3

[실측 2026-09-04 · `scripts/ops_rollback_drill.py`] 되돌리기 훈련(OPS-08)이 그 앞에서
**빈 DB 를 새로 만들고 매뉴얼 §2-3 을 그대로 쳤다.** 곁다리가 아니라 같은 실행의 §2 다:

```
psql -c CREATE DATABASE "e_rollback_check"   rc=0
manage.py migrate user                       rc=0
manage.py migrate multilanguage              rc=0
manage.py migrate                            rc=0
manage.py migrate --check                    rc=0      ← 정합
세운 직후: 표 220개 · stream_monitors 머리 0027_ops15_camera_pulse
```

**매뉴얼 §2-3 의 「세 줄」은 오늘도 유효하다.** 한 줄로 죽는 결함(P-ENV-1)도 그대로다.

★ 다만 **매뉴얼의 수가 낡았다.** §2-3 은 2026-09-01 실측으로 「표 214개 ·
stream_monitors 최신 `0020_…`」을 적어 두었는데, 오늘 빈 DB 는 **220개 · `0027_…`** 이다.
매뉴얼을 고칠 사람은 조율자다(이 문서는 등재부를 고치지 않는다) — 보고에 적었다.

전문: `docs/agent/evidence/OPS-08/rollback_drill.md` §1~2

## 2. 재현되지 **않는 절반** — 컨테이너 이미지를 이 기계에서 만들 수 없다

매뉴얼 §2-2 는 `docker compose` 로 컨테이너를 띄우라고 한다. 빈 환경이란 **이미지도
없는** 환경이고, 그러면 `compose` 가 `backend` 를 **빌드한다.** 그 빌드가 막힌다:

```
backend/requirements.txt:3
    dj-core @ git+ssh://git@192.168.0.22/thuongle/dj-core.git@master

backend/Dockerfile:63
    RUN --mount=type=ssh \
        GIT_SSH_COMMAND="ssh -o StrictHostKeyChecking=no" ...
```

이 기계에서 잰 것 [실측 2026-09-04]:

| 무엇 | 값 | 뜻 |
|---|---|---|
| `SSH_AUTH_SOCK` | **비어 있음** | `--mount=type=ssh` 에 넘길 에이전트가 없다 |
| `~/.ssh` | `known_hosts` · `known_hosts.old` **뿐** | 개인키가 없다 |
| `192.168.0.22:22` | **닿지 않는다** (`nc -z -w 3`, 컨테이너 안에서) | 사내망 밖이다 |
| `192.168.0.22:9418` | **닿지 않는다** | git 프로토콜도 막혀 있다 |

즉 **dj-core 를 받을 길이 없다.** 매뉴얼 §1 이 스스로 적어 둔 그 관문이다:

> "★ **dj-core 가 이 설치의 유일한 실질 관문이다.** 저장소에 없고(사내 private) …"

지금 이 기계에 `guardianx-backend:latest`(5.55GB)가 **이미 있는 것**이 유일한 이유이고,
있는 이미지를 다시 쓰는 것은 **재현이 아니라 재사용**이다.

---

## 3. 그러면 「컨테이너를 지우고 다시」는 왜 안 했나 — 두 가지

① **지우면 안 되는 것들이다.** `postgres` · `gx-shell` 에는 지금 다른 차선 셋의
   runserver(8000·8300·8400)와 시험이 붙어 있다. 지시서가 지우지 말라고 못 박았고,
   지웠다면 그 순간 다른 차선 셋이 죽는다.

② **지워도 되는 것을 지워 봐야 §2 를 못 넘는다.** 새 프로젝트 이름으로 두 번째
   스택을 띄우는 길(`docker compose -p … up`)은 다른 차선을 안 건드리지만, compose 는
   `backend` 서비스에 `image:` 가 없고 `build:` 만 있어 **새 이름으로 빌드를 시작한다.**
   그 빌드가 §2 에서 막힌다. 즉 「지울 수 있는 것만 지우기」로는 이 절이 안 갚아진다.

★ 그래서 **아무것도 지우지 않았다.** 지우기 전에 무엇을 지우고 어떻게 되살리는지를
  적어야 하는데(지시 규약), 적어 보니 **지워서 얻을 것이 없다**는 것이 먼저 드러났다.

---

## 4. 무엇이 있으면 갚아지나 — 셋 중 하나

| 길 | 필요한 것 | 누가 |
|---|---|---|
| ㉠ 사내망에서 실행 | `192.168.0.22` 에 닿는 자리 + dj-core 배포키 | 대표/사내 |
| ㉡ dj-core 를 사내 레지스트리 wheel 로 | 이미 뜬 wheel 하나 + `requirements` 한 줄 | 사내 |
| ㉢ 이미지를 사내 레지스트리에 올린다 | `guardianx-backend` 를 push 할 자리 | 사내 |

셋 다 **저장소 밖의 결정**이다. 그래서 OPS-02 는 **「손 밖」 후보**다.

★ 그러나 **아직 옮기지 않았다**(D-389: 재기 전에 옮기지 마십시오).
  오늘 재 본 결과가 위 §1·§2 이고, 옮기는 것은 조율자의 손이다. 이 문서는
  **옮겨 달라는 요청이지 옮긴 기록이 아니다.**

---

## 5. 남는 사실 하나 — 절의 절반은 이미 초록이다

「빈 환경에서 매뉴얼대로」를 **DB 절차**와 **이미지 조달**로 가르면:

```
DB 절차 (§2-1 · §2-3 · §2-5)   → 오늘 빈 DB 에서 rc=0 ×4 로 재현됐다   [실측]
이미지 조달 (§2-2 의 앞단)      → 이 기계에서 불가. 사유는 §2         [실측]
```

가르지 않고 하나로 두면 절 전체가 회색이고, 회색인 동안 **이미 초록인 절반도 안 지켜진다.**
가르는 것을 제안한다 — 자르는 것은 등재부의 일이고, 등재부는 조율자만 고친다.
