## 2. Table B — 턴 배정 (AK · AL · AM · AN)

**배정 규칙**(코드로 재현 가능 — 아래 파이썬 조각을 다시 돌리면 같은 수가 난다):

```python
def bucket(r):
    doc, role = r["doc"], r["role"]
    if (doc == "DSM" and role in ("U1", "U2")) or (doc == "FWS" and role in ("F1", "F2")):
        return "AK"   # U1·U2 화면 · 사건 처리 · 경보
    if (doc == "DSM" and role in ("U4", "U5")) or (doc == "FWS" and role in ("F3", "U5")) or r["id"] == "O-03":
        return "AL"   # U4 보고서 · U5 관리자 · 청구 화면
    if (doc == "DSM" and role in ("U3", "U6")) or (doc == "FWS" and role in ("F5", "F6")) or r["id"] in ("O-10", "O-04"):
        return "AM"   # U3 모바일 · U6 연계 · 서명키 · AI 모델
    return "AN"        # 나머지
```

|---|---|---|---|
| **AK** | U1·U2 화면 · 사건 처리 · 경보 | DSM U1(6)·U2(5) + FWS F1 산불감시원·탐지(15)·F2 진화대·초기대응(15) | **41** |
| **AL** | U4 보고서 · U5 관리자 · 청구 화면 | DSM U4(9)·U5(5) + FWS F3 산림과·통계(20)·U5 관리자(5) + O-03 라이선스·계량·청구(1) | **40** |
| **AM** | U3 모바일 · U6 연계 · 서명키 | DSM U3(4)·U6(3) + FWS F5 드론(10)·F6 연계(10) + O-10 키·자격 회전(1)·O-04 모델 레지스트리(1) | **29** |

넷 다 ≥25 를 채운다. **136건 전부가 AK~AN 안에 들어간다 — 「출시 뒤」로 미루는 항목은
이번 배정에서 0건이다.** (AN 안에서도 규모가 갈린다 — M 19 · S 6 · L 1. 만약 AN 을 맡는
차선이 한 턴에 26건을 다 못 닫으면, **L 1건(FWS-F4-14 「진화완료 후 잔불·뒷불 감시 계획
승인」)을 먼저 「출시 뒤」로 미루고 S·M 25건을 이번 턴 목표로 잡을 것을 권한다** — 그것이
정확히 ≥25 문턱을 다시 채운다.)

★ **DSM U1/U2 와 FWS F1/F2 를 한 턴(AK)에 묶은 이유**: 지시서 문구 「U1·U2 화면·사건 처리·
경보」가 역할 번호(U1/U2)만 말하지만, FWS 의 F1(산불감시원 — 탐지·경보)·F2(진화대 —
초기대응)가 **같은 일**(사건을 처음 받아 처리하는 화면)의 산불판이다. DSM 의 U1/U2 만 잡으면
11건뿐이라 ≥25 를 못 채운다 — 같은 성격의 다른 앱 절을 더해야 문턱이 선다.
★ **역할 표기가 지시서의 「U1~U6」과 안 맞는 자리**: FWS 는 F1~F6(현장) + U5(관리자) 를 쓰고
OPS 는 U0(플랫폼 운영자) 를 쓴다 — DSM 의 U1~U6 표기를 FWS·OPS 에 억지로 씌우면 없는
역할을 지어내는 것이라 그러지 않았다(문서 §3의 실제 역할 이름 그대로 §1 참고).

## 3. S 규모 후보(≥5) — 판정기가 세려면 무엇이 있어야 하는가

**닫지 않았다 — 무엇이 없는지를 적는다.** 이유는 구조적이다:
`scripts/verify_spec_coverage.py::score()` 는 분자(`sec_points`)를 **대장의 8영역 절 157개
(`roll["counts"]`)에서만** 합산한다. 별표(annex) 136 건은 `n_annex` 로 **분모에만** 더해지고,
그 안의 `kind`/`status` 값이 무엇이든(`unmeasurable`이든 손으로 `closed`로 바꾸든) **분자
계산에 한 번도 안 들어간다.** 그래서 annex 항목 하나를 "닫아도" 이 산출기의 `%` 는
안 움직인다 — 그 함수를 annex 의 kind 를 읽게 고치는 것은 **판정기를 고쳐 수를 올리는 일**
(P-203 금지 · D-380: 판정기는 보고서 문장이 아니라 실측을 센다)이다. 그래서 이번 턴엔
**annex 항목을 scripts/docs 만으로 「닫을」 방법이 없다** — 진짜로 닫으려면:

  ① 그 기능이 **실제로 구현**되어야 하고(백엔드 엔드포인트 또는 프런트 화면 — scripts/docs 밖),
  ② 그 절이 `annex_2_spec` 이 아니라 **8영역(`areas`) 중 하나의 절**로 대장에 새로 등재되어야
     하고(그 등재 결정은 8영역 가중치 표를 쥔 차선/조율자의 몫 — 조율자가 「별표는 8영역
     밖」이라고 이미 판정했다, 이 판정을 뒤집는 것은 이 차선의 권한 밖이다),
  ③ 그 절에 `verify_ga_readiness.py::evidence_problems` 가 확인할 수 있는 **실재 증거 파일**이
     있어야 한다.

## 4. 다음 사람에게 남기는 것

- 기능명세 포함 완료율을 **annex 를 통해** 올리려면, `annex_2_spec` 항목을 8영역 절로
  승격하는 결정(그리고 그 승격이 상용/100 가중치 표를 안 무너뜨리는 방법)이 먼저 서야 한다
  — 그 결정은 이 차선의 소유표 밖이다(조율자·차선 N 의 자리, `verify_spec_coverage.py`
  머리글 §37행 「별표는 8영역 밖」참고).
- Table B(AK/AL/AM/AN)는 **역할·화면 성격**으로만 나눴다 — 실제 턴 배정은 각 차선의
  §0.4 금지구역(backend/delivery·orders·terminals)과 겹치는지 다시 확인해야 한다. 이번
  분석은 DSM/FWS/플랫폼 앱의 신규 화면·API 이야기라 금지구역과 안 겹칠 가능성이 높지만,
  **이 차선은 그 대조를 하지 않았다** — 배정을 받는 차선이 착수 전에 한 번 더 대야 한다.
