# GuardianX 설치·운영 매뉴얼 v0.1 — 릴리스 후보(SDN 제외판)

**발행** 2026-09-01 · **대상** 인수측 운영자 · **근거** 계약 제7조 3단계 인도물 ②
**★ 이 문서의 명령은 전부 실행해 보고 적었다.** 돌던 환경에서 적은 것이 아니다 (D-303 §4).

---

## 0. 이 문서를 어떻게 썼나 — **빈 것에서 세워 보며 적었다**

이미 도는 환경에서 절차를 적으면 **이미 되어 있는 단계가 빠진다.** 그래서 빈 데이터베이스
하나(`gx_install_probe`)를 새로 만들고, 거기에 처음부터 세우면서 **친 명령과 그 결과를
그대로** 옮겼다. 아래 rc 값은 전부 실측이다(2026-09-01).

확인 후 그 데이터베이스는 지웠다. **운영 DB 는 건드리지 않았다** (D-002 · 불변 제약).

⚠ 아직 적지 못한 것은 §7 에 **적지 못한 이유와 함께** 있다. 빈칸으로 두지 않는다 —
빈칸은 "없다"인지 "안 봤다"인지 구별되지 않는다(D-264).

## 1. 무엇이 필요한가

| 항목 | 값 | 확인 방법 |
|---|---|---|
| Docker / Docker Compose | v2 | `docker compose version` |
| PostgreSQL | 16 (compose 가 띄운다) | `docker exec postgres psql -U postgres -c "select version();"` |
| Redis | compose 가 띄운다 | `docker exec redis redis-cli ping` → `PONG` |
| **dj-core** | 사내 private 패키지 | `python -c "import core.base"` — **호스트에는 없다.** §2 참조 |
| MinIO · OpenSearch · AI(gRPC) | **선택** | 없으면 저하 운전으로 돈다. §6 참조 |

★ **dj-core 가 이 설치의 유일한 실질 관문이다.** 저장소에 없고(사내 private), 호스트 파이썬에도
없다. 그래서 백엔드는 **컨테이너 안에서** 돈다 — 이미지에 dj-core 가 들어 있다.
호스트에서 `python manage.py …` 를 치면 `ModuleNotFoundError: No module named 'core'` 가 난다.
그것은 설치 실패가 아니라 **잘못된 자리에서 친 것**이다.

## 2. 설치 — 다섯 단계

### 2-1. 환경 파일

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

⚠ `.env.example` 에는 **실값이 한 개도 없다**(게이트가 매 커밋 판정한다 · D-298).
실값은 사내 vault 에서 받아 `backend/.env` 에 채운다. **저장소에 커밋하지 않는다**(D-204).

채우지 않으면 안 되는 것은 넷뿐이다:

| 변수 | 없으면 | 비고 |
|---|---|---|
| `DJANGO_SETTINGS_MODULE` | 전 명령이 `ImproperlyConfigured` | `config.settings` |
| `DB_HOST` `DB_NAME` `DB_USER` `DB_PASSWORD` | 기동 불가 | compose 기본값 있음 |
| `REDIS_HOST` | 캐시 초기화 실패 | compose 기본값 있음 |
| `SECRET_KEY` | 기동 불가 | 배포마다 새로 만든다 |

나머지(외부 API 키 11종)는 **비워도 선다.** 비면 해당 기능이 "조회 안 함"으로 정직하게
표시된다 — 조용히 실패하지 않는다(D-290 · FX-5 `address_status='disabled'`).

### 2-2. 컨테이너 기동

```bash
docker compose up -d postgres redis
docker compose --profile tools up -d shell     # 관리 명령을 치는 자리
```

### 2-3. ★ 마이그레이션 — **세 줄이다. 한 줄이 아니다**

```bash
docker compose exec -T shell python manage.py migrate user
docker compose exec -T shell python manage.py migrate multilanguage
docker compose exec -T shell python manage.py migrate
docker compose exec -T shell python manage.py migrate --check      # rc=0 이어야 한다
```

**왜 세 줄인가 — 실측된 결함이다.** `manage.py migrate` 한 줄로는 빈 DB 에서 죽는다:

```
core/logger/migrations/0009_…py:17
    MultiLanguageContent = apps.get_model("multilanguage", "MultiLanguageContent")
LookupError: No installed app with label 'multilanguage'
```

dj-core 의 `logger/0009` 가 `multilanguage` 의존을 선언하지 않아, 실행 계획에서 뒤에 오면
그 시점의 상태에 모델이 없다. `user` 가 먼저인 것도 실측이다 — `multilanguage` 만 먼저 돌리면
dj-core 시그널이 `AnonymousUser` 를 만들려다 `user_coreuser` 표가 없어 죽는다.

근본 원인은 **§0.4 금지구역(dj-core)** 안이라 이 저장소가 고칠 수 없다(P-ENV-1).
전말과 되돌린 시도는 `docs/agent/evidence/e2e/migration_from_scratch.md` 에 있다.

**2026-09-01 실측** (빈 DB `gx_install_probe`):

```
migrate user            rc=0
migrate multilanguage   rc=0
migrate                 rc=0
migrate --check         rc=0        ← 정합
manage.py check         rc=0        System check identified no issues (0 silenced)

표 214개 · stream_monitors 최신 마이그레이션 0020_detectionevent_address_address_status
구역 표 2개 생성 확인: stream_monitors_zone · stream_monitors_zone_cameras
```

### 2-4. 초기 데이터

```bash
docker compose exec -T shell python manage.py createsuperuser
docker compose exec -T shell bash gen_default_data.sh      # 코드값·메뉴 등 마스터
```

### 2-5. 기동 확인

```bash
docker compose exec -T shell python manage.py check                 # rc=0
docker compose up -d backend nginx
curl -sS -o /dev/null -w '%{http_code}\n' http://localhost/api/docs # 200
```

## 4-B. 백업과 복구 — **해 봤다. 그리고 뜨는 자리가 정해져 있다** (D-354 · D-356)

> **복구를 해 보지 않은 백업은 백업이 아니다.** 「백업 있음」은 절이 아니고
> **「복구 성공」이 절이다.** 아래 명령은 전부 실제로 돌려 본 것이고, 그 기록이
> `docs/agent/evidence/D-354/restore_run.md`(DB)와
> `docs/agent/evidence/D-356/restore_objects_run.md`(영상)에 있다.

### 4-B-1. ★ **뜨는 자리가 정해져 있다** — 이걸 모르면 사고 나는 날 못 뜬다

```
pg_dump: error: aborting because of server version mismatch
detail:  server version: 18.1 · pg_dump version: 17.7
```

[실측 2026-09-09] **앱 컨테이너의 `pg_dump`(17.7)로는 DB 서버(18.1)를 못 뜬다.**
아무 데서나 돌리면 안 되고, **DB 컨테이너 안의 클라이언트로** 떠야 판이 반드시 맞는다.

```bash
# ★ --via docker:postgres — 이 인자가 위 오류를 피하는 유일한 방법이다
docker exec gx-shell python /repo/scripts/ops_backup.py --db     --via docker:postgres --out /docs/agent/evidence/D-354/backup
```

### 4-B-2. 영상(객체저장) — **이벤트에 묶인 것만 뜬다**

버킷 전량은 크고 비싸고, **제품이 필요로 하는 것도 아니다.** 재난안전에서 증빙이 되는
것은 「그 이벤트의 그 장면」이고, 그것을 아는 표가 `EventClip` 이다. 그래서 기본 범위가
`event_bound` 다. 이관·이사처럼 통째로 옮겨야 할 때만 `--object-scope all` 을 쓴다.

```bash
docker exec gx-shell python /repo/scripts/ops_backup.py --objects     --out /docs/agent/evidence/D-356/backup           # 기본 = event_bound
```

★ 이 명령이 **「DB 는 영상이 있다고 하는데 그 장면이 실제로 없는」 건수를 함께 낸다.**
그 수가 0 이 아니면 그것은 백업 문제가 아니라 **이미 잃어버린 것**이고, 복구해도 안 돌아온다.

### 4-B-3. 복구 — **되살려 보고 바이트로 대조한다**

```bash
# DB — 임시 DB(gx_restore_*)로만 간다. 원본에는 쓰지 않는다
docker exec gx-shell python /repo/scripts/ops_restore.py     --via docker:postgres --manifest /docs/agent/evidence/D-354/backup/manifest.json

# 영상 — 새 버킷(gx-restore-*)으로만 간다. 원본 버킷에는 쓰지 않는다
docker exec gx-shell python /repo/scripts/ops_restore.py --objects-only     --manifest /docs/agent/evidence/D-356/backup/manifest.json     --evidence /docs/agent/evidence/D-356/restore_objects_run.md
```

[실측 2026-09-10] 영상 복구 예행 — **대상 3개 · 되살림 3개 · 해시 일치 3개.**
원본 버킷은 건드리지 않았다. 「파일이 생겼다」가 아니라 **바이트가 그때 그 바이트인지**를 잰다.

### 4-B-4. 보존 기간 — **정하지 않으면 디스크가 정한다**

`scripts/ops_backup.py` 의 `RETENTION_DAYS = 90`. 계약이 정한 수가 **아니다**
(계약 [별첨1] 에 보존 기간 조항이 없다). 고객이 다른 값을 요구하면 그 상수 하나를 고친다.

### 4-B-5. ★ 아직 아닌 것 — **어디에 둘지는 안 정했다**

지금 백업 목적지는 **저장소 안**이다. **같은 디스크는 백업이 아니다.**
운영에서는 최소 다른 볼륨, 가능하면 다른 호스트여야 하고, 그 목적지는 배포 구성에서
정해진다. 실측하지 않은 경로를 여기 적으면 **매뉴얼이 거짓말을 시작한다**(D-286) —
그래서 「해 봤다」와 「어디에 둘지는 아직」을 함께 적는다.

## 6. 외부 의존이 죽었을 때 — **저하 운전**

| 죽은 것 | 결과 |
|---|---|
| MinIO | 이벤트는 기록된다. `snapshot_path` 가 **빈 문자열**이고 로그에 사유가 남는다 (가짜 경로를 만들지 않는다) |
| 메일 서버 | 이벤트·등급 판정·수신자 결정은 산다. 발송 실패가 `DeliveryRecord` 에 사유와 함께 남는다 |
| 주소 API (FX-5) | 이벤트는 난다. `address_status='failed'` 이고 알림에 "주소 확인 불가(좌표: …)" 로 나간다 |
| AI gRPC | 검출이 안 들어온다. 옮기지 못한 라벨은 **세어서** 로그에 남는다 |
| OpenSearch | 기동 시 경고만 남기고 계속 선다 |

★ 공통 규칙: **조용한 성공을 만들지 않는다.** 못 한 것은 못 했다고 상태·로그에 남는다.
