## ⑤ 스스로 의심하는 점
- **골든타임 준수율(F3-16)은 근사다.** 제목이 부르는 것은 annex §4.3 의 「헬기
  투하·지상 도달 30분」이지만, 그 도달 시각은 `stream_monitors.services.
  response_clock` 안에 있고 이 앱이 거치는 공개 문(`apps.dsm.services.
  response_latency`)은 분포(p50/p95)만 낸다 — 사건별 원값을 안 준다. 그래서
  「확인 회신(occurred_at→reviewed_at) 30분 이내 비율」로 근사했고 응답에
  `golden_time_note` 로 그 사실을 밝혔다. 세종/조율자가 이것을 "제목이 부르는
  것과 다른 것을 쟀다"고 보면 F3-16 은 반쪽으로 재분류될 수 있다 — 그 경우
  대안은 (a) `apps.dsm.services` 에 사건별 도달 시각을 내는 공개 함수를 새로
  더하는 것(다른 차선·조율자 판단이 필요) 또는 (b) 이 근사를 그대로 두고
  제목에 "(근사)"를 다는 것이다.
- **F3-18 계도·단속 통계는 본인 실적만이다.** 감사 표(`logger.AuditLogs`)에
  테넌트 칸이 없다는 것은 이 저장소 전체의 기존 한계(patrol.py·standby.py·
  equipment.py 가 이미 같은 자리에서 멈췄다)이지 이 차선이 새로 만든 구멍이
  아니다 — 그러나 "통계"라는 제목이 조직 전체 집계를 암시할 수 있어, 승격
  기준을 엄격히 보면 이 절도 F3-16 과 같은 논쟁 대상이 될 수 있다.
  `patrol_enforcement_stats`/`entry_control_zones` 응답에 `"scope": "mine"` 을
  명시적으로 넣어 화면·다음 사람이 오독하지 않게 했다.
- **F3-11 의 "앱 푸시"는 F6-07 이 이미 열어 둔 [미확인]을 그대로 물려받았다** —
  이 차선이 직접 조사하지 않았다(F6-07 의 판단을 신뢰했다). 만약 그 사이
  산림청 공개 API 가 확인됐다면 이 절도 다시 열어야 한다.
- 프런트(`OfficeReport.tsx`)는 17개 라우트 중 핵심 흐름(대피 계획·이행·상황
  보고·최종보고·통계·카메라·계도단속·훈련·온보딩)을 카드로 노출했지만, 화면
  자체의 HTTP 실측 시험(예: `verify_click_completes`)은 이 차선이 돌리지
  않았다 — 그 측정은 V 창의 몫(규약에 그렇게 적혀 있다)이라 판단했다.
- 테스트 실행 중 `test_fws_f3a.py`(N2 의 F3-01~09 시험으로 추정)가 같은
  gx-shell 안에서 동시에 돌고 있는 것을 `ps aux` 로 확인했다 — 서로 다른 DB
  이름(`test_gx_lane_n3` vs N2 의 것)을 썼다고 가정하지만, 직접 확인하지는
  못했다. 만약 같은 DB 이름을 썼다면 두 차선의 `--create-db` 가 충돌했을 수
  있다 — 조율자가 병합 전에 각 차선의 DB 이름을 재확인해 주시면 좋겠다.
