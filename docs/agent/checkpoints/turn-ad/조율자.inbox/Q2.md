## ② 고친 파일:줄
- `scripts/verify_ga_readiness.py` — **옛 5키 줄(호환 접기) print 를 걷었다.**
  구간 약 1435~1463(현재 1435~1466). `roll_q` 접기와 그 print 문을 지우고, 「닫힌
  절 N/N …」요약 줄을 `roll`(6키)로 다시 써서 **못 잼과 재서 빨강을 나란히** 보이게
  했다. 6키 줄 print 는 그대로 두되 「이제 유일한 정본」이라는 주석을 달았다.
  ⚠ 이 한 파일에서 **그 print 블록 하나만** 건드렸다 — `KINDS`·`KIND_POINTS`·
  `judge_gate_alignment` 등 부류 셈·게이트 대조 로직은 손대지 않았다.
- `scripts/verify_readiness_scores.py`
  - `_KIND_LINE` 정규식을 `부류\s+(\d+)절` → `P-246\s*여섯째\s*부류\s*[—-]` 로 바꿨다.
  - `parse_ga_kinds()` — 6키 줄에서 여섯 칸을 읽고, 총합은 (옛 줄처럼 별도로 안
    적으므로) **여섯 칸의 합으로** 낸다. `KIND_SCORE`·`KIND_ORDER`·`kind_points()`
    는 **안 건드렸다**(부류 셈·점수 식 그대로 다섯 칸).
  - `_OLD_5KEY_LINE` 정규식 + `old_5key_line_present()` 신설 — 옛 줄이
    (6키 줄과 나란히 있어도) 다시 나타나면 잡는다.
  - `aa_report()` — `roll = parse_ga_kinds(...)` 직후 재발 검사를 넣어 **빨강**으로
    `red` 리스트에 적는다(회색이 아니다). PR① 점수 계산 직전에만
    `measured_red`→`unmeasurable` 로 **접어서** `kind_points()`(다섯 칸 표)에
    먹인다 — 점수식은 그대로, `roll["counts"]` 원본은 안 접는다. `pr_closed_line`
    에 「재서 빨강 N」을 추가해 Q 자신의 보고 줄도 은닉을 되풀이하지 않게 했다.
  - `--self-test` 배터리에 6키 픽스처 재작성(`_ga`) + 신규 표본 5개(양성 3 ·
    음성 1 · aa_report 빨강 1) 추가.

## ④ 음성 대조 · 출생 표본 결과
- **음성 A** — 고치기 전에 잡은 실제 `--static` 출력(옛 줄 포함)을 새 코드에
  먹였다 → `old_5key_line_present(...) == True`(재발 감지 성공) **그리고**
  `parse_ga_kinds(...)` 는 옛 줄을 무시하고 6키 줄만 제대로 읽었다(둘이 나란히
  있어도 옳게 갈랐다).
- **음성 B(자기시험 내)** — 옛 5키 줄만 있는 합성 표본 → `parse_ga_kinds` `None`,
  `old_5key_line_present` `True`, `aa_report(...)["red"]` 에 `"P-253 재발"` 포함.
  6키 줄만 있는 표본 → `old_5key_line_present` `False`(false positive 없음).
- **출생 표본(D-310, 주석에 문구 그대로 넣었다)**: `old_5key_line_present()` 와
  `_OLD_5KEY_LINE`/`_KIND_LINE` 주석 — 이 칸이 태어난 사례는 **「못 잼 71 안에
  재서 빨강 3이 묻혀 있었다」**(차선 Q, 2026-09-22 저녁 `--static` 실측, 위 ①
  그대로) **이고 조율자가 게이트-부르는 갈래로 잰 다른 시각(WO-GX-20260923-07
  §1)에는 같은 은닉이 「못 잼 72 안에 재서 빨강 4」로 나타났다** — 둘 다 합성이
  아니라 서로 다른 시각의 실측이다. `verify_tool_selftest.py` 가 두 파일을 여전히
  「출생 표본 있음」으로 센다(위 ① 로그).

## ⑤ CR 산출기가 낸 수 (P-256)
**31.25 는 지금 안 난다 — 왜인지 재서 확인했다(손으로 안 고쳤다).**
- `--aa` 실행: `CR 18.8% [1.5/8]` — 두 출처(WO-04 §4-1 정본 · N 전사
  `GX-CR_8칸_v1.0_20260921.md`)를 **다 읽고 대조 — 같다**, CR2(계량 씨앗)는
  두 출처 모두 아직 **0**(`**0**` / `**없다** — 값 0`)이다. `verify_seed_p20
  rc 0`(0/23) 판정이 **아직 어느 출처 문서에도 안 옮겨졌다** — `docs/workorders/`,
  `docs/design/`, `docs/agent/RESUME_NEXT.md` 전부 grep 했고 새 값 없음.
- **드라이런으로 배선만 검증**(저장소 파일은 건드리지 않고, 메모리 안에서 두
  출처 텍스트를 함께 고쳐 `aa_cr8_chain()` 에 먹였다):
  ```
  CR2: **0** → **1** (두 출처 동일하게)
  → sum 2.5/8 = 31.25%  ← 정확히 P-256 이 말한 수
  ```
  한쪽만 고치면(WO-04 만) 산출기가 **「CR 표가 갈렸다」 빨강**을 낸다 — 즉 이
  산출기는 **정확히 설계대로** 작동한다: 손으로 넣은 수가 아니라 **두 출처가
  일치할 때만** 읽어서 31.25 를 낸다.
- **CR2 값을 왜 내가 안 고쳤나**: (a) `_규약.md` 소유표에 이 문서(`GX-CR_8칸`,
  `WO-04 §4-1`)는 Q 소유가 아니다. (b) P-256 문장 자체가 「CR 8칸 정본 갱신(N)」
  이라고 이름으로 못박았다 — 갱신 판단(청구 0/23 을 CR2=1 로 볼지)은 N/세종
  자리다. (c) 「산출기가 세어서 낸다」 지시는 **파이프라인을 고치라는 것**이지
  **증거 문서의 값을 대신 판단하라는 것**이 아니라고 읽었다. → **미룸으로
  적는다**: CR2 실제 갱신(WO-04 §4-1 **와** `GX-CR_8칸` 두 곳 동시)은 N/조율자.

## ⑥ 못 한 것과 왜
- CR2 실제 값 갱신 — 위 ⑤ 사유(소유·판정 권한 밖).
- `docs/design/GX-CR_8칸_v1.0_20260921.md` §2 의 「2.0 vs 1.5」 미해결 서술은
  손 안 댔다 — P-244 가 이미 1.5/8=18.75 를 정본으로 정정했다고 지시서에
  적혀 있는데(내 지시서 §0.4 메모), 이 문서 자체는 여전히 「2.0/8 이 정본」
  으로 §2 를 열어 두고 있다. **이 문서도 N 소유**라 손 안 댔다 — 대신 이
  갈림을 여기 적어 둔다(다음 사람이 조용히 삼키지 않도록).
- 게이트-부르는 실측 갈래(20분+)는 **한 번도 안 불렀다** — 이번 확인은 전부
  `--static`/`--self-test`/`--aa`(기본 정적) 로 됐고, 429 위험을 늘릴 이유가
  없었다.
