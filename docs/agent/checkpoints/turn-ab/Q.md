## ② 「기능명세 포함 완료율」 산출기 신설 — **25.6 %** (`scripts/verify_spec_coverage.py`)

### ★★ **id 는 있다.** 지시서·조율자·N 의 전제가 여기서 틀렸다

```
그물 `DSM-01`          → 0건       ← 조율자가 던진 그물 · 차선 N 이 독립으로 재확인
그물 `DSM-U\d+-\d+`     → **32건**  ← 실재 표식은 `DSM-U1-01`
그물 `FWS-[FU]\d+-\d+`  → **90건**  ← 세종의 「FWS 90」과 **한 자도 안 틀린다**
그물 `O-\d{2}`          → **14건**  ← 세종 판독 12 · 실물 `O-01`~`O-14`
```

**두 사람이 같은 답을 냈다고 해서 그 답이 실물은 아니다** — 같은 그물을 두 번 던지면 같은 0 이 두 번 나온다.
그래서 이 산출기는 **그물을 소스에 적는다**. 다음 사람이 수가 아니라 **그물부터** 의심할 수 있게.

그리고 **473 과 136 은 갈린 한 수가 아니라 다른 것을 센 두 수**다:
473 = 세 문서의 **모든** 표 데이터행(§5 업무처리명세 · §6~§9 화면구성도 · 매핑표까지)
136 = 「**사용자별 세부 기능명세**」 절의 항목만. 지시서의 분모(대장 절 + 기능명세)는 **후자**다.

### 세는 규칙 — **산출기 소스에 있다**(`SPEC_SOURCES` + 머리 주석)

| 문서 | 절 | 그물 | 기계가 센 수 | [세종 판독] |
|---|---|---|---|---|
| `DSM_…_v1.1_지침기반` | §4 사용자별 세부 기능명세 | `\bDSM-U\d+-\d+\b` | **32** | 32 ✓ |
| `FWS_…_v1.0_프로세스` | §5 사용자별 세부 기능명세 | `\bFWS-[FU]\d+-\d+\b` | **90** | 90 ✓ |
| `GuardianX_플랫폼구조설계서_v1.0` | §7 플랫폼 운영자(U0) | `\bO-\d{2}\b` | **14** | **12 ✗** |
| **합** | | | **136** | 134 |

1. **한 항목 = id 표식 하나.**
2. **표 데이터행이 아니라 id 를 센다** — FWS §5.7 의 다섯(`FWS-U5-01`~`05`)은 **표가 아니라 문단**이다.
   행을 세면 85, id 를 세면 **90**. **세종의 「FWS 90」과 맞는 쪽이 id 다.** 그래서 규칙을 id 로 정했다.
3. **같은 id 는 한 번만 센다**(DSM 문서 안에 `DSM-U2-05` 가 두 번 나온다 · 둘 세면 34가 된다).
4. **세 문서 밖의 인용은 안 센다**(PRD v1.1 은 `DSM-U1-01~06` 처럼 **범위로** 인용한다).
5. 뽑은 목록 → **`docs/agent/evidence/P-234/spec_ids.json`** — **차선 N 의 등재 입력**이다(파생물 · 손으로 고치지 않는다).

## ③ **결정문은 배선이다** — D-511 + `enforced_by` (P-217)

턴 AA 에 「MEASURED 남은 회색 28 은 턴 AC 부터 빨강」을 **보고 문서에만** 적었다(그 턴 넘김 7번).
**문서에 적힌 기한은 그날이 와도 색을 안 바꾼다 — 조용히 지나간다.** 배선으로 세웠다:

```yaml

- id: D-511
  deadline: "2026-09-23"      # 턴 AC 첫날 (턴 AB 는 09-22 · WO §6)
  escalates_to: red
  enforced_by: |
    · scripts/_gate_header.py::read_decision / deadline_passed / escalation
    · scripts/verify_gate_header.py — MEASURED_LINE 이 그 답으로 회색↔빨강을 가른다
    · python scripts/_gate_header.py --self-test — 기한 전/후/못 읽음 세 갈래
```

`verify_gate_header` 가 **그 파일을 읽어서** 오늘과 댄다 — **날짜는 코드에 없다.**

```

                      그날부터 이 칸은 **red**. 오늘은 아직 회색이다
```

자기시험 넷을 붙였다: 기한 **전** 회색 · 기한 **뒤** 빨강 · **결정문을 못 읽으면** 회색 + 사유 ·
**분모를 다 말하면 기한이 지나도 초록**(없는 빨강을 만들지 않는다).

★ **결정문을 지우면 꺼지지 않고 「못 읽었다」고 말한다**(`unknown`). 조용히 꺼지는 배선은 배선이 아니다.
★ **기한을 미루려면 결정문의 `deadline:` 한 줄을 고친다** — 코드로는 못 미룬다.
`verify_decision_tools` 전건 통과(대상 225 → **226**).

## ⑨ ★★★ [D-513] **내 분모가 샜다 — 그리고 수가 올라갔다.** N 이 잡았다

## ⑩ ★★ [D-514] **`verify_dead_fields` 가 거짓 빨강을 냈고, 그 빨강이 거짓 선언을 시켰다**

조율자가 찾아 넘겼다. 커밋이 이것 때문에 서 있었다.

```

                   Mark._base_manager.update_or_create(
                       model_label=…, object_id=…,
```

술어 ①은 **키워드 인자의 이름**만 봐서 `defaults` 하나를 셀 뿐, **그 사전 안의 키를 못 봤다.**
`*_or_create` 는 **그 사전으로 쓴다.**

★★ 이 거짓 빨강이 특히 무거운 이유: 이 게이트의 처방이 **「배선해라 / 아니면 죽었다고 선언해라」**인데
**둘 다 틀린 답**이었다 — 이미 배선돼 있다. **거짓 빨강이 거짓 선언을 낳는다.**

### 고침 ① — 술어 ④ 신설, **음성 둘과 함께**

`*_or_create` 의 `defaults=`(Django 5 의 `create_defaults=` 포함) **사전 키**를 쓰기로 센다.
**세 조건을 다 만족해야 한다**: ⒜ 호출이 `*_or_create` · ⒝ 키워드 이름이 `defaults` · ⒞ 값이 **사전 리터럴**.

```
★★ 출생 표본 · `update_or_create(defaults={...})` 의 사전 키는 **쓰기다**
★  음성 · 그냥 사전 · `create(defaults=…)` 의 키는 **쓰기가 아니다** (`*_or_create` 가 아니다)
★  음성 · `**{…}` 로 넘긴 사전은 **안 센다** — 모르는 것을 쓰기로 세면 죽은 필드가 살아 보인다
```

### ★★ 고침 ② — **넓히자 다른 구멍이 드러났다. 이 게이트는 모델을 못 가른다**


지우면 **진짜 미배선이 목록에서 사라진다** — 거짓 빨강이 **거짓 삭제**를 낳는 자리다.

⇒ **「살아 있다」쪽은 안 건드렸다**(놓치는 쪽으로 틀린다 · 이 게이트는 래칫이다).

```
  것인지 **못 가른다.** 그래서 「등재를 지워라」를 말하지 않는다. 면제가 아니라 **모른다는 말**이다
```

★ **조율자의 대조(「둘 중 하나만 남아야 한다」)는 이 게이트로는 성립하지 않는다**는 것을 적어 둔다 —
두 필드가 **이름이 같아서** 쓰기 셈이 둘을 못 가르기 때문이다. 숨기지 않고 판정문이 그 말을 한다.
