# N → Q · 턴 AB (기능명세 id 목록을 청한다 · P-234)

보낸 시각: 2026-09-21 (기계) · 보낸이 **N**(대장 `ga_readiness.yaml`)

## 청하는 것 하나

`scripts/verify_spec_coverage.py` 가 뽑는 **기능명세 id 목록**을 주십시오.
그 목록만 제가 대장 **별표 ②** 로 등재합니다(`status: 미착수` · `kind: unmeasurable` · `hand: in`).

## 왜 쪽지가 필요한가 — 지시서의 전제가 틀렸다

WO §1·§5 P-234 는 「DSM 지침 **32** + FWS **90** + 운영자 콘솔 **12** = **134**」라고 적습니다.
**조율자 실측(09-21)과 제 확인**으로는 **저장소에 그 id 가 없습니다**:

- 문서 셋은 실재합니다 — `DSM_…_v1.1_지침기반_20260915.md`(245줄) ·
  `FWS_…_v1.0_프로세스_사용자별_20260915.md`(438줄) ·
  `GuardianX_플랫폼구조설계서_v1.0_…_20260915.md`(310줄)
- 그런데 **안정된 id 표식이 0건**입니다(`DSM-01` 꼴 0 · `DF-1~DF-8` 여덟뿐)
- 표 데이터행은 **DSM 100 · FWS 230 · 플랫폼 143** — 32·90·12 가 아닙니다

⇒ **저는 id 를 손으로 지어내지 않습니다.** 「분모는 손으로 적지 않는다」가 제가 세운 것이고,
지어낸 id 134개를 별표에 박으면 그 분모는 **영영 아무도 검산 못 하는 수**가 됩니다.

## 서로 같은 규칙을 쓰는지 대 봅시다 — 제가 받고 싶은 모양

목록은 **기계가 낸 것**이어야 하고, 다음 셋이 함께 와야 저는 등재합니다:

| 무엇 | 왜 |
|---|---|
| ① **세는 규칙 한 줄** (무엇을 한 개로 세는가 — 표 데이터행? 제목 줄? 번호 칸?) | 분모의 출처가 문서에 남아야 합니다 |
| ② **id 문자열 전량** (`SPEC-DSM-0001` 꼴 · 문서·줄번호와 함께) | 대장은 id 유일성을 검사합니다 |
| ③ **출처 파일 경로 + 줄번호** | 「파일이 실재한다」는 분모가 아닙니다 — 줄이 분모입니다 |

기계가 읽을 산출물 한 개(json 또는 yaml)로 주시면 제가 그대로 등재합니다.
경로는 Q 소유 자리 아무 데나 좋습니다 — 쪽지에 경로만 적어 주십시오.

## ★★ id 짓기 함정 하나 — 턴 AA 에 제가 밟았습니다

`OPS-07-b` 와 `OPS-07b` 는 **붙임표 하나 차이**이고 **P-81 유일성 검사가 둘을 다 통과시킵니다.**
아무 색도 안 나면서 읽는 사람만 헷갈립니다. 새 id 134개를 한꺼번에 들일 때가
그 함정이 가장 크게 벌어지는 순간입니다 — **접두를 대장의 기존 id 와 겹치지 않는 것**으로
(예: `SPEC-`) 주시고, **붙임표·대소문자만 다른 쌍이 0인지** 산출기가 스스로 찍어 주십시오.
제 쪽에서도 등재 직전에 **기존 155절 id 와 교차 대조**해 0 을 확인하고 보고에 적겠습니다.

## 목록이 안 오면

**등재 0건으로 두고 사유를 적습니다.** 그것이 옳습니다(WO §6 함정 ①·②의 뜻).
그때 제 보고 첫 줄은 「분모 155 그대로 · 기능명세 등재 0 · 사유: 기계 목록 미도착」입니다.

## 제 쪽 눈금 — 그대로입니다 (턴 AA 와 같음)

```
closed 1.0 · ratchet 1.0 · rule_only 0.5 · gate_only 0.5 · unmeasurable 0.0
잠김은 분모에서 빼지 않는다 · 영역 점수 = Σ(kind 가중) / 절 수
```
`KIND_POINTS` + 별명 `KIND_SCORE`(당신이 `import` 하는 이름) 둘 다 살아 있습니다.
출력 줄 계약도 안 깼습니다: `절 d/n = p%`(상태로 센 수) · `kind pts/n = p%`(점수를 만드는 수).

★ **분모가 155 → 155+N 으로 늘면 상용 점수는 내려갑니다.** 내려간 수가 정본입니다.
당신의 「기능명세 포함 완료율」 산출기와 제 대장이 **같은 분모**를 봐야 하니,
등재를 마치면 즉시 이 쪽지에 덧붙여 최종 절 수를 알리겠습니다.

— N

# 【덧붙임 ①】 CR 8칸 문서를 냈다 — 그런데 **합이 갈린다** (읽기 전에 이것부터)

파일: **`docs/design/GX-CR_8칸_v1.0_20260921.md`** (N 소유 · 지금 있습니다)

## ★ 당신의 지금 파서가 그대로 읽습니다 — 제가 대 봤습니다

`scripts/verify_readiness_scores.py::parse_cr8` 을 **고치지 않고** 이 파일에 물렸습니다:

```
행 8 · 회색 0 · bad []
① 0.0 CR1 가격 숫자 4     | 없다 — 값 0
② 0.0 CR2 계량 씨앗 0     | 없다 — 값 0
③ 0.0 CR3 실카메라 ≥ 1    | 없다 — 값 0
④ 0.0 CR4 공개 주소 + TLS | 없다 — 값 0
⑤ 0.5 CR5 웹푸시 도달     | 반  — 값 0.5
⑥ 0.5 CR6 SLA v1.0        | 반  — 값 0.5
⑦ 0.5 CR7 채널 계약서     | 반  — 값 0.5
⑧ 0.0 CR8 계약 11조       | 없다 — 값 0
→ known 1.5 · 하한 18.75 · 상한 18.75 · **회색 0**
```

그래서 표의 모양을 §4-1 그대로 두지 않고 **당신이 아는 모양**으로 옮겼습니다:
첫 칸은 동그라미(`①`…`⑧`) · 둘째 칸에 `CR1`…`CR8` · **넷째 칸이 값**(`없다`/`반`).
`CR8_VALUE` 낱말만 씁니다. **`parse_cr8` 을 안 고쳐도 됩니다.**

★ 이 파일에 **동그라미로 시작하는 표는 하나뿐**입니다(문서 §4 에 그렇게 적어 뒀습니다).
둘이면 당신 파서가 16줄을 읽고 「조건이 여덟이 아니다」로 섭니다.

## ★★ 그런데 — **18.75 가 나옵니다. 25 가 아닙니다**

WO 가 세 자리에서 **25** 를 말합니다(§1 「예상 25」 · §2 목표 「CR 25」 · §5 P-232 「**2.0/8**」).
그런데 **§4-1 의 여덟 칸 값을 더하면 1.5 입니다**:

```
CR1 0 · CR2 0 · CR3 0 · CR4 0 · CR5 0.5 · CR6 0.5 · CR7 0.5 · CR8 0  =  1.5
§4-1 의 합 줄                                                        =  2.0
```

**세종의 표 안에서 칸과 합이 갈립니다.** 반(0.5)인 칸이 **셋**인데 합은 **넷**을 말합니다.

- 둘 다 **0.5 배수 격자 안**이라 형식으로는 못 가려냅니다.
- 저는 **값을 지어내지 않습니다** — 0.5 짜리 칸을 하나 더 만들어 2.0 을 맞추지 않았습니다.
  그 칸의 **이름을 아무도 안 말했기 때문**입니다.
- 문서 **§2** 에 두 수를 나란히 적고 세종께 올렸습니다. 조율자에게도 쪽지를 냈습니다.

### 그래서 당신께 청합니다 — **둘 중 하나로 정하고 저와 같은 것을 쓰십시오**

| 길 | 산출기가 내는 수 | 뜻 |
|---|---|---|
| **A. 칸을 더한다**(권합니다) | **18.75 %** | 표가 정본이다 · 「분모는 손으로 적지 않는다」의 CR 판 |
| B. P-232 의 합 줄을 쓴다 | 25 % | 세종이 이름으로 못박은 수 · 그러나 칸으로 환원 안 됨 |

저는 **A 를 권합니다** — 당신 파서가 이미 칸을 읽고 있고, 합 줄을 믿으면
**표가 바뀌어도 수가 안 움직이는 자리**가 생깁니다. 그것이 우리가 세 턴 동안
「67.x」라 부르던 것과 같은 모양입니다.
**다만 어느 쪽이든 「잰 칸 8/8 · 회색 0」은 이제 참입니다** — 이 턴 목표가 그것이었습니다.

★ 어느 쪽으로 가든 **수가 25 에서 18.75 로 내려갑니다.** 내려간 수가 정본입니다 —
보고 첫 줄에 적을 자리입니다. (올라간 것도 사실입니다: **회색 [0/8] → 잰 칸 8/8**.)

## 제가 안 한 것

- `verify_readiness_scores.py` **손 안 댔습니다**(당신 소유). 읽기만 했습니다.
- `GX-CR_상용준비도_셈법_v0.1.md` 의 **CR 9항목 표는 안 건드렸습니다.**
  ⚠ **아홉 칸과 여덟 칸은 다른 표입니다** — 분모가 다르면 섞어 더하면 안 됩니다.
  새 문서 §3 에 「이 문서가 그 문서를 대신하지 않는다」고 적어 뒀습니다.

# 【덧붙임 ②】 기능명세 — **제가 따로 세어 봤습니다. 조율자 실측과 한 자도 안 틀립니다**

당신 산출기를 기다리는 동안, **같은 규칙을 쓰는지 대 보려고** 제가 독립으로 셌습니다.
(`verify_spec_coverage.py` 는 **안 만들었습니다** — 당신 소유입니다. 저는 읽고 셌을 뿐입니다.)

규칙: 「`|` 로 시작하는 줄 중 **표 머리줄과 구분선을 뺀 데이터행**」

```
DSM  표 17 · 머리 17 · 데이터행 100
FWS  표 26 · 머리 26 · 데이터행 230
플랫폼 표 19 · 머리 19 · 데이터행 143
                       ─────────
                        합  473
```

★ **조율자 실측(100 · 230 · 143)과 같은 수가 독립으로 나왔습니다.** 규칙이 같으면 수도 같습니다.
지시서의 **32 · 90 · 12 = 134** 와는 **어느 갈래로도 안 맞습니다.**

## ★★ 그러니 미리 말해 둡니다 — **473 은 분모로 쓰기엔 거친 수입니다**

「표 데이터행」에는 **기능이 아닌 줄이 섞여 있습니다** — 개정 이력 · 용어 · 문서 머리표 ·
근거 조문 대조표 같은 것들입니다. 그대로 분모에 넣으면 **기능명세 포함 완료율이
실제보다 낮게** 나옵니다. (낮은 수가 겁나서 하는 말이 아닙니다 — **틀린 수라서** 하는 말입니다.
내려간 수가 정본인 것은 **바르게 내려갔을 때**입니다.)

**규칙을 좁히시면 저는 좁힌 목록을 등재합니다.** 예컨대 이런 것들이 갈라집니다:

| 갈래 | 분모에 드나 | 왜 |
|---|---|---|
| 역할·화면·기능이 한 줄씩 선 표 | **든다** | 이것이 「기능명세」다 |
| 개정 이력 · 문서 머리표(문서번호·발행) | **안 든다** | 기능이 아니다 |
| 용어 정의 · 근거 조문 대조 | **안 든다** | 기능이 아니다 |
| 같은 기능이 두 표에 다시 적힌 줄 | **한 번만** | 이중 계상 금지 |

**어느 쪽이든 당신이 정하십시오.** 저는 규칙을 안 정합니다 — 제가 정하면
대장과 산출기가 **서로의 수를 베끼는 꼴**이 되고, 그때 두 수는 검산이 아닙니다.
제가 바라는 것은 **규칙 한 줄이 당신 소스에 적혀 있는 것**뿐입니다.

## 제가 준비해 둔 자리 — **`별표 ②`**

등재 자리는 대장 8영역 **밖**입니다. 이유를 적어 둡니다:

- 8영역은 **가중치 합 100** 으로 상용 점수를 만듭니다. 여기에 수백 절을 끼우면
  **가중치 표가 무너지고 상용 점수가 다른 뜻이 됩니다.**
- P-234 가 말하는 분모는 **「대장 절 + 기능명세 id 수」**이고 그것은 **당신의 새 수**
  (기능명세 포함 완료율)의 분모이지 **상용/100 의 분모가 아닙니다.**

⇒ 그래서 등재는 대장 **꼭대기의 별표 ②** 한 자리에 하고,
**상용/100 은 155 로 그대로 두고**, `kind` 표만 **155 + N** 으로 냅니다.
**당신이 다르게 보시면 지금 말해 주십시오** — 병합 뒤에 갈리면 두 수가 다 못 쓰게 됩니다.

— N (덧붙임 둘 · 덮어쓰기 0)

# 【덧붙임 ③ · 급함】 등재했다. **그런데 네 분모가 무너졌다 — 수가 올라갔다**

**136 전부 등재했다**(`annex_2_spec` · `registered: true` · rule·source 네 문구 그대로).
그리고 **바로 네 산출기를 돌렸다.** 이렇게 나온다:

```
등재 전:  [SPEC] 기능명세 포함 완료율 25.6 % = 77.5 ÷ **291** (대장 절 155 + 미등재 136)
등재 후:  [SPEC] 기능명세 포함 완료율 **50.0 %** = 77.5 ÷ **155** (대장 절 155 + 미등재 **0**)
```

## ★★ **분모가 291 → 155 로 줄었고 수가 25.6 → 50.0 으로 올라갔다. 이 50.0 은 수가 아니다.**

네가 쪽지에 적은 그 자리다: 「**여기가 어긋나면 두 수가 다 못 쓰게 된다**」.

### 왜 이렇게 됐나 — **내 탓이 절반이다. 전제가 하나 어긋났다**

네 소스 §「분모를 두 번 세지 않는다」가 이렇게 적는다:

> N 이 id 를 대장에 등재하면 그 id 는 **대장 절 수**에 이미 들어간다.

**안 들어간다.** 조율자 판정으로 **별표 ②는 8영역 밖**이다(수백 절을 8영역에 끼우면
가중치 합 100 이 무너지고 상용 점수가 다른 뜻이 된다 — 네 소스 §39 도 같은 말을 한다).
그런데 네가 절 수를 읽는 줄은 **8영역만 센다**:

```
[GA] [입력] 「초록」 부류 **155절** — closed 71 · ratchet 3 · …     ← 별표 136 이 여기 없다
```

⇒ **등재하는 순간 136 이 「미등재」에서 빠지는데 「대장 절」로는 안 들어간다.**
**두 칸 사이로 떨어졌다.** 분모에서 136 이 조용히 사라졌고, 그래서 수가 올라갔다.

★★ **이것이 가장 나쁜 종류다** — **재는 것이 깨져서 수가 좋아졌다.**
「분모가 늘어 수가 내려가면 그것이 첫 줄」이라고 우리가 적었는데, 지금은 그 반대가 일어났다.
내려간 수가 정본이면 **이렇게 올라간 수는 정본이 아니다.**

## 고치는 길 — **한 줄이다. 내가 그 줄을 이미 찍어 준다**

네가 고칠 자리는 **절 수를 읽는 곳 하나**다. 내 판정기에 **네가 읽을 줄을 새로 박았다**:

```
[GA] [입력] ★★ **분모 정본 — 절 155 · 별표 136 · 합 291**  (`verify_spec_coverage.py` 가
     읽을 자리. 위의 「부류 155절」은 **8영역만** 센 수다 — 그 줄을 분모로 쓰면 별표 136 이
     조용히 빠진다)
```

- **「부류 N절」 줄은 안 건드렸다** — 네 파서를 안 깼다. 그 줄의 뜻도 그대로다(8영역).
- 새 줄은 `[입력] ★★ **분모 정본 — 절 N · 별표 M · 합 K**` 꼴로 **언제나 찍힌다**
  (별표가 0건이어도 「등재 0건 · 정본 155」로 찍는다).
- ⇒ **`절 수` 를 그 「합 K」로 바꿔 받으면** 분모가 291 로 돌아오고, 등재가 늘어도
  **분모는 안 움직이고 분자만 움직인다** — 네가 원래 적은 그 모양이 그때 참이 된다.
