**파일**: `backend/common/migrations/0001_audit_logger_name_index.py`
**표는 빌리고 코드는 안 만진다** — `logger_auditlogs` 는 dj-core 의 표(§0.4)이고,
그 앱(site-packages)에 마이그레이션을 끼우면 **패키지를 올리는 날 사라진다.**
우리 앱이 **남의 표에 인덱스만** 만든다. `dependencies=[("logger","0001_initial")]` 은
**읽기 의존**이다. dj-core 파일 **0줄** (`forbidden-zone` 게이트 통과).

| 요구 | 어디에 | 왜 |
|---|---|---|
| `atomic=False` | `Migration.atomic` | CONCURRENTLY 는 트랜잭션 안에서 못 돈다 — 아니면 **배포 한가운데서** 죽는다 |
| `IF NOT EXISTS` | `FORWARD_SQL` | 이미 있는 DB 에서 **no-op** |
| 역방향 `DROP INDEX … IF EXISTS` | `REVERSE_SQL` | 되돌릴 수 있는 변경만 둔다 |
| 모델 상태 안 건드림 | `state_operations` 없음 | 남의 선언을 들면 dj-core 올리는 날 **두 선언이 어긋난다** |

**눌러서 본 것**
- **있는 DB 에서 no-op**: `django_migrations` 에 `common|0001|2026-09-20 06:50:30+00` ·
  인덱스 **하나** · `indisvalid=t · indisready=t` · 5,040 kB.
- **정합**: `verify_migrations` **exit 0** — 미반영 **0** · 미적용 **0** · 양성 대조 둘 다 작동.
  ★ 「미반영 0」이 `state_operations` 를 안 둔 값이다(makemigrations 가 다시 만들라고 안 한다).
- **빈 DB 에서 태어난다**: 새 DB `test_gx_f_mig` 를 **실 마이그레이션**으로 세우니
  260개 적용 뒤 인덱스가 **이미 서 있고 성하다**(`indisvalid=t`). — 스테이징이 그 경우다.
- **인덱스가 실제로 든다** [F 재측 · 표가 더 커진 뒤]:
  `Index Scan using gx_audit_logger_dt_idx` · 240행 직행 · **0.825 ms** ·
  버퍼 `hit=75 read=8`. 전에는 seq scan · 35.4 ms · `hit=12,166 read=6,281`.
  ★ 표가 **130,499 → 147,484행**으로 **늘어난 뒤에도** 0.8ms — 인덱스가 이 질의를
  **표 크기에서 떼어 냈다.**

**시험**: `backend/tests/test_f_audit_index_migration.py` — **9 passed · 건너뜀 0**
(280.99s · 새 DB 를 지우고 실 마이그레이션 260개로 세운 뒤). 규격 5건(DB 없이) +
진짜 DB 4건(태어남 · **성함** · 두 번 걸어도 no-op · 되감았다 다시 걺).
되감기 시험 뒤 **개발 DB 는 그대로**(`indisvalid=t` · 5,064 kB) · 시험 DB 는 치워졌다.
`sqlmigrate` 가 양쪽을 다 낸다 — 역방향이 **말로만** 있는 것이 아니다.
⚠ **`--nomigrations` 로 돌리면 이 마이그레이션이 아예 안 돈다** — 그때는 초록이 아니라
**건너뜀**이 되게 `_migrations_ran()` 으로 먼저 가른다. 건너뛴 것은 통과가 아니다.
⚠ 실패한 CONCURRENTLY 는 **INVALID 인덱스**를 남기고 `IF NOT EXISTS` 는 이름만 보므로
그 찌꺼기도 「있다」로 읽는다 — 그래서 `indisvalid` 를 **따로** 잰다.

**성장률 첫 수 (OPS-18 이 읽을 자리)** [실측 09-20]
```
전체 147,484행 · 324 MB (본문 165 + 인덱스 107) · 새 인덱스 5,040 kB
하루 평균 12,383행 · 17 MB   가운데 11,173행   최대 19,864행(09-19)   잰 날 5일
```
★ **운영의 수로 읽지 말 것** — 여기는 개발 기계이고 이 행의 상당수는 **우리가 게이트·
시험·부하를 돌려서** 생겼다(나만 이 턴에 HTTP 2,658 요청 · 요청마다 감사 한 행).
운영 수를 내려면 **요청 수 대비 행 수**로 재야 하고 **아직 안 쟀다.**
★ 그래도 방향은 말한다: 하루 1만~2만 행 = **한 달 30만~60만 행**. 인덱스 없던 시절
이 질의는 **행 수에 비례**했다 — **가만히 두면 다시 빨개지는 자리**였고 인덱스가 그 비례를 끊었다.

**안 한 것**: 보존 정책은 안 건드렸다 — 인덱스는 **읽기를 빠르게** 할 뿐 **표가 자라는
것을 안 막는다**(하루 17 MB). 줄이려면 보존/파티션이고 그건 이 절이 아니다(OPS-18 에 수만 넘긴다).
