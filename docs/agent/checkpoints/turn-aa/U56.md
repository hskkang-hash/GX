# 차선 U56 — 기관 관리자 · 연계 (턴 AA · 2026-09-21 17:38~18:2x KST)

WO-GX-20260921-03 파 1 턴 1 「고객 화면에서 시험 장치를 걷어낸다」 · 브랜치 `turn-q`

**한 줄**: 「받는 사람 4명」 초록은 **거짓이었고**, 지금은 빨강이다 — 실측으로 확인했다.
API 키의 표식 칸은 **없었고, 만들 수 없었다**(dj-core) — 없다고 적고 **만드는 자리**에 달았다.
인수 메뉴 넷은 **역할 전수의 `RoleMenu` 에 들어 있었다** — 사람을 정했든 아니든 뗀다.

## ① 초록 배지 — **거짓 초록이었다. 실측으로 확인했다**

### 무엇이 거짓이었나

```python
# 전 (turn S~Z · backend/kernels/k2_notify/rule_admin.py:248)
"critical_blocked": critical.recipient_count == 0,
```

같은 파일에 **이미 옳은 판정이 있었다**:

```python
@property
def reaches_people(self) -> bool:
    return self.recipient_count > 0 and bool(self.human_channels)
```

등급 표는 `reaches_people` 로 그리고 **배지만 다른 식으로 쟀다.** 판정식이 두 벌
(D-212)이었고, 두 벌은 갈렸다. 그래서 한 화면이 두 말을 했다.

### 고친 것

```python
# 후
"critical_human_channels": list(critical.human_channels),
"critical_blocked": not critical.reaches_people,
"critical_block_reason": _critical_block_reason(critical),   # 서버가 쓴 한국어
```

`_critical_block_reason` 은 **두 사유를 가른다** — 다음 손이 다르기 때문이다(P-221):
「사람이 없다」는 역할에 사람을 넣어야 풀리고, 「채널이 사람에게 안 간다」는 규칙의
채널을 바꿔야 풀린다. 한 문장으로 뭉치면 운영자가 엉뚱한 쪽을 고친다.

### 고친 뒤 **실제로 어떻게 뜨는가** — 실측

```
[실측 2026-09-21 18:0x · ORM · notify_rule_overview(scope=thanh@ETRI-Group)]

  NotificationRule (ETRI-Group) 전수 9건 — **채널이 전부 ['log']** (훈련 채널)
    #9  critical  fire_user            ['log']  켜짐
    #10 critical  operator             ['log']  꺼짐
    #11 critical  fire_admin           ['log']  켜짐
    #12 critical  view_only_-_anyang   ['log']  켜짐
    #13~#15 warning · #16~#17 info — 전부 ['log']

  critical_recipient_count = 4
  critical_human_channels  = []          ← 사람에게 닿는 채널 0
  전(前) critical_blocked  = False       ← **초록** 「심각 경보를 받는 사람 4명」
  후(後) critical_blocked  = True        ← **빨강**
  후 사유 = "심각 규칙이 가리키는 사람은 4명 있지만, 그 규칙의 채널이 사람에게
             닿지 않는 채널뿐입니다(훈련·검수용). …"

  등급 표 세 줄 — 전·후 모두 reaches=False (info 14명 · warning 15명 · critical 4명)
```

**⇒ 고친 뒤 이 테넌트의 화면은 빨강이다.** 세종이 본 「초록 + 세 줄 빨강」의 모순은
사라졌고, 빨강이 그 이유를 같은 줄에 말한다. 초록으로 되돌리는 길은 하나뿐이다 —
심각 규칙의 채널에 `email` 을 넣는 것. 그것은 고객의 손이지 우리 코드가 아니다.

★ 초록에도 **닿는 채널 이름을 적게** 했다(`… · email 로 닿습니다`). 「4명」만으로는
  그 4명이 무엇으로 받는지 알 수 없고, **알 수 없는 초록은 다시 거짓이 될 자리**다.

★ **저장 문의 409 는 안 넓혔다.** `save_rule` 은 여전히 「심각 수신자 0명」만 거절한다.
  즉 지금은 **배지가 저장 문보다 엄격**하다. 안전한 방향(더 빨강)이고, 쓰기 경로를
  같은 턴에 넓히면 기존 시험 100건의 계약이 바뀐다. **다음 턴 후보로 적는다.**

## ② 역할 표시명 — 사전 넷 · **사전에 없는 코드는 지어내지 않았다**

새 파일 `frontend/src/features/dsm/roleNames.ts`:

## ③ API 키 표 — **표식 칸이 없다. 그 사실을 적고, 만드는 자리에 달았다**

### ⚠ 먼저 **없다고 적는다**

```
[실측 2026-09-21 17:5x · apikey_account.APIKey 칸 전수]
  id · name · prefix · key_hash · user · created_at · expires_at ·
  is_active · last_used · usage_logs

  data_source 없음 · track_id 없음
  그리고 이 모델은 **dj-core 다** — `backend/apikey_account/` 는 저장소에 없다
  (설치된 패키지). §0.4 로 그 표에 칸을 **못 더한다.**
```

### 그래서 표식을 **만드는 자리**에 달았다 (이름으로 거르지 않았다)

```
kernels/k5_trust/inbound_keys.py
  DATA_SOURCES = (live · probe · seed · drill)      · 기본 live · 모르는 값은 ValueError
  data_source_tag(src) → " [data_source=probe]"     · live 는 표식 없음(기본값이 정본)
  issue_key(..., data_source="live")                · **발급 순간**에 이름 꼬리에 쓴다
  _data_source_of(name)                             · **우리가 쓴 정해진 모양**만 읽는다
  _strip_markers(name)                              · 화면에는 표식을 떼고 보여 준다
  rotate_key                                        · 회전해도 **출처를 잃지 않는다**
  inbound_key_facts                                 · 고객 면에서만 거른다 + 뺀 수를 낸다
  list_keys                                         · **한 줄도 안 뺀다**(운영·감사의 면)

apps/dsm/api.py  POST /settings/api-keys?…&data_source=probe   · 기본 live · 모르면 400
```

**왜 이름이 아닌가**: 「이름에 gate 가 들어가니 우리 것」은 추측이다. 손님이 제 연계를
`anyang-gateway` 라 부르는 날 그 손님 키가 조용히 사라진다. `common/billing_marks.py`
머리말이 계정 접두(`username__startswith="gxseed"`)로 같은 길을 이미 금지했다(D-280).

**왜 이름 꼬리표는 되는가**: 이 파일이 이미 같은 §0.4 제약에서 `ROTATED_SUFFIX` 를
만들어 쓰고 있었다(`_status` 가 그것을 읽는다). 차이는 **「우리가 썼다」**이지
「이름이 그렇게 생겼다」가 아니다. 표식은 정해진 모양이고, 화면은 그것을 **떼고** 보여 준다.

### 실측 — 게이트 키 **18건**

```
[실측 2026-09-21 17:5x · ETRI-Group 키 21건]
  p118-gate    15건   ← verify_click_completes U6#1
  onb-U6-*      3건   ← measure_onboarding_t
  key2 · key3   3건   ← 고객의 키로 보임
  살아 있는 키 18건 / 전체 21건
```

⚠ **지금 이 18건은 표에서 안 빠진다.** 표식은 **이제부터 발급되는 키**에만 붙기
때문이다. 표식 없는 키는 `live` 로 읽힌다(그것이 규약이다 — 「모르면 숨긴다」로 두면
표식 안 단 **고객** 키가 사라지고, 사라진 것은 안 보인다).

빠지게 하려면 둘 중 하나가 필요하고, 둘 다 제 손 밖이다:
- **차선 A** 가 `&data_source=probe` 를 U6#1 에 붙인다(쪽지 ③) → 다음 턴부터 자동으로 빠짐
- **대표**가 옛 18건의 소급 표식을 결정한다(쪽지 ④) → 청구·화면 근거 변경이라 대표

★ **뺀 수를 숨기지 않는다**: 화면에 「시험·점검용으로 GuardianX 가 발급한 키 N건을
  이 표에서 뺐습니다」 경고 줄이 뜬다(`inbound_hidden_by_marker`). 조용히 빼면
  「키 3건」과 「3건인데 18건을 숨겼다」가 같은 그림이 된다.

## ④ 키 상태 — 「사용 중 / 만료 / 폐기 / 교체됨」

`typed` 는 개발 어휘다(표 ② 5값 · D-328). 옮기는 판정은 **서버 한 곳**이다
(`_status_label` · `STATUS_LABELS`) — 화면이 제 손으로 옮기면 두 벌이 되고, 갈리는 날
「폐기」가 「사용 중」으로 보인다.

| 기계 어휘 | 고객의 말 | 근거 |
|---|---|---|
| `typed` · `verified` | **사용 중** | 발급됐고 살아 있다(쓰인 적 유무는 우리 사실이지 고객 사실이 아니다) |
| `absent` + 만료일 지남 | **만료** | 재발급이 다음 손 |
| `absent` + 사람이 끔 | **폐기** | 되돌리지 않는 것이 다음 손 |
| `rotated` | **교체됨** | 후속 키가 있다 |

★ `absent` 를 **한 낱말로 안 뭉친다** — 만료와 폐기는 다음 손이 다르다.
★ 기계 어휘를 **안 버린다** — 응답에 `status` 가 그대로 남고, 화면은 그것을 `title` 에 둔다
  (판정기·로그가 읽을 것이 없어지면 안 된다).

## ⑤ 인수 메뉴 넷 — **뗐다. 라우트는 그대로다**

### 왜 허용 목록만으로 모자랐나 — **안 걸리는 역할이 있었다**

`roleNav.ts` 의 `NAV_ALLOW` 는 허용 목록이라 넷이 애초에 없다. 그런데
`RoleNavFilter` 는 **`bucketOf` 가 사람을 정했을 때만** 돌고, 모르는 역할에서는
아무 일도 안 한다(빈 사이드바는 사고다). 그리고 —

```
[실측 2026-09-21 17:5x · menu.RoleMenu · 역할 14종 · dj-core]
  /operation-settings        14/14 역할에 들어 있다
  /report-template           14/14 역할에 들어 있다
  /roles                      6/14 역할
  /configuration-management  menu #6 · `Admin `(#2) 의 자식

  표에 있는 역할   fire_user · fire_admin · operator · surveillance_operation ·
                  surveillance_order · view_only_-_anyang · admin       (7종)
  표에 없는 역할   superuser · user · order · tenant_admin_4 ·
                  delivery_operation · delivery_order · delivery_admin ·
                  drone_robot_user · drone_robot_admin                   (9종)
```

**표에 없는 역할로 들어오면 인수 사이드바가 통째로 뜨고 거기 넷이 들어 있다.**
ETRI-Group 에 그런 계정이 실재한다 — `order_*` · `gxprobe_*`(role `user`) ·
`gxprobe_q`(role `tenant_admin_4`).

### 고친 것 — `NAV_ACQUIRED_HIDDEN` + `hideAcquired()`

| 뗀 것 | 경로 | dj-core 행 |
|---|---|---|
| 운영 설정 | `/operation-settings` | menu #82 |
| 구성 관리 | `/configuration-management` | menu #6 |
| 역할 | `/roles` | menu #5 (『역할 관리』) |
| 보고서 서식 | `/report-template` | menu #95 · #106 |

- **사람을 정했든 아니든** 뗀다(`RoleNavFilter` 의 `bucket === null` 가지에도 건다).
  줄 넷을 떼도 사이드바는 안 빈다 — 남는 줄이 열 개가 넘는다. 사고가 아니라 결정이 된다.
- **지우지 않았다.** dj-core `Menu`·`RoleMenu` 행도, 라우터의 라우트도 그대로다.
  U0 은 주소로 그대로 들어간다. 권한은 서버가 판정한다(SEC-11a · P-105).
- 자식을 다 뗀 마디 중 **제 경로가 없는 마디**도 뗀다 — 눌러도 아무 데도 안 가는 줄이다.
- ⚠ **`/device` 는 안 뗐다** — 드론 장비 등록은 FWS 쪽 자산이고 우리 시험 장치가 아니다.
