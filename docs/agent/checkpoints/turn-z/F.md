## 1. 조율자 진단의 한 곳을 고쳐 적습니다 — **원인이 하나가 아니라 둘입니다**

조율자께서 「세 자리 전부 읽기이고, 게이트는 **SQL 을 상수로 못 읽어서** 쓰기로 센 것」이라

```

220 이 해석된 모습 그대로:

```

`any(v in sql.upper() for v in SQL_WRITE)` 로 **부분 문자열**을 봅니다

★ 이것은 「모르면 세는 쪽에 둔다」가 **아닙니다.** 게이트는 이 SQL 을 정확히 읽었고,
  `select … from` 으로 시작하는 것도 보이는 자리에서 **CREATE 라고 판정**했습니다.
  보수성이 아니라 **오독**입니다 — 그래서 저는 이것을 「게이트도 옳다」로 적지 않습니다.

**지금 세어지는 쓰기 11건 중 6건(55%)이 거짓 양성이고, 제 파일만의 문제가 아닙니다.**

## 3. 제 잘못이었던 267 — **고쳤습니다**

`_explain(cur, sql, params)` 가 SQL 을 **매개변수로** 받아 이었습니다.
매개변수는 AST 가 따라갈 수 없습니다 — **게이트가 못 읽게 쓴 것은 제 쪽이 맞습니다.**

→ 세 질의를 **EXPLAIN 까지 붙인 모듈 상수 셋**으로 올리고(`SQL_EXPLAIN_INDEXED` ·
`SQL_EXPLAIN_CHAIN_ALL` · `SQL_EXPLAIN_PAGE`), `_explain` 은 **이름으로 고르는 분기**가
됐습니다. 사전에 담으면 AST 가 다시 못 읽으므로 **분기를 보이게** 뒀습니다.

그리고 「읽기만 한다」는 머리말의 약속을 **검사로** 바꿨습니다 — `--self-test` 가
**제 소스를 AST 로 다시 읽어** ① 모든 `execute` 의 SQL 을 상수로 읽을 수 있는지
② 전부 `select`/`explain` 으로 시작하는지 매번 셉니다. 자기시험 **10/10 → 14/14**.

★ **그런데 이 고침만으로는 통과하지 못합니다. 오히려 수가 늘었습니다.**
  267 이 읽히게 되자 그 SQL 안의 `create_datetime` 이 보여서 **쓰기 3 → 5건**이 됐습니다.
  조율자께서 주신 방향(「게이트가 읽을 수 있게」)을 **그대로 따랐더니 더 막혔습니다** —
  이 사실을 숨기지 않고 적습니다.

  | | 쓰기 판정 |
  |---|---|
  | 고치기 전 | 5건이 아니라 **3건**(writes 2 · unknown 1) |
  | 267 을 읽히게 한 뒤 | **5건** (전부 `create_datetime` 때문) |
