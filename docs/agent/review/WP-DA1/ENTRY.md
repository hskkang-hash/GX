## 0. 이 WP 를 왜 지금 여는가 (WP-2 와의 관계)

지시서 §5 Code 지시가 넷을 준다: ① WP-2 계속 최우선 ② WP-DA1 등재 + 문서 산출물만
③ 코드(WP-DA2)는 WP-2 EXIT + 대표 승인 후 ④ 로봇 어댑터는 티켓 만들지 않는다.

**WP-2 는 지금 대표 판정 대기로 코드 전진이 막혀 있다** — 652 라우트 확대는 W0-13 백필
뒤이고(D-254), 그 백필은 `P-W0-13-1` 대기다. W0-18 은 `verify-pending` 이며 P-W0-18-1/2/3 이 열려 있다.
즉 **WP-2 를 앞지르지 않으면서 지금 할 수 있는 일이 정확히 이 WP** 다.

AGENT_LOOP v4.1 은 "WP 두 개를 동시에 열지 않는다"고 규정한다. 이 WP 는 그 규정의 예외를
요청한다 — 근거는 ① 지시서 §5 가 "WP-2와 병행"을 명시했고 ② 산출물이 **코드 0줄**이라
WP-2 의 작업 트리와 충돌면이 없다는 것이다. **승인 사항 1번**으로 올린다.

## 3. 전제 검증 — 지시서와 실측의 차이 **4건** (D-210)

**전제가 통째로 틀린 티켓이 있는가?** ☐ 없음 · ☑ **있음 — 아래 4건. 전부 문서에 반영·기록했다.**

### 3-1. "5상태"는 재난 상태가 아니라 **화면 상태**다 → P-DA-4

지시서 §3·§6 은 "5상태 100%"로만 적었다. 계약 원문은 **"5상태(기본/로딩/빈/오류/권한없음)"** 다.
**이 문서의 초안이 실제로 재난 5단계로 오독했다가 계약 대조에서 잡혔다.**
오독한 채로 갔으면 F-09 를 통째로 잘못 설계했을 것이다. 재난 등급은 F-04 의 **3종**(주의·경계·심각)이다.
→ DA-01 §0-1 · DA-03 §0 에 반영. **이번 오독은 지시서 작성자가 아니라 에이전트 자신의 것이다.**

### 3-2. U 매핑이 한 칸 밀렸다 → P-DA-1

지시서 §1: "U1↔F-11 보고서 · U2↔F-10 알림". 정의 원본(상품화 개발방안 §2):
**U1=이벤트 증거화 · U2=보고 자동화**. 같은 지시서의 v2.1 커널 절은 **원 정의와 맞다**.
D-246 도 "AI 이벤트 센터(WP-3 · U1)"로 원 정의를 쓴다. → **원 정의를 따랐다** (DA-01 §3 · DA-04 §0).

### 3-3. `ReportTemplate` 에 테넌트 격리가 없다 → P-DA-3

`BaseModel` 상속이라 모델 레벨 group 격리가 없다. W0-14c 가 핸들러 문지기를 붙여 HTTP 표면은
막았으나 모델·매니저는 그대로다. **F-11 이 이 위에 얹힌다.** 에스비 채널은 고객사별 분리가 전제다.
기본값 권고: **C — 격리 시험 레지스트리에 등록만 지금**(전환은 K4 착수 시 백필과 함께).

### 3-4. "U1~U4 티켓"이라는 표현 — U 는 티켓이 아니라 WP 묶음이다

지시서 v2.1 은 "tickets.yaml U1~U4 티켓에 kernel 필드 추가"라 적었으나 `U*` ID 티켓은 0건이다.
U 는 상품화 2단계의 **WP 묶음**이고 D-246 이 이미 그렇게 쓴다.
→ 실측대로 **해당 WP 의 개별 티켓 18건**에 `kernel:` 을 넣었다. 매핑은 DA-04 §4 · 검증은 스크립트.
