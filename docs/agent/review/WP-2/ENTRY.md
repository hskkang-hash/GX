## 3. 전제 검증 — 티켓 spec 과 실측의 차이

### 3-0. ★ 티켓 ID 충돌 — 기존 W2-2·W2-3·W2-4 를 덮어쓰게 되어 있다

RESUME_NEXT §2 는 신규 작업 3건에 `W2-2` `W2-3` `W2-4` 를 부여했다.
**그 세 ID 는 정본에 이미 다른 내용으로 존재한다.**

| ID | 정본 `tickets.yaml` (WP-3 소속) | RESUME_NEXT §2 가 부여한 내용 |
|---|---|---|
| W2-2 | 검출 결과 → 이벤트 수집 (중복 억제) | superuser 역할 분리·대체역할 부여 |
| W2-3 | AI 이벤트 센터 화면 (3열 콘솔) | 외부 의존 부분 실패 격리 |
| W2-4 | 오탐 피드백 통계 | 상태코드·엔드포인트 정정 |

> **그대로 적용하면 U1(이벤트 증거화)의 티켓 3개가 사라진다.** 상품화 방안 2단계의
> U1 은 정확히 이 세 티켓이다. 덮어쓰면 6주 뒤에 "U1 의 티켓이 어디 갔나"가 된다.

**제안(기계적 정정)**: 신규 3건에 **빈 번호**를 준다 — `W0-16`(역할 분리) · `W0-17`(저하 운전) ·
`W0-18`(계약 정합). 전부 R1 위생 계열이라 W0-* 대역이 의미상으로도 맞는다.
manifest total 67 → 70. **ID 부여는 정본 `spec` 영역이라 에이전트가 정할 수 없다(금지 #11).**
§8-2 로 올린다. **대표가 다른 번호를 지정하면 그대로 따른다.**

### 3-1. ★★ W0-14 는 지금 설계대로는 경로①을 막지 못한다 — 오히려 재현한다

RESUME_NEXT §2 는 이렇게 적었다:

> W0-14 · **superuser 역할이 남아 있어도 뷰에서 테넌트 스코프를 강제 (역할 우회 무력화)**

**현재 구현은 정반대다.**

```python
# common/tenant_scope.py:165  _check()
def _check(request, func):
    user = getattr(request, "user", None)
    if is_superuser(user):
        return                      # ← 통과시킨다

# common/tenant_filters.py:72  is_superuser()
def is_superuser(user):
    if getattr(user, "is_superuser", False):  return True
    roles = getattr(user, "roles", None)
    return bool(roles and any(r.code == "superuser" for r in roles.all()))
                                    # ← dj-core base.py:308 과 같은 판정

# common/tenant_filters.py:95 · 105  — filter_by_group_field / get_scoped_or_404
    if is_superuser(user):  return queryset          # ← 좁히지 않는다
```

**W0-14 의 도구 3개가 전부 dj-core 의 역할 우회를 그대로 복제해 두었다.**
착수 당시엔 그것이 옳았다 — 기존 동작을 바꾸지 않는 것이 안전했다. **지금은 그 전제가 뒤집혔다.**

→ **W0-14 는 "466개에 데코레이터 붙이기"가 아니라 "우회 판정 기준을 바꾸는 일"부터다.**
그리고 그 기준을 바꾸려면 **"어떤 superuser 가 전역인가"를 먼저 정의해야 한다** — 그것이 D-243 의
역할 분리다. 즉 **W0-14 와 역할분리 티켓은 순차가 아니라 결합돼 있다.** 실행 순서를 바꿔야 한다:

```
지시서 순서 : W0-14 → 역할분리 → W0-13
실측 기반   : 역할분리(정의) → W0-14(그 정의를 뷰가 강제) → W0-13
              └ 정의 없이 W0-14 를 먼저 하면 두 번 고친다
```

### 3-2. 상태코드 정정은 저장소 코드로 못 고친다 — 응답 후처리가 필요하다

권한거부 200 은 `core/role/permission.py:512` 가 dict 를 반환해서 생긴다. **§0.4 금지구역**이다.
따라서 W2-4(신규) 는 핸들러 수정이 아니라 **저장소 쪽 응답 후처리 계층**이어야 한다 —
`{"success": false, "status_code": 4xx}` 형태를 감지해 실제 HTTP 상태로 다시 내보내는 미들웨어.

**그리고 이것은 하위호환을 깬다.** 지금 200 을 기대하는 프론트가 있다면 그 화면이 죽는다.
지시서도 "클라 호환 영향조사 먼저"라고 적었다 — 그 조사를 **첫 작업**으로 잡는다.

### 3-3. 지시서가 옳았던 것 (기록)

- "경로① · ② 는 독립 — 각각 막는다" → **맞다.** `created_by` 를 전부 채워도 13계정엔 무효다.
- "466 일괄 부착 금지, 파일럿 1개부터" (D-241) → **맞다.** 실측 652 이므로 더욱 그렇다.
- "운영 서버·운영 DB 직접 접속 금지" → 이번 세션에서 실제로 그 선을 지켰다. 프로덕션 로그인
  시도는 자동 차단됐고, D-245 대상 복제본은 삭제했다(§9).

## 8. 사람이 해야 할 것 (승인 전)

### 8-1. P-LOCAL-2 판정 — **이것이 없으면 EXIT 조건 5 를 못 채운다**
격리 시험 픽스처가 `CoreUser.email` UNIQUE 에 걸려 5시나리오가 0/5 다. 한 줄이면 풀리지만
절대금지 #5 가 그 파일 수정을 막는다. **권고: 승인.** 근거 하나 더 붙인다 —
저장소 밖 프로브가 이미 **누출이 실재함**을 보였으므로, 이 시험을 살리면 **빨간불이 켜진다.**
픽스처 수정은 결함을 드러내는 방향이지 감추는 방향이 아니다.

### 8-2. §3-0 티켓 ID 부여 — `W0-16/17/18` 안을 승인하거나 다른 번호 지정
그대로 두면 U1 티켓 3개가 덮인다.

### 8-3. §3-1 실행 순서 — 역할분리를 W0-14 **앞**으로 옮기는 것 승인
지시서 순서(W0-14 → 역할분리)대로 가면 우회 판정 기준을 두 번 고친다.

### 8-4. (참고) D-244 보안 즉시조치 — 에이전트 소관 아님
자격증명 회전 · HTTPS · 접근 IP 제한 · 결제계정 생존 확인.
**부수 실측 1건 추가**: 운영 서버의 **9200(OpenSearch)이 인터넷에 열려 있다**(401 응답 확인).
5601(Dashboards)도 응답한다. 접근 IP 제한 대상에 이 둘을 포함하시기 바란다.

### 8-5. (참고) P-LOCAL-3 · P-LOCAL-4 는 이 WP 를 막지 않는다
각각 격리 판정 함수, 저장소/운영 드리프트 73파일. 열어 둔 채 진행 가능하다.
