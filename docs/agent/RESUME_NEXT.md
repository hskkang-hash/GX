## §1 축 선택 — ⓐ 세 번째 칸 `response_state` 신설 [판정]

Code가 낸 선택지: ⓐ 대응 축을 세 번째 칸으로 신설 / ⓑ `status`를 대응 축으로 재정의하고 판정은 `verdict`에 맡김(계약 문서 수정 동반).

**ⓐ다.** 이유 셋.
- 판정(이 탐지가 진짜인가)과 대응(누가 무엇을 하고 있나)은 **독립**이다. CONFIRMED이면서 in_progress일 수 있고, 조치 중에 REJECTED로 바뀔 수도 있다. 한 칸에 넣으면 D-293이 갈라 놓은 것을 다시 섞는다.
- `status`는 `docs/contracts/detection-event.md`에 있는 **계약 필드**다. U6(외부 연계 시스템)이 읽는다. 기존 필드의 뜻을 바꾸는 것은 래칫(D-311) 위반이다 — 기존분은 이름으로 잠근다. **필드 추가는 래칫 안이다.**
- ⓑ는 계약 문서를 고쳐야 하고, 그 순간 SDN 명세 발송분(계약 6조3항 재통지)과도 어긋난다. 상대방 대기 6절을 늘리는 일은 하지 않는다.

```
▣ P-1 대응 축 response_state (제안 → Code 정본 D-40x)
   response_state ∈ pending → acknowledged → in_progress → closed   (생성 시 pending)
   response_reason ∈ resolved | false_positive | no_action | duplicate | other   (closed일 때 필수)
   response_by · response_at · 전이 감사(who·when·from·to·reason) — 기존 감사 테이블 재사용 (D-333)
▣ 전이: 앞으로만. 되돌림은 closed → in_progress 한 가지, U2(관제팀장) 권한, reason 필수.
▣ 결합 규칙은 단 하나: verdict=REJECTED 로 바뀌면 response_state=closed, response_reason=false_positive 자동.
   그 외 status(판정 축)와 response_state(대응 축)는 서로를 건드리지 않는다. 결합을 더 만들지 마라.
▣ 화면 규칙 (D-378 「사용자에게는 같은 일이다」): W1·M1의 배지는 response_state 다. verdict는 「확인됨 / 오탐」 태그로 옆에 작게.
   사용자가 두 종류의 「종결」을 보게 하지 마라 — 「종결」이라는 말은 response_state=closed 에만 쓴다. status=CLOSED는 화면에서 「판정 종료」라 부른다.
▣ 계약 문서: docs/contracts/detection-event.md 에 response_state·response_reason 을 **추가**한다(기존 필드 무변경). 변경 이력에 P-1.
▣ 마이그레이션: 기존 이벤트는 response_state=closed, response_reason=other (이관), 단 status=NEW 는 pending. dry-run 먼저 (D-209). 이관 건수 [실측].
▣ 강제 도구: 허용 전이 3 + 되돌림 1 통과 · 금지 전이(pending→closed 직행 · closed→pending) 거절 4xx 각 1건 ·
   REJECTED→자동 closed 1건. 200 봉투 안 오류는 실패 (착시 ⑧형).
```
