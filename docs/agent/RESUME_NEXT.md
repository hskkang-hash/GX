## §0 인정 — P-1이 섰고, 시험이 설계를 고쳤다

1. **두 축이 섰다.** `status`(이 탐지가 진짜인가) 무손상 · `response_state`(사람이 어디까지 했나) 신설 · 계약 문서 무손상 · 마이그레이션 가산적(AddField 1). 되돌림 하나뿐(팀장·사유 필수). 거절 409/400/403/404를 한 코드로 묶지 않은 것 — 옳다. 「접수한 사람 없는 종결이 생기면 아무도 안 봤는데 닫힌 것과 보고 닫은 것이 같아진다」 — 이 문장을 PRD §4.1 규칙 표에 그대로 넣어라.
2. **시험 일곱이 설계를 고쳤다.** 1차판은 규칙을 `apps/dsm/`에 뒀고, AppStaysThin·TenantIsolationWrite·EntrySurfaceIsOne/Locked×5·KernelPublicSurface가 빨갰다. Code는 시험을 고치지 않고 **규칙을 K1 커널로 옮겼다.** 이것이 D-327의 뒷면이다 — **빨간 시험은 버그가 아니라 설계 지적일 수 있다. 시험을 고치지 말고 설계를 옮긴다.** (→ 원칙으로 등재, P-8과 함께)
   - 격리 탐침이 잡은 것이 핵심이다: 「남의 이벤트를 접수 확인으로 미는 것은 심어진 행보다 나쁘다」. 새 쓰기 면이 격리 탐침(WRITE_PROBES)에 없으면 격리 시험은 그 면을 모른다 — **탐침 없는 쓰기 면은 격리되지 않은 면이다.**
   - 규칙이 K1으로 갔으므로 대응 축은 **가이온 IP(계약 8조3항)** 안에 있다. DA-04 §2 K1 표에 이미 올렸다 [실측] — 계약 축에 한 줄: 「커널 표 갱신 1건, 상대방 대기 6절 변화 없음」.
3. **0행을 검증으로 쓰지 않았다.** 개발 DB 이벤트 0행 → 네 상태를 심어 이관 함수를 직접 돌렸다(D-301). 옳다. 그리고 이 0행이 다음 문제의 뿌리다(→ P-9).

## §1 묻는다 — 사유 없는 초록 하나 (P-10)

직전 턴(09-14) route-alive는 **빨갰다**(죽은 라우트 2: `/monitoring-dashboard` · `/intergrated-dashboard`, exit 1). 이번 보고는 「게이트 9종 전부 exit 0」. **왜 초록이 됐는지가 보고에 없다.** 셋 중 하나다:
- (a) 죽은 라우트 2건을 처분했다(P-6) → 처분 내용(㉮ 잇기 / ㉰ 제거, 314 분류표 근거)을 보고하라.
- (b) 시험(route-alive)이 바뀌었다 → 무엇이 바뀌었나. 시험을 고쳐 초록이 됐으면 D-327 위반이다.
- (c) 게이트 9종에 route-alive가 **빠졌다**(8→9인데 구성이 바뀜) → 그러면 「전부 exit 0」은 빨간 것을 빼고 센 초록이다.

```

   직전 턴 빨갰던 시험·게이트가 초록이 되면 보고에 「무엇을 고쳐서」 한 줄이 필수다. 사유 없는 초록은 세종이 인정하지 않는다.
   게이트 수가 바뀌면(8→9) 이름 목록 전체를 한 번 적는다 — 이번 턴에 9종 이름을 적어라. 새 1종이 무엇인지(봉투 일관성? 잰 수?).
   이번 route-alive 건은 (a)(b)(c) 중 어느 것인지 이번 보고 첫 줄에.
```
