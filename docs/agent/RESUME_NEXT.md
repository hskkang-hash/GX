## §0 인정 — 회색은 한 종류가 아니었고, 401은 도달이 아니었다

1. **회색 셋으로 갈린 것 — 인정, 그대로 대장에.** 진짜 빚 2(route-alive·secrets → 갚음) · 잘못 칠한 색 1(bypass — 잤고 알면서 SKIP → 래칫 D-311) · 빚이 아닌 것 2(model-inheritance·ui-library — 대상 0 → 「대기」 신설). 「대기」를 만들되 없애지 않은 것(P-12 ④) 옳다. 목표 「잼 ≥ 6 · 회색 ≤ 3」을 넘겼다.
2. **자격증명을 넣었더니 초록이 났다 — 이번 턴의 뿌리.** 26건 중 24건이 401인데 게이트가 exit 0. 「401 = 문지기가 섰다(살아 있다)」 규칙이, 들어가지 못한 채로 초록을 만들었다. 파일 첫머리에 「가장 나쁜 실패」라고 적어 두었는데도 막히지 않았다. Code의 고침 — **규칙이 아니라 증거로**: 로그인 뒤 익명으로 한 번 더 때려 토큰이 바꾼 것을 세고, 0건이면 판정 불가. 그러자 401 밑에 덮여 있던 `/api/media-data(/)` 500이 드러나 exit 1 — 옳은 색. 대조 실측 있이 1 · 없이 2.
   - **착시 ⑪형 등재 — 문지기형**: 거절(401/403)을 도달로 읽는다. 문지기가 섰다는 것은 살아 있다는 증거이지 기능의 증거가 아니다. 대장에 올려라.
   - **원칙**: 「적어 두는 것으로는 안 막힌다 — 증거로 막는다.」 주석은 게이트가 아니다. 이 문장을 `verify_*` 공통 머리말에 넣어라.
3. **시크릿 — 어디를 보는가가 판정의 절반.** 파일 면 19 · 이력 면 1. 발견 1건(`example_frontend.html:813` 하드코딩 CSRF 토큰)은 유출이면서 기능 결함(값이 차 있어 대체 경로 세 갈래가 한 번도 안 돎) — 비우니 둘이 함께 고쳐졌다. 측정기 결함 둘(허용목록 ~100KB 넘으면 조용히 꺼짐 · `check-ignore` CRLF)도 D-350대로 잡았다. **한 가지 더**: 그 CSRF 값이 실제 환경에서 발급된 것이었는지 확인하고, 그렇다면 무효화(D-004 — 이력 재작성 금지, 값 무효화). 예시 파일이라도 같다.
4. **오탐 ① 「돌아가는 듯하다」는 추정이었다 — 인정.** `review_event`는 `response_state`를 건드리지 않고 시드가 두 축을 각각 불렀다. 「수는 원인을 말하지 않는다」 — 이 문장도 대장에. 판정은 §1.
5. **저장소 게이트 둘이 Code의 커밋을 먼저 막았다**(`verify_tool_selftest` 출생 표본 없음 · `verify_homonyms` 맨 `api_key`). 둘 다 옳았다. 동음이의 대장이 일하고 있다.

## §1 판정 — 오탐 결합 규칙은 붙인다, 단 이벤트로 (P-16)

Code의 물음: REJECTED → response_state=closed 자동 결합을 붙이면 D-399가 가른 두 축이 다시 맞물린다. 붙일 것인가.

**붙인다. 그러나 코드에서는 맞물리지 않게.**
- 사용자에게는 같은 일이다(D-378): U1이 「오탐」을 누르고 나서 「종결」을 또 눌러야 하면 두 종류의 종결을 보게 된다 — P-1 화면 규칙이 막으려던 바로 그것.
- 코드에서는 `review_event`가 `response_state`를 **직접 쓰지 않는다.** 대신 **K1 소비자 1개**가 「verdict가 REJECTED로 바뀜」 이벤트를 받아 대응 축 전이 `→ closed / false_positive`를 부른다. 행위자 = `system:false_positive`, 감사에 남는다. 두 축의 코드는 서로를 모르고, 결합은 소비자 한 곳에만 있다.
- 역방향 없음: 대응 축은 verdict를 절대 쓰지 않는다. REJECTED가 나중에 CONFIRMED로 재판정되어도 대응 축은 그대로 closed — U2가 되돌림(closed→in_progress, 사유 필수)으로 다시 연다. 이것도 감사에 남는다.

```
▣ P-16 오탐 결합 규칙 — K1 소비자 1개 [판정]
   K1_CONSUMERS 에 등록(이미 있는 등록부 — 직전 턴 게이트가 「소비자 미등재」를 잡았다). 쓰기 면이므로 P-8: WRITE_PROBES 등록 → 격리 시험 빨감 → 구현 → 초록.
   시험 3: ① REJECTED → closed/false_positive 자동 1건 ② CONFIRMED 재판정 후 response_state 불변 1건 ③ 다른 테넌트의 verdict 이벤트에 반응하지 않음 1건(격리 탐침).
   시드 재점검: 시드가 두 축을 각각 부르던 자리는 그대로 두되, rejected 4건 중 대응 축을 직접 닫던 호출을 빼고 소비자가 닫는지 [실측].
▣ 오탐 ②③④ (같은 묶음)
   ② 판정 API — 서비스 있음·라우트 없음 → 라우트 1개 잇기(쓰기 면 → P-8). 거절은 4xx.
   ③ 오탐 종결 통지 — 알림이 나간 이벤트가 REJECTED 되면 원 수신자에게 1회. 로그 어댑터. 쓰기 면 → P-8.
   ④ 오탐률 — REJECTED / 전체(기간·카메라·시나리오) → K6 계측 1개. W1 프리셋 「지난 12시간」 요약 한 줄의 「오탐 N」이 이 수를 읽는다(P-13).
```

## §2 묻는다 — JWT 거절은 게이트만의 문제인가 (P-15)

`/api/token/pair`가 준 JWT를 dj-core가 `user.token` 없다고 거절했다(`core/auth.py:38`). 게이트는 다른 길로 들어갔다. **그러면 실제 클라이언트는 어느 길로 들어가나?** 모바일 M1~M3(다음 순서)은 로그인이 첫 화면이다. 죽은 길 위에 화면을 세우지 않는다.

```
▣ P-15 인증 경로 대장 [판정]
   docs/agent/authn_paths.md: 면(웹 UI · 모바일 M1~M3 · 외부 API U6 · 게이트 · 시드)마다 「어느 인증(세션 / user.token / JWT pair / api_key)으로 들어가나 · 실측 결과(200/401) · 근거 경로」 한 줄.
   /api/token/pair 처분: 실제 클라이언트가 쓰지 않으면 ㉰(제거, 대장에 남김). 쓰는데 거절되면 그것이 버그다 — 어느 쪽인지 [실측] 후 처분. dj-core 는 고치지 않는다(D-207) — 바깥에서 잇거나 뺀다.
   동음이의 대장 authn 항목 갱신: 「토큰」이 셋(JWT · user.token · api_key)이면 이름을 갈라라.
   M1~M3 는 이 대장이 확정한 길 하나로만 로그인한다. 무계정 링크 금지는 그대로.
   강제 도구: 대장의 각 면을 그 인증으로 1회 때려 200 [실측] — 게이트가 한 것과 같은 「증거로」.
```
