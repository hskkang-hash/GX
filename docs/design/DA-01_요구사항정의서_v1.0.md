## 0. 먼저 말할 것 — 이 App 은 대부분 신규가 아니다

착수 전 저장소를 실측했다. 결론 세 가지다.

1. **F-01~F-05 의 저장 계약은 이미 고정돼 있다.** `DetectionEvent` 모델이 실재하고
   (`backend/stream_monitors/models.py:125`), 그 스키마는 W6-2 에서 계약으로 못박혀 있다
   (`docs/contracts/detection-event.md` v1.0 · 2026-08-13 고정).
   재난 이벤트를 위해 **새 모델을 만들지 않는다.** `event_type` 에 `fire`·`smoke` 가 이미 있고
   `severity` 3종(`info`/`warning`/`critical`)도 있다. 침수·수위만 열거값 추가다.
2. **F-09 대시보드의 뼈대도 이미 있다.** `frontend/src/features/Dashboard/SurveillanceDashboard/`
   에 이상징후 개요·알림목록·지도 탐지마커·기상·드론상태 위젯이 전부 있고,
   백엔드 7개 엔드포인트(`backend/surveillance/views/surveillance_dashboard_view.py`)가 그것을 먹인다.
   F-09 는 신규 화면이 아니라 **재난 5상태로의 재배치 + 클릭→영상 3초 경로 신설**이다.
3. **그러나 F-11 보고서의 기반 모델에는 테넌트 격리가 없다.** `ReportTemplate` 은
   `BaseModel` 을 상속한다 — `BaseModelWithGroup` 이 아니다(`backend/report_template/models.py:5`).
   에스비는 **고객사별 분리**가 전제인 채널이다. 이것은 요구사항이 아니라 **선결 결함**이고
   OPEN-03 으로 올린다.

**따라서 이 App 의 실제 신규 개발은 F-04(규칙엔진) · F-05(외부 OpenAPI) · F-06~F-08(SDN 연계) 넷에 몰려 있다.**
나머지 열 건은 확장·연결이다. 일정과 견적은 이 사실 위에서 짠다.

### 0-1. 계약 원문 대조 — 상위 지시서만 읽으면 틀리는 것 3개

## 2. 기능요구 전개 — F-01 ~ F-14

표기: **FR** 기능요구 / **NFR** 비기능요구 / **AC** 인수조건(검수 판정 문장) / **재사용 근거** = 실재 파일
신규도: `확장`(기존에 붙임) · `연결`(있는 것끼리 잇기) · **`신규`**(없어서 만듦)

### F-01 화재·연기 탐지 — L3 Platform 확장 · 우선 M · 신규도 `확장`

- **FR-01-1** 스트림별로 화재/연기 탐지 모델을 켜고 끌 수 있다. 모델-스트림 결합은 이미 있다
  (`StreamMonitorAIModel`, `backend/stream_monitors/models.py:44`).
- **FR-01-2** 탐지 결과는 `DetectionEvent(event_type='fire'|'smoke')` 로 적재한다. **모델 신설 없음.**
- **FR-01-3** 스냅샷 1장을 MinIO 에 남긴다(`snapshot_path`). 원본 프레임을 DB 에 넣지 않는다(계약 불변규칙 4).
- **NFR-01-1** 중복 억제: 동일 stream+type 이 기본 10초 내 재발 시 새 행을 만들지 않고 `last_seen_at` 만 갱신
  (계약 불변규칙 3 · W2-2). **이것이 F-04 의 "5분 내 중복 알림 0"의 하부 구조다.**
- **AC-01** 시험 영상셋에 대한 성능 보고서(정탐/오탐/미탐)가 제출된다.
  ⚠ **목표 수치는 이 문서에서 정하지 않는다** — 지시서 §3 이 "1단계 합의" 대상으로 남겨 두었다 → **OPEN-01**.
- **재사용 근거** `backend/stream_monitors/models.py` · `docs/contracts/detection-event.md`

### F-02 침수·수위 탐지 — L3 Platform 확장 · M · `확장`

- **FR-02-1** `DetectionEvent.EventType` 에 침수 계열 열거값을 **추가**한다.
  계약 하위호환 조항: 필드 추가는 호환이지만 **열거값 추가는 이 계약 문서와 W2-3 색 규칙을 함께 갱신**해야 한다.
- **FR-02-2** 지점별 수위 기준선(임계값)을 설정에서 관리한다 → F-12 로 수렴.
- **AC-02** 기준선 초과 후 **30초 내** 이벤트가 생성된다.
  측정 지점: 프레임 타임스탬프(`occurred_at`) → 이벤트 행 커밋 시각. 이 두 값의 차로 잰다.
- **재사용 근거** `backend/stream_monitors/models.py` · F-12 설정 저장소

### F-03 위험구역 인명·차량 — L3 Platform 재사용 · M · `연결`

- **FR-03-1** `event_type` `person`·`vehicle`·`intrusion` 은 **이미 열거에 있다.** 추가 개발 없음.
- **FR-03-2** 위험구역(폴리곤) 정의를 재사용한다 — `today-profiles-polygon` 엔드포인트가 실재한다
  (`surveillance_dashboard_view.py:306`). 새 폴리곤 편집기를 만들지 않는다(§0.4 지도 3종 통합 금지).
- **AC-03** 구역 진입 후 **10초 내** 이벤트.
- **재사용 근거** `backend/surveillance/views/surveillance_dashboard_view.py` · `backend/surveillance/models.py`

### F-04 재난 규칙 엔진 — **L4 DSM App** · M · **`신규`**

- **FR-04-1** 규칙은 JSON 으로 정의한다: `조건(event_type·severity·구역·시간대·연속발생수) → 판정(재난등급) → 조치(F-10 수신자·F-06 QoS 요청)`.
  **재난등급은 3종 — 주의 / 경계 / 심각**(계약 [별첨 1] 기능명세서 F-04).
  `DetectionEvent.severity`(info/warning/critical)와 1:1 대응시킨다. **네 번째 등급을 만들지 않는다.**
  ★ **'심각'이 F-06 QoS 요청의 발동 조건이다** (기능명세서 F-06: "심각 등급 이벤트 발생 시").
  즉 등급 판정의 정확도가 곧 네트워크 제어의 발동 정확도다 — 규칙엔진은 표시용이 아니다.
- **FR-04-2** **무재기동 반영** — 규칙 변경이 프로세스 재시작 없이 적용된다.
  구현 방향: 규칙을 DB/설정에 두고 평가 시점에 읽는다. 코드 상수로 굳히지 않는다(D-212 정신).
- **FR-04-3** 중복 억제 2단: F-01 의 10초 억제(이벤트 레벨) 위에 **알림 레벨 5분 억제**를 얹는다.
  둘은 다른 층이다 — 이벤트는 남기되 알림만 접는다. 이벤트를 접으면 F-14 통계가 거짓이 된다.
- **AC-04** ① JSON 수정 후 **재기동 없이** 다음 이벤트부터 새 규칙이 적용된다.
  ② 동일 사건에 대해 **5분 내 중복 알림 0건**.
- **재사용 근거** 없음(신규). 단 평가 입력은 `DetectionEvent` 계약 그대로다 — **파이프라인이 바뀌어도 규칙엔진은 안 바뀐다.**

### F-05 재난 이벤트 API — **L2 연계 API** · M · **`신규`**

- **FR-05-1** OpenAPI 문서 + Webhook 구독. **외부 연동의 유일한 공식 문**이다 —
  외부 APP 이 내부 엔드포인트를 직접 부르는 경로를 만들지 않는다(Flow 5).
- **FR-05-2** 조회·확인(confirm/reject) API. `DetectionEvent.status`·`reviewed_by`·`reject_reason` 이 이미 있다.
- **FR-05-3** API Key 발급·폐기는 F-12 에서 한다. 키 값은 비밀저장소 참조로만 다룬다(D-204).
- **NFR-05-1** **p95 500ms**. 측정 지점: 서버 수신 → 응답 최종 바이트. 부하 조건은 계측 시 합의한다 → **OPEN-02**.
- **NFR-05-2** ★ **오류 계약을 지킨다.** 이 저장소는 권한거부가 `HTTP 200 + {"success":false}` 로 나가는
  구조를 가지고 있었고 W0-18 이 후처리 계층으로 승격시켰다(플래그 `API_CONTRACT_PROMOTE_ERROR_STATUS`).
  **F-05 는 신규이므로 처음부터 올바른 HTTP 상태로 낸다** — 승격 계층에 의존하지 않는다.
  근거·주의사항: `docs/contracts/api-error-and-auth.md`.
- **AC-05** OpenAPI 문서로 외부 개발자가 인증→구독→조회를 완주하고, p95 가 500ms 이하로 계측된다.
- **재사용 근거** `docs/contracts/api-error-and-auth.md` · `docs/contracts/stream-control.openapi.yaml`(서식) · `backend/third_api/`(외부연동 관례)

### F-06 SDN QoS 제어 — **L2 연계 API** + SDN(에스비) · M · **`신규`**

- **FR-06-1** F-04 가 **심각** 등급을 판정하면 SDN 컨트롤러에 QoS 상향을 요청한다 — 인터페이스 **I-1**.
  I-1 데이터(계약 §4): 카메라/드론 식별자 · 소스·목적지 · 우선순위 · 대역폭 · 유지 시간. REST(JSON) · 결과코드 수신.
- **FR-06-2** **요청과 결과코드를 전건 기록**한다. 성공/실패/무응답이 감사로그에 남는다.
- **NFR-06-1** 외부 호출은 **반드시 타임아웃을 건다** — `backend/common/external_http.py` 규약을 따른다.
  W0-17 이 타임아웃 없는 동기 호출 17건을 0으로 만든 이력이 있다. 신규 코드가 그것을 되돌리지 않는다.
- **AC-06** 이벤트 발생 후 **10초 내** 요청이 나가고 결과코드가 기록된다.
- **책임 경계** SDN 이 요청을 이행했는지는 **에스비 책임**이다(10조1항). 가이온 AC 는 "요청·기록"까지다.
- **재사용 근거** `backend/common/external_http.py` · DA-02 매핑서

### F-07 SDN 경로 우회 — **L2 연계 API** + SDN · M · **`신규`**

- **FR-07-1** 링크 장애·혼잡 시 대체 경로 전환을 요청하고 전환 확인 응답을 기록한다 — 인터페이스 **I-2**.
  I-2 데이터(계약 §4): 스트림 식별자 · 장애 링크 · 대체 경로 정책.
- **FR-07-2** 제어 결과·감사 이력은 **I-4**(SDN → GX: 요청 ID · 처리 결과 · 처리 시각)로 되받아
  F-09 화면과 F-11 보고서에 반영한다. **요청과 결과를 요청 ID 로 잇는다** — 잇지 못하면 감사로그가 반쪽이다.
- **AC-07** 링크 차단 시나리오에서 전환이 확인된다(에스비 시험환경 · 2027.1 6차 통합).
- **재사용 근거** `backend/common/external_http.py` · DA-02 매핑서

### F-08 통신두절 이벤트 — **L2→L4** · M · `연결`

## 4. 역할 5종 × 기능 권한 매트릭스

**역할 5종의 출처**: 계획서 §2.2-4 — "GuardianX **기존 4종 역할 + 재난관제 관리자 1종 신설**".
