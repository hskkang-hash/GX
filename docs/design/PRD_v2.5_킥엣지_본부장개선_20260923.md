## 2. 킥 — 대응 시계 (Response Clock) · P-21 [판정]

### 2.1 무엇인가
이벤트 하나에 **시계 하나**. 네 개의 시각을 이벤트가 스스로 기록한다 — `occurred_at`(탐지) → `acknowledged_at`(접수 확인) → `arrived_at`(현장 도착) → `closed_at`(종결). 앞의 셋은 09-15 대응 축(P-1·D-399)에 이미 있거나 전이 API가 있다 [실측: `POST /api/dsm/events/{id}/response`]. **새 모델이 아니다. 새 계산과 새 표시다.**

### 2.2 어디에 나오나 — 다섯 자리
1. **이벤트 카드**(W1): 경과 시간이 **글자 크기로 커진다** — 30초·2분·5분·8분 문턱마다 한 단계. 관제요원은 숫자를 읽지 않고 크기를 본다.
2. **이벤트 상세**(W2): 네 시각의 타임라인 + 각 구간의 담당자.
3. **모바일 M1**: 「탐지 후 N분 경과 · 아직 아무도 접수하지 않음」 한 줄.
4. **월간 보고서**(K4): 첫 표가 오탐률이 아니라 **대응 시간 분포(p50/p95)** 다. 오탐률은 둘째 표.
5. **관리자 화면**(U5): 카메라별·시간대별 대응 시간 히트맵 — 어디서 느린가.

### 2.3 약속 — 숫자로
| 구간 | 목표 [추정] | 확정 방법 |
|---|---|---|
| 탐지 → 발송 | ≤ 30초 (계약 F-10 · 이미 시험 있음 [실측]) | 유지 |
| 탐지 → 접수 확인 | 중앙값 **≤ 90초** | 파일럿 4주 실측 후 p50·p95로 확정 |
| 탐지 → 현장 도착 | **≤ 8분** (안양 관제센터↔안양천 거리 기준) | 동일 |
| 미접수 재알림 | 2분 후 U2로 승격 (D-400 재알림 N분의 N을 2로 [판정]) | 규칙 |

**규칙 하나**: 시계는 사람이 멈춘다. 시스템 자동 종결(오탐 자동 종결 D-401)은 시계에 「자동」 표기가 붙고 대응 시간 통계의 **분모에서 뺀다** — 자동 종결이 대응 시간을 좋게 만드는 착시를 막는다(D-293 정신).

### 2.4 강제 도구
`scripts/verify_response_clock.py` — 시드 이벤트 20건에 대해 네 시각의 단조 증가 · 자동 종결 분모 제외 · p50/p95 산출이 두 번 돌려 같은 수인지(QA-06). 화면 캡처는 W1 카드에 경과 시간 4단계가 실제로 렌더되는지(data_source 표기).

## 3. 엣지 3

### E1 · 확인된 알림만 보낸다 — VLM 2차 사유 + 사람 1클릭 + 알림 예산 · P-22 [판정]

**문제**: 재난안전 시스템이 실패하는 가장 흔한 이유는 탐지 성능이 아니라 **알림 피로**다(09-14 평가 ③). 오탐 표시 자리는 09-20에 섰다 [실측: `/review`]. 그러나 「왜 심각인가」를 사람이 3초 안에 알 방법이 없고, 규칙 하나가 알림 폭주를 만들어도 저장 전에 알 방법이 없다.

**설계 3층**
1. **VLM 2차 사유(설명)** — K1이 이벤트를 만들면 스냅샷 크롭을 VLM에 넘겨 **한 줄 사유 + 근거 등급(높음/보통/낮음)** 을 받는다. 예: 「굴뚝 연기로 보임 — 수직 상승, 열원 없음, 근거 보통」. **VLM은 판정하지 않는다 — `verdict`를 쓰지 않는다.** 사유는 카드에 회색 글자로 붙고, 판정은 사람이 1클릭으로 한다. NVIDIA가 자기 문서에 적은 「환각이 부정확한 판정을 낸다」 [인용]가 이 규칙의 근거다. 시간 예산 **p95 ≤ 2초** · 못 지키면 「사유 없음」 — 알림은 사유를 기다리지 않는다(30초 AC가 우선).
2. **사람 1클릭** — 진짜 / 오탐 / 보류. 키보드 `1·2·3`. 오탐 사유 enum(D-401)은 그대로. 이 클릭이 K6 오탐률의 분자이자 규칙 감도 제안(§3 E1-3)의 입력이다.
3. **알림 예산(Alarm Budget)** — 규칙 저장 전 [시험] 버튼(DA-03 §3-3)이 **최근 7일 이벤트로 시간당 알림 수를 시뮬레이션**한다. **관제요원 1인당 시간당 6건**을 넘으면 저장 버튼 옆에 빨강이 아닌 **주황 경고** 「이 규칙은 시간당 N건을 보냅니다 — EEMUA 191 권고 상한 6건」. 상한은 공정 경보 관리 표준 EEMUA 191(정상 시 10분당 1건, 이상 시 10분당 10건 이하) [인용]에서 왔다 — 우리가 지은 수가 아니다.

**GPU**: 용량산정서가 「GPU는 남는다 — 디코딩이 먼저 걸린다」 [추정]고 적었다. 4장 중 **1장을 VLM 전용으로 예약**한다(MIG 또는 프로세스 고정). 실측(PERF-07)에서 1장으로 p95 2초를 못 지키면 크롭 해상도를 336px로 내린다 — Vaidio 실측 110~150ms [인용].

**모델 선택은 이 문서가 정하지 않는다.** 라이선스·온프렘·한국어 사유 품질 세 조건을 Code가 실측해 후보 2종을 낸다(AGPL 보고서 §5의 교훈 — 근거 없이 정하지 않는다). 후보 조건: 8B 이하 · 상업 이용 허용 · 오프라인 실행 · 한국어 출력.

**강제 도구**: `verify_vlm_advisory.py` — VLM 출력이 `verdict`·`status`·`severity` 어느 칸에도 쓰이지 않음(부작위 시험 QA-04) · 시간 예산 초과 시 「사유 없음」 경로 · 알림 발송 지연이 사유 대기로 늘지 않음.

### E2 · 네트워크가 센서다 — 카메라 맥박 군집 두절 · P-23 [판정]

**문제**: 「통신두절 = 재난 징후」(F-08)는 이 제품의 참신성 항목인데 SDN 명세 미수령으로 **손 밖**이다. 그런데 안양천이 넘치면 하천변 카메라가 **동시에** 죽는다. 그것을 알기 위해 SDN이 필요하지 않다 — 우리 스트림 수집기가 이미 안다.

**설계**
- 카메라마다 **맥박(heartbeat)** 칸: 마지막 프레임 수신 시각(`last_frame_at`). D-415가 `cameras_silent_24h`를 만들었지만 「조용함」과 「죽음」을 못 가른다고 적었다 [실측: onboarding_48 U1#3] — 맥박 칸이 그 둘을 가른다.
- **군집 규칙**: 같은 구역(Zone) 카메라 N대(기본 3) 중 M대(기본 2)가 **5분 안에** 동시에 맥박을 잃으면 `camera_cluster_down` 이벤트(등급 경계)를 K1 경로로 만든다. 단일 카메라 죽음은 시스템 이벤트(운영), **군집 죽음은 재난 징후 이벤트**(관제) — 둘은 다른 화면에 간다.
- 지도(F-09 FR-09-5 「지도 위 네트워크 상태」)에 카메라 맥박을 색이 아닌 **점멸/정지**로 그린다 — 색은 등급에 예약돼 있다(ISA-101).
- SDN 명세가 오면 I-3 링크 상태가 **같은 규칙의 두 번째 입력**이 된다. 규칙은 안 바뀌고 입력만 는다 — F-08의 「위치 매핑」 필드가 오기 전에 우리 쪽 위치(카메라 주소·좌표)로 먼저 돈다.

**정직 고지**: 이것은 F-08을 「구현」으로 바꾸지 않는다. F-08은 SDN 링크 상태를 말하고 그 절은 손 밖에 그대로 있다. 이것은 **새 절(OPS-15)** 이고, F-08이 열릴 때 시험이 재사용된다.

**강제 도구**: `verify_camera_pulse.py` — 시드에서 구역 A 카메라 3대 중 2대의 프레임을 멈추면 5분 안에 `camera_cluster_down` 1건 · 1대만 멈추면 0건(부작위) · 캐시를 지나지 않음(P-19).

### E3 · 증거 봉인 — 11조를 무기로 · P-24 [판정]

**문제**: 원본 영상 무반출(11조)은 지금 「못 하는 것」으로 적혀 있다(U3#14·U4#9 영구 ◐/○). 뒤집는다: **반출하지 않기 때문에 믿을 수 있다.** 지자체 담당자(U4)가 사는 것은 영상이 아니라 **감사에서 살아남는 기록**이다.

**설계 3층**
1. **해시 체인 감사로그(LAW-08)** — 이벤트의 스냅샷·판정·대응 전이·전파 기록 각 행에 `prev_hash`·`hash`(SHA-256)를 붙이고, **매일 00:00 그날의 마지막 해시를 일일 보고서 PDF/HWPX 꼬리에 인쇄**한다. 종이가 앵커다. 변조하면 다음 날 보고서와 어긋난다. 새 저장소 없음 — 기존 `AuditLogs`에 두 칸.
2. **개인정보 열람·삭제 청구 대응(LAW-07)** — U4 화면에 「열람 청구」 절차 한 장: 청구 접수 → 해당 시각·카메라의 이벤트 메타 + 스냅샷 **마스킹본** 조회 → 회신 기록. 원본 영상은 여전히 나가지 않는다 — 법이 요구하는 것은 「열람·존재 확인」이지 반출이 아니다 [인용]. 운영·관리 방침 서식 초안을 제품이 낸다(카메라 수·위치·보관 기간을 설정에서 자동 채움).
3. **AI기본법 5의무 내장(LAW-06)** — 34조 다섯을 화면과 문서로 맞춘다: 위험관리(오탐률 월간 · 알림 예산) · 설명가능성(E1 VLM 사유 + 규칙 판정 근거 표시, 이미 W2에 「규칙 판정 근거」 있음) · 이용자 보호(열람 청구 절차) · **사람 감독(사람 확인 없이 외부 전파 없음 — 이미 F-13 부정 AC와 같은 형태)** · 문서(고영향 AI 자기평가서 초안을 제품이 생성). 사전 고지 문구 「이 화면의 판정 후보는 AI가 제안하고 사람이 확정합니다」를 로그인 화면과 알림 본문에 넣는다.

**강제 도구**: `verify_evidence_chain.py` — 행 하나를 고치면 체인 검증 exit 1 · 마스킹본에 원본 경로 없음 · 열람 청구 회신이 감사로그에 남음.

**분모 변화 — 정직 고지**

| | v2.4 (105절) | **v2.5 (120절)** |
|---|---|---|
| 상용 오픈 가중 | 59.9% | **54.9%** |
| 손 안 도달율 | 72.0% (67/93) | **62.0%** (67/108) |
| 1파 → 2파 → 3파 | 64.1 → 81.8 → 90.8 | **58.9 → 80.8 → 91.8** |
| 4파 → 5파 | 99.5 → 100 | 99.5 → 100 |

**같은 59.9가 아니다.** 내려간 5%p는 잃은 것이 아니라 **못 재던 15절이 자로 들어온 것**이다(D-410의 논리). 첫 보고 한 턴은 두 수를 나란히 적고, 그다음부터 120절이 유일한 분모다. 래칫(D-311)은 「절이 는 턴」에 한해 예외를 인정한다 — 사유는 이 문서 번호다.

**영역 가중은 안 바꾼다.** ⑦사용성 10%에 절이 7개 늘어 절당 무게가 0.83→0.53%p로 준다. 그것이 맞다 — 화면이 늘어난다고 상용이 가까워지지 않는다. ②④가 여전히 큰 문이다.
