## ① 컨테이너 재생성 창 1회 (30분)

**결정 한 줄.** 개발 서버의 컨테이너를 한 번 새로 띄우는 30분 창을 허락한다 — 그 안에서 자격 3(MinIO·DB·서명키)을 진짜 값으로 바꾸고, `/backup`을 마운트하고, 운영 프로필로 뜨게 한다.

**왜 지금.** `verify_prod_settings` 7 중 1이 실패한다 — MinIO 두 값이 5자로 같고, DB 비밀번호 5자, 서명키가 `local-bringup-only-not-a-real-key`(33자 · 운영은 50자 미만 거부). 이 값들은 **컨테이너를 다시 만들어야** 바뀐다(기동 시 읽는다). 공개 URL(②)은 7/7 없이는 게이트가 열지 않는다(`deploy.sh`가 개발 프로필이면 배치 거부). SEC-18a·OPS-13a 잠김 2절도 이 창에서 돌아온다.

**대표가 하는 일.**

1. 날짜·시각을 정한다 — 관제 트래픽이 없는 시간(개발 서버이므로 평일 낮도 된다) · **30분**.
2. 영실에게 「창 승인 · 시각」 한 줄을 보낸다.
3. 창 시작 전 영실이 보낸 **runbook 1쪽**(`docs/agent/RUNBOOK_재생성창.md`)을 읽는다 — 순서·되돌리기가 적혀 있으면 됨. 값은 적혀 있지 않아야 정상이다.
4. 창이 끝나면 보고 첫 줄 「`prod_settings` 7/7 · `live_freshness` 초록 · 로그인 4/4」 를 확인한다.

**영실이 하는 일(창 앞 · 이번 턴).** vault에 새 값 3 준비(형식 통과 · 저장소·`.env*` 밖 · 터미널에 찍지 않음 P-135) · `.env.example`에 이름만 · runbook 1쪽 · `pre-recreate` 태그 · 백업 덤프 1 + 회수증(`ops_backup.py` → `ops_restore_drill.py`).

**영실이 하는 일(창 안 · 30분).**

| 분 | 일 | 확인 |
| --- | --- | --- |
| 0~5 | `ops_backup.py` 덤프 · 회수증 · `docker compose down`(볼륨 유지) | 덤프 파일 · 행 수 |

**끝났다는 증거.** `prod_settings` 7/7 · SEC-18a 잠김→구현 · `/backup`에 덤프 1 + 복원 시험 1 · `live_freshness` 초록 · 로그인 4/4.

## ② 사내 git 원격 · 스테이징 공개 URL

**결정 한 줄.** ⑴ 사내 git(GitLab/GitHub)에 저장소 원격 1개를 만들어 주소를 준다 ⑵ 소형 서버 1대 + 도메인 1개(또는 클라우드 월 사용 승인)를 준다.

**왜 지금.** `turn-p` 커밋 6개(537파일)가 개발 PC 한 곳에만 있다 — 디스크 하나가 죽으면 8일 치가 사라진다. 그리고 상용 기준 G1 「신규 사용자가 URL로 들어간다」가 0이다. 회사 밖에서 아무도 못 들어가면 대표·세종도 제품을 열어 볼 수 없다(CR 조건 ①).

**대표가 하는 일(원격 · 5분).**

1. 사내 git에 프로젝트 `guardianx-source` 생성(비공개) — 웹 화면에서 「New project」.
2. 영실 계정을 Maintainer로 초대.
3. 저장소 주소(`https://…/guardianx-source.git`) 한 줄을 영실에게.

**대표가 하는 일(스테이징 · 반나절).**

1. 둘 중 하나를 고른다 — ㉮ 사내 서버 1대(4 vCPU · 16GB · 200GB · GPU 없음 [추정]) ㉯ 클라우드 1대(월 수만 원대 [추정] · 견적은 영실 실측).
2. 도메인 1개(예: `stg.guardianx.…`)와 TLS 인증서 발급 권한(Let's Encrypt면 0원) — 이름은 영실이 `DJANGO_ALLOWED_HOSTS`·`CSRF_TRUSTED_ORIGINS`에 적어야 하므로 **먼저** 정해 준다.
3. 서버 접속 정보는 vault로(메일·슬랙 금지).

**영실이 하는 일.** 원격 push(`git bundle`은 이번 턴 미리 · push 5분) → 서버에 빈 환경 설치 재현(OPS-02 · 매뉴얼대로 · 손 밖→손 안) → `deploy.sh --profile prod --target staging` → 시드·훈련 데이터만(`data_source=seed` · 고객 데이터 0 · 원본 영상 0 · 실발송 0) → `walk_scenarios` S1~S3(데스크+390px).

**끝났다는 증거.** 원격에 master + `turn-p` · 대표가 휴대폰으로 `https://stg…/login`에 들어가 역할 계정으로 로그인 → 역할 홈이 뜬다 · PR 항목 1 = 1.

**되돌리기.** 서버 삭제 한 번 · 원격은 남긴다. **소요·비용.** 원격 5분·0원 · 서버 반나절 · 월 수만 원 [추정]. **함정.** ①이 먼저다 — 7/7 없이는 게이트가 URL을 열지 않는다 · 도메인이 정해져야 값 넷을 적을 수 있다.

## ③ 운영 공개 진입면 읽기 4건 「보내라」

**결정 한 줄.** 안양 운영 서버의 공개 URL에 **읽기 전용 GET 4건**(익명 · 로그인 없음 · 데이터 변경 0)을 보내는 것을 허락한다.

**왜 지금.** 개발 서버에서 익명으로 자료가 나가던 자리 5곳을 닫았다(익명 반출 5→0). **같은 문이 운영 서버에도 열려 있는지 모른 채** 여섯 턴이 지났다. 운영계는 읽기라도 대표 한 마디 뒤라는 불변 때문에 아무도 보내지 않았다.

**무엇을 보내나.** 익명 `GET` 4건 — 개발에서 닫은 자리(`config-management/list-optimized` · `auth/timezones` · `register-settings` · 사건 목록 `dsm/events`) [정확한 목록은 영실의 P-90 정본 · 4건 밖은 보내지 않는다]. 보내는 것은 브라우저가 로그인 화면을 열 때 하는 것과 같은 종류의 요청이다. 아무것도 쓰지 않는다.

**대표가 하는 일.** 「4건 보내라」 한 마디(슬랙·메일 · 시각 포함). 그뿐이다.

**영실이 하는 일.** 4건 → 상태 코드·바이트 수만 기록(본문 저장 없음) → 보고 한 줄 「운영 4건: 401·401·401·401」 또는 「200 N바이트 — 사고」.

**끝났다는 증거.** 4건 전부 401(또는 로그인 화면이 읽는 두 칸만 200). **200에 자료가 있으면** — 그 순간 결정 ④번째 항목(운영 긴급 패치 창 + 계정 회전)이 살아난다. 이것이 「조건부」의 뜻이다.

**되돌리기.** 없음(읽기). **소요.** 10분. **함정.** 4건 밖으로 넓히지 않는다 · 본문을 저장하지 않는다 · 결과가 200이면 **바로 대표에게** — 다음 턴을 기다리지 않는다.

## ④ SMTP 자격증명 + 경보 수신 주소

**결정 한 줄.** 메일을 보낼 계정 하나(회사 SMTP 또는 업무용 Gmail 앱 비밀번호)와 **경보를 받을 이메일 주소 1개**를 준다.

**왜 지금.** 사람에게 도달한 경보가 0건이다. 발송→도착은 기계로 쟀지만(mailpit) 받은 통이 우리가 세운 통이다. 새벽 3시 장애를 아무도 모른다. 초대 메일·비밀번호 재설정(G2 항목 6)·08:00 생존 알림(OPS-14)·월간 1쪽 발송이 전부 여기 걸린다.

**대표가 하는 일.**

1. 보내는 계정을 정한다 — ㉮ 회사 SMTP(정보팀에 「gx-alert@…」 발급 요청) ㉯ Gmail 업무 계정에 「앱 비밀번호」 생성(2단계 인증 켜진 계정 · Google 계정 → 보안 → 앱 비밀번호).
2. 다섯 값을 **vault(또는 봉인 메모)** 로 영실에게 — `EMAIL_HOST` · `EMAIL_PORT`(TLS 587) · `EMAIL_HOST_USER` · `EMAIL_HOST_PASSWORD` · `DEFAULT_FROM_EMAIL`. 이름은 `.env.example`에 이미 있다.
3. **받을 주소 1개**를 정해 준다(대표 본인 또는 당직 공용함). 이 주소가 `K2_OPS_ALERT_ROLE_CODES`(U5 시스템관리자)에 매인 계정의 이메일이 된다.
4. 도착한 첫 메일(제목 「[GuardianX] 생존 알림 08:00」 또는 「[GuardianX] 시험 발송」)을 **캡처 1장**으로 영실에게 돌려준다 — 이것이 OPS-10을 닫는 증거다.

**영실이 하는 일.** `.env` 값 5(D-204) · 허용 도메인(`K2_SEND_ALLOWED_DOMAINS`)에 회사 도메인 추가 · 시험 발송 1 · 08:00 생존 알림 켬 · 초대 메일 골격.

**끝났다는 증거.** 대표 수신함 캡처 1 · `verify_send_allowlist` 초록 · OPS-10 구현 · PR 항목 6·14 = 1.

**되돌리기.** 앱 비밀번호 폐기 1회. **소요.** 값 받은 뒤 2~3시간. **함정.** Gmail 앱 비밀번호는 16자 — 일반 비밀번호를 주면 실패한다 · 허용 도메인 밖으로는 실발송하지 않으므로 개인 도메인 수신함이면 도메인을 먼저 등록해야 한다.

## ⑤ 알림 채널 — 문자 / 카카오 알림톡 / 앱

**결정 한 줄.** 현장 대응자(U3)와 산불 진화대(F2)에게 가는 알림을 **이메일+웹푸시**로 갈지, **문자를 더할지** 정한다. 그리고 안양 현장에서 실제로 알림을 받는 사람이 누구인지(소방·시설·당직) 답 하나.

**왜 지금.** U3 왕복(접수 「1」 회신)이 채널에 걸려 있다. 웹푸시(PWA · 앱 없이 잠금화면 알림)는 v1.1이 이미 만든다 — 결정이 늦어도 왕복은 닫힌다. 문자는 발송 어댑터만 준비돼 있고 켜려면 계정이 필요하다.

**대표가 하는 일.**

1. 안양 관제팀에 한 질문 — 「새벽에 알림을 실제로 받는 사람이 누구이고, 지금은 무엇으로 받습니까(전화·문자·카톡)?」 답을 영실에게.

3. ㉯면 발송 계정의 API 키를 vault로.

**영실이 하는 일.** ㉮: 웹푸시 구독→훈련 사건→잠금화면 도달 캡처 1 · ㉯: 어댑터 켬 + 「1」 회신 파서 + 훈련 채널로 발송 0 실측 → 실채널 1.

**끝났다는 증거.** 대표 휴대폰에 훈련 사건 알림 도달 캡처 1(푸시 또는 문자) · 「1」 회신 → 관제 화면 「접수」.
