**이 문서가 정하는 것 하나.** 「어디까지가 플랫폼이고 어디부터가 앱인가」를 코드 자리와 계약 파일로 못박는다. 경계가 문서에만 있으면 두 번째 앱에서 무너진다(구현계획 v2.0 §2.3 「대안 없는 금지는 규율이 아니다」). 그래서 경계마다 **어느 저장소 경로에 사는지 · 어느 계약 파일이 선언하는지 · 어느 게이트가 막는지**를 함께 적는다.

## 0. 한 장 요약

GuardianX는 이미 세 겹으로 되어 있다 — 인수 자산(dj-core · 드론·배송)과 플랫폼 커널(`kernels/k1~k6`)과 첫 번째 앱(`apps/dsm`). 그런데 셋의 경계가 코드에는 있고 문서에는 없어서, 산불감시 App을 얹으려 하면 「K1 사건 커널은 공통인가, 등급 규칙은 앱인가」를 매번 다시 묻게 된다. 이 문서는 **4층**으로 답한다.

| 층 | 이름 | 무엇 | 소유 | 앱 추가 시 |
| --- | --- | --- | --- | --- |
| **L-P** | 플랫폼 공통 | 테넌시 · 인증 · 역할·메뉴 · 감사 · 계량 · 파일 · 설정 · 배포·게이트 · 앱 레지스트리 | 플랫폼 운영자(U0) | 손대지 않는다 |
| **L-T** | 기술 공통 | 스트림 수집 · AI 추론 파이프라인 · 이벤트 버스 · 알림 채널(문자·메일·푸시·CBS) · 지도 · 보고서 엔진(PDF·HWPX) · 모바일 셸 · 웹훅 · 저장·보존 · 드론 커넥터 | 플랫폼 팀 | 능력 선언만 추가 |
| **L-B** | 업무 공통 모듈 | 사건 생명주기(K1) · 알림 왕복(K2) · 역할 홈(K3) · 보고서(K4) · 신뢰·감사 체인(K5) · 오탐 학습(K6) · 대응 시계 · 훈련 모드 · 인계 · 온보딩 진행률 · 열람청구 | 플랫폼 팀 | 설정으로 인스턴스화 |
| **L-A** | 앱 개별 | 탐지 클래스 · 등급 규칙 · 대응 흐름·상태 확장 · 사용자 정의·역할 프리셋 · 화면 · 서식 · 외부 연계 어댑터 · 용어 | 앱 팀 | 앱 폴더 하나 + 계약 파일 |

**재난안전관리 App(DSM)** 은 R(대응-조치형) 아키타입의 1호이고, **산불감시 App(FWS)** 은 같은 R 아키타입에 **P(순찰-대장형)** 의 감시 구간이 앞에 붙은 인스턴스다. 둘의 차이는 탐지 클래스·등급 규칙·대응 흐름·화면·서식·외부 연계 **여섯**뿐이며, 그 여섯은 전부 L-A 안에 있다. 그 밖에 앱이 손대야 하는 것이 나오면 그것은 앱이 아니라 **플랫폼 결손**이고 릴리스 트레인(§6)으로 올린다.

## 1. 계층 — 구현계획 v2.0의 6계층 위에 「무엇이 공통인가」를 얹는다

구현계획 v2.0은 **어디에 코드가 사는가**(L4 셸 · L3 앱 · L2 코어 · L1 커널 · L0 커넥터 · L-1 엣지)를 정했다. 이 문서는 그 위에 **누가 소유하고 앱이 무엇을 바꿀 수 있는가**(L-P · L-T · L-B · L-A)를 얹는다. 둘은 직교한다 — 예를 들어 알림 채널은 코드로는 L1 커널이지만 소유로는 L-T 기술 공통이고, 등급 규칙은 코드로는 L3 앱 폴더에 있고 소유로는 L-A 앱 개별이다.

```
                 소유 축 (이 문서)        코드 축 (구현계획 v2.0)
┌─────────────┬──────────────────────┬────────────────────────────────┐
│ L-A 앱 개별  │ 탐지 클래스·등급·흐름  │ L3 gx-apps/<code>/**            │
│             │ 화면·서식·연계·용어    │ L4 셸의 앱 슬롯(screens.yaml)    │
├─────────────┼──────────────────────┼────────────────────────────────┤
│ L-B 업무 공통│ K1~K6·대응시계·훈련   │ L1 kernels/** · L2 core(mission)│
│             │ 인계·온보딩·열람청구   │                                │
├─────────────┼──────────────────────┼────────────────────────────────┤
│ L-T 기술 공통│ 스트림·추론·버스·채널  │ L1 kernel(event-bus·notify)     │
│             │ 지도·보고서엔진·모바일  │ L0 gx-link(dji·mavlink·sms·cbs) │
│             │ 웹훅·저장·드론         │ L4 셸(지도 컨테이너·플레이어)    │
├─────────────┼──────────────────────┼────────────────────────────────┤
│ L-P 플랫폼  │ 테넌시·인증·역할·메뉴  │ L1 kernel(tenancy·authn·menu·   │
│    공통     │ 감사·계량·파일·설정    │   audit·metering·registry)      │
│             │ 배포·게이트·레지스트리 │ scripts/verify_* · deploy.sh    │
└─────────────┴──────────────────────┴────────────────────────────────┘
```

## 4. 앱 간 연계 — 이벤트 버스 한 길

| 시나리오 | 발행 | 구독 | 처리 |
| --- | --- | --- | --- |
| 산 인접 마을 CCTV가 연기를 잡았다 | DSM `dsm.event.created{type=fire, zone.forest_adjacent=true}` | FWS | FWS가 같은 카메라 프레임을 연기 모델로 재추론 → 산불 후보 사건 생성 · DSM 사건에 「산불 후보 #」 참조 |
| 산불이 확정됐다 | FWS `fws.fire.confirmed{stage=initial}` | DSM | 상황실 큐에 「산불 · 시스템 사건」 카드 · 재난안전과 상황보고 제1보 초안에 자동 삽입 |
| 대피 명령이 내려졌다 | FWS `fws.evacuation.ordered{zone, deadline}` | DSM | CBS 초안(90/157자) 생성 → 재난안전과 승인 화면으로 · 관제 화면 대피 구역 오버레이 |
| 산불 진화 완료 | FWS `fws.fire.extinguished` | DSM | 상황보고 최종보 초안 · 시스템 사건 종결 |
| 카메라가 죽었다 | 플랫폼 `platform.camera.down` | DSM · FWS | 두 앱 모두 시스템 프리셋에 표시 |

규칙: 이벤트 스키마는 `k_event_contract`에 버전과 함께 등록 · 구독자가 없어도 발행은 실패하지 않는다 · 앱은 상대 앱 테이블을 조회하지 않는다(참조 ID만).

## 5. 런타임 — 한 테넌트에 앱 두 개가 뜨는 모양

```
┌ 상단바  안양시 │ [재난안전 관제 ▾ 산불감시]  훈련·시드 배지 · 🔔 · 내 정보 ┐   ← L4 셸(앱 레일)
├ 사이드바(역할 × 설치 앱의 메뉴 합집합 · 허용 목록) ─────────────────────┤
│  홈(역할 홈: 설치 앱마다 카드 띠 하나씩 — U1은 「지금 처리할 것」에       │
│      DSM 카드와 FWS 카드가 한 큐로 섞여 우선순위로 정렬)                 │
│  사건 · 카메라 · 인계 ······ [DSM]                                       │
│  산불 상황판 · 감시 · 자원 · 대피 ······ [FWS]                          │
│  보고 · 통계 · 감사 ······ [공통 K4·K5 — 앱 필터]                       │
│  관리(사람·알림·시스템·앱) ······ [공통 · U5]                            │
└──────────────────────────────────────────────────────────────────────┘
```

| 항목 | 규칙 |
| --- | --- |
| 설치 | 테넌트별 `k_app_installation` — 플랫폼 운영자가 설치·버전 고정 · 테넌트 관리자는 켜고 끄기만 |
| 역할 홈 | 역할 홈은 K3가 그리고, 앱은 **카드 띠**를 슬롯에 꽂는다 · 큐형 홈(U1)은 두 앱 사건을 한 큐로 병합(등급·경과 정렬) |

## 7. 플랫폼 운영자(U0) — 세부 기능명세

플랫폼 운영자는 두 사람이다 — **에스비(채널 파트너) 1차 운영자**와 **가이온 2차 운영자**(DA-03 Flow 4 · SLA 1차 4영업시간 · 2차 1영업일). 둘은 같은 콘솔을 쓰고 권한만 다르다. 테넌트 화면에는 절대 들어가지 않는다 — 테넌트 화면에서 A 고객 데이터를 B 고객이 보면 채널 신뢰가 끝난다(DA-03).
